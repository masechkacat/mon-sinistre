# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Контекст всего монорепозитория — в корневом `../../CLAUDE.md`; он загружен
всегда, и правила оттуда (жёсткие ограничения продукта, доменная модель) здесь
не повторяются. Ниже — только специфика `@mon-sinistre/api`.

## Стек

NestJS 11 на **Fastify** (не Express — плагины подключаются через
`app.register`, см. `src/main.ts`), **Prisma** + PostgreSQL, Passport (local +
JWT), Swagger на `/docs`.

## Команды (из apps/api)

Запуск, юнит-тесты и линт — из корня (`npm run dev:api` делегирует в
`start:dev`, который читает `.env` через `--env-file`). Здесь только то, чего в
корне нет:

```bash
npm test -- steps        # один тест по подстроке пути
npm run test:int         # *.int-spec.ts против реального Postgres — нужен npm run db:up
npm run test:cov
npm run lint:fix
npm run prisma:generate  # после каждой правки schema.prisma
npm run migration:dev    # prisma migrate dev — локально
npm run migration:deploy # prisma migrate deploy — прод/CI
npm run seed             # импорт справочника коммун COG, идемпотентен
```

База данных поднимается из корня: `npm run db:up`. Перед запуском API нужен
собранный contracts (`npm run build:contracts` из корня) — рантайм импортирует
его из `dist/`. В тестах это не нужно: jest через `moduleNameMapper`
подставляет исходники `packages/contracts/src`.

## Модули

У модулей со своими правилами — собственный `CLAUDE.md` рядом с кодом; он
подхватывается, когда сессия работает с файлами модуля:

- `src/prisma/` — подключение Prisma 7, сборка connection string из `DB_*`,
  `escapeLikePattern`, клиент интеграционных тестов → `src/prisma/CLAUDE.md`.
- `src/communes/` — импорт справочника COG, нормализация названий, колонка
  `nameNormalized`, поиск `GET /communes?q=` → `src/communes/CLAUDE.md`.
- `src/mail/` — каркас письма, единственная точка отправки, транспорты →
  `src/mail/CLAUDE.md`.

Правила этих модулей, действующие на **весь** API, продублированы строкой в
«Правилах проекта» ниже: модульный файл читает только тот, кто уже открыл
модуль, а запрет «второй реализации не заводить» нужен и тому, кто пишет новый.

## Состояние скелета

- **Валидация переменных окружения на старте** (`src/config/env.validation.ts`,
  class-validator): отсутствующий или некорректный секрет валит приложение при
  bootstrap, а не при первом использовании. Новая переменная добавляется в эту
  схему и в `.env.example` одним коммитом.
  - `FRONTEND_URL` обязателен и принимается только как схема с хостом
    (`http`/`https`, `require_tld: false` — иначе `http://localhost:3000` из
    `.env.example` не пройдёт; путевой префикс отвергается, причина —
    `docs/decisions.md`, 03.08.2026): из него каркас писем собирает все ссылки.
  - `MAIL_FROM` обязателен и проверяется как адрес: без отправителя письмо не
    собирается ни одним транспортом (`docs/decisions.md`, 03.08.2026).
  - `MAIL_TRANSPORT` (`file` | `scaleway`, по умолчанию `file`) выбирает
    транспорт письма; читает его один `useFactory` модуля почты
    (`src/mail/CLAUDE.md`); `MAIL_SENDER_DOMAIN`, `SCW_SECRET_KEY` и
    `SCW_PROJECT_ID` обязательны **только** при `scaleway` (`@ValidateIf`):
    свежий клон отправляет письма локально, без аккаунта у провайдера.
    При `NODE_ENV=production` локальный транспорт отвергается на старте, но
    страховка срабатывает лишь у процесса, объявившего себя продакшеном, — а
    `start:prod` `NODE_ENV` не выставляет: задать её обязан тот, кто запускает
    (задача деплоя, issue 29).
- **Глобальный rate limiting** (`@nestjs/throttler`, 100 запросов в минуту,
  `ThrottlerGuard` через `APP_GUARD`). Auth-эндпоинтам при появлении задать
  более строгие лимиты через `@Throttle()`.
- `app.enableShutdownHooks()` в `main.ts` — корректная остановка cron-задач по
  SIGTERM; тот же механизм вызывает disconnect `PrismaModule`.
- `tsconfig.build.json` исключает из продакшен-сборки `*.spec.ts`,
  `*.int-spec.ts`, `*.int-helper.ts`, `*.test-helper.ts`; `nest build`
  использует его автоматически.

## Интеграционные тесты

Решение и его причины — `docs/research/commune-referential.md`; здесь действующие
правила:

- Спеки — `*.int-spec.ts` рядом с кодом в `src/`. Юнит-конфиг в `package.json`
  их не видит (суффикс не подпадает под `.*\.spec\.ts$`), поэтому pre-commit хук
  и корневой `npm test` остаются быстрыми и без Docker-требования.
- `jest.int.config.js`: `maxWorkers: 1` обязателен, пока тесты делят одну базу;
  если прогон станет медленным — база-на-воркера через `JEST_WORKER_ID`, не
  testcontainers.
- База — `${DB_NAME}_test` на том же docker-compose Postgres.
  `test/jest.int.global-setup.js` создаёт её при отсутствии и прогоняет
  `prisma migrate deploy` с переопределённым `DB_NAME`; `test/jest.int.env.js`
  тем же переопределением направляет туда `PrismaService`. Имя тестовой базы оба
  вычисляют общим хелпером `test/test-db-name.js` — setup и тесты обязаны
  смотреть на одну базу.
- Между тестами — `TRUNCATE` затронутых таблиц в `beforeEach`, не пересоздание
  схемы.
- Суффиксы `*.int-helper.ts` (для интеграционных спеков) и `*.test-helper.ts`
  (для юнит-спеков) — тестовый код, живущий в `src/` ради алиаса `src/*` и
  охвата `npm run lint`; под `testRegex` не подпадают. Общий хелпер заводить,
  когда два спека задают один и тот же вопрос: два его написания ответят
  по-разному (образец — `src/mail/mail-links.test-helper.ts`).
- В CI понадобится сервисный Postgres 18 — зафиксировать при настройке CI.

## Правила проекта

- Глобальный `ValidationPipe` с `whitelist + forbidNonWhitelisted`: у каждого
  эндпоинта, принимающего данные, должен быть DTO с декораторами
  class-validator, иначе любое тело запроса будет отклонено. Пайп создаётся
  фабрикой `createGlobalValidationPipe` (`src/config/validation-pipe.ts`) — её
  же использовать в интеграционных тестах, конфигурацию не копировать.
- Принадлежность объекта пользователю проверяется в условии запроса
  (`where: { ..., user }`): чужой и несуществующий объект дают одинаковый
  ответ — **404, не 403**.
- **Логи — только через `Logger` из `@nestjs/common`**, с контекстом класса
  (`private readonly logger = new Logger(CommuneImportService.name)`);
  `console.*` в коде приложения не используется. Уровни задаются один раз в
  `main.ts`: `error`/`warn`/`log` в продакшене, плюс `debug`/`verbose` в
  остальных средах; ошибка логируется с уровнем `error` и стеком, а не `log`.
  `nestjs-pino` не заводить, пока нет сбора логов. Почему так —
  `docs/decisions.md`, запись о логах от 03.08.2026.
- Запрет на персональные данные в логах действует и на логирование ошибок:
  пишутся идентификаторы, коды и счётчики, но не тело запроса и не DTO целиком.
- **Swagger-схема свойств — через CLI-плагин `@nestjs/swagger`** (`plugins` в
  `nest-cli.json`, `introspectComments: true`): типы полей и JSDoc-комментарии
  DTO попадают в `/docs` без ручных декораторов. `@ApiProperty` пишется только
  там, где плагину нечего вывести: пример значения, описание вне JSDoc,
  брендированные типы contracts (`IsoDate` стирается до `string` — указывать
  `type: String, format: 'date'`). Response-класс с `implements` контракта нужен
  по-прежнему (интерфейсы contracts на рантайме отсутствуют); ts-jest плагин не
  применяет — схему проверять на запущенном приложении (`/docs`), не в тестах.
  Контекст решения — `docs/decisions.md`, запись о плагине от 03.08.2026.
- Refresh-токены — в httpOnly-cookie с ротацией; access — в теле ответа.
  Секреты и сроки — в `.env` (`.env.example` — актуальный список переменных).
- Доменные даты в Postgres — колонки `date`, не `timestamp`. Тесты хелперов
  `IsoDate` — `src/common/iso-date.spec.ts`: у contracts нет своего test
  runner'а, jest подставляет его исходники через `moduleNameMapper`.
- Рассылка напоминаний — `@nestjs/schedule`, раз в сутки, не больше одного
  письма пользователю в день; сбой отправки одному получателю не прерывает
  остальных.
- **Строки, которые читает пользователь продукта (письма, тексты ответов), —
  только в `src/i18n/fr.ts`**: типизированный словарь `as const`, импорт
  напрямую, параметры — функциями-полями; фичи добавляют свои строки в ветки
  того же объекта, второго файла и текстов в `packages/contracts` быть не
  должно. Административные термины употребляются только в составе объясняющей
  формулировки (`fr.mail.terms.arreteCatNat`) — сторож `src/i18n/fr.spec.ts`
  проверяет это, а заодно отсутствие разметки и типографику по всему словарю.
  Почему словарь, а не i18n-библиотека — `docs/research/emails.md`. Описание
  OpenAPI в `main.ts` под правило не подпадает: его читают разработчики в
  `/docs`, а не пользователи.
- **Письмо уходит только через `MailService.send()`** — единственная точка
  выхода письма из API; правила каркаса — `src/mail/CLAUDE.md`.
- **Экранирование LIKE — только `escapeLikePattern`** (`src/prisma/`), для
  любого пользовательского ввода в `startsWith`/`contains`/`endsWith`; второй
  реализации не заводить.
- **Поисковый ключ названия коммуны — только `normalizeCommuneName`**
  (`src/communes/`); ею нормализуются и колонка, и запрос.

## Актуализация документации

- Новый модуль со своими правилами — заводить `CLAUDE.md` рядом с его кодом и
  добавлять строку в «Модули» выше; правило, действующее на весь API, —
  дополнительно строкой в «Правилах проекта».
- Изменения в устройстве существующего модуля — в его `CLAUDE.md`, в том же
  коммите, что и код.
- Изменения в аутентификации, конфигурации или структуре `src/` — в этом файле.
- Изменения, затрагивающие весь монорепозиторий (команды, порядок сборки,
  contracts), — в корневом `../../CLAUDE.md`.
- Факт, уже написанный в корневом `CLAUDE.md`, здесь не повторять: корневой файл
  загружен всегда, вторая копия только разойдётся с первой.
