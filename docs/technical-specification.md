# Техническое задание

## Jalons. Сопровождение цикла продления прав MDPH

> Рабочее название проекта. `Jalon` (фр.) — веха, ориентир на местности.

---

## О проекте

«Jalons» — веб-приложение, которое ведёт семью через цикл продления прав MDPH: рассчитывает персональный график подготовки от даты истечения текущих прав, следит за сроками годности медицинских документов и заранее напоминает о шагах, которые нужно начать выполнять.

Приложение не даёт юридических консультаций и не подаёт документы за пользователя. Его задача — не дать пропустить сроки.

## Общая концепция проекта

Права, назначенные MDPH, выдаются на срок и требуют продления. Подготовка занимает до года: запись к специалистам занимает месяцы, медицинский сертификат имеет ограниченный срок годности, а само досье нужно подать сильно заранее, потому что рассмотрение занимает от 4 до 6 месяцев. Семьи, проходящие цикл впервые, не знают этой последовательности и опаздывают.

Пользователь вводит одну дату — когда истекают текущие права. Приложение разворачивает из справочника процедур персональный план: что делать, когда начинать, в каком порядке. Дальше оно ведёт этот план: отмечает выполненное, пересчитывает даты при сдвигах, следит за сроками годности загруженных документов и рассылает напоминания по электронной почте.

Ключевое отличие от календаря: пользователю не нужно знать, что именно вносить в календарь. Приложение знает это за него.

## Технические требования

Для разработки применяется **монолитная архитектура**. Проект разрабатывается и поддерживается одним разработчиком, объём предметной области не оправдывает разделение на сервисы. Модульная структура обеспечивается средствами NestJS: каждый модуль решает свою задачу.

Бэкенд разрабатывается на **NestJS** с использованием **Fastify** в качестве HTTP-сервера. Работа с базой данных — через **TypeORM**. СУБД — **PostgreSQL**. Изменения схемы выполняются только через миграции; `synchronize` в продакшене запрещён.

Фронтенд разрабатывается на **Next.js** с использованием библиотеки компонентов **shadcn/ui** (на основе Base UI). Компоненты, требующие сложного управления фокусом и клавиатурой — прежде всего выбор даты, — реализуются на **React Aria Components**.

Код разрабатывается только на **TypeScript**. Используется актуальный LTS-релиз **Node.js**.

Язык интерфейса — **французский**. Все пользовательские строки выносятся в файлы локализации, даже если вторая локаль не реализуется в рамках MVP. Даты форматируются по локали `fr-FR`.

Приложение должно соответствовать уровню **WCAG 2.1 AA**; в качестве отраслевого ориентира используется **RGAA 4.1.2**. Требования вынесены в раздел «Доступность» и являются обязательными к проверке наравне с функциональными.

В корневой директории размещается файл `specification.md` с инструкциями по запуску проекта.

Техническое задание не определяет контракты API и внутреннюю структуру модулей. Проектирование ресурсов, схемы базы данных и прочие архитектурные решения принимаются разработчиком самостоятельно.

## Функциональность

### 1. Регистрация и авторизация пользователей

1.1. Регистрация доступна только анонимным клиентам.

1.2. Для регистрации клиент передаёт следующий набор информации:

- **Электронная почта** (обязательно). Используется в качестве логина. Адрес уникален: в базе данных не может быть двух пользователей с одинаковым email.
- **Пароль** (обязательно). Минимальная длина 8 символов, максимальная 64. Ограничение снизу выбрано осознанно выше учебного минимума: приложение хранит сведения о состоянии здоровья.
- **Имя** (обязательно). Минимальная длина 2 символа, максимальная 50.

1.3. Перед записью информации в базу данных выполняется валидация. В случае обнаружения ошибок клиенту отправляется полный список.

1.4. Пароль не хранится в базе данных в открытом виде. Вместо пароля хранится его хеш, полученный с помощью пакета `bcrypt`.

1.5. Приложение фиксирует дату регистрации пользователя.

1.6. В случае успешной регистрации приложение возвращает корректный код состояния и объект с информацией о созданном пользователе. Хеш пароля в ответ не включается ни при каких условиях.

1.7. Авторизация построена на основе JWT. После успешной проверки логина и пароля приложение возвращает пару токенов: access-токен в теле ответа и refresh-токен в httpOnly-cookie.

1.8. Реализуется ротация refresh-токенов: при обновлении пары старый refresh-токен отзывается. Отозванные и истёкшие токены удаляются по расписанию.

1.9. Авторизованный пользователь может сменить пароль. Для смены передаётся:

- **Текущий пароль** (обязательно). Проверяется на соответствие сохранённому хешу.
- **Новый пароль** (обязательно). Ограничения совпадают с п. 1.2. Новый пароль должен отличаться от текущего.

1.10. Смена пароля отзывает все refresh-токены пользователя, кроме текущей сессии.

1.11. Пользователь может запросить восстановление доступа по электронной почте. Приложение отправляет письмо со ссылкой, содержащей одноразовый токен. Срок действия токена — 60 минут. Повторный запрос до истечения предыдущего токена не создаёт новый токен, а продлевает попытку отправки письма.

1.12. Ответ на запрос восстановления не зависит от того, зарегистрирован ли указанный адрес. Приложение не раскрывает факт существования учётной записи.

1.13. В приложении определены две роли: `USER` и `ADMIN`. Роль `ADMIN` требуется только для управления справочником процедур (раздел 3). Все прикладные сценарии выполняются под ролью `USER`.

1.14. Отношение пользователя к подопечному (ведёт досье на себя или на другого человека) ролью **не является** и определяется на уровне карточки подопечного (раздел 2).

### 2. Подопечные

2.1. Подопечный (`bénéficiaire`) — человек, на которого оформлено досье. Все операции с подопечными доступны только авторизованным пользователям.

2.2. Пользователь может создать одну или несколько карточек подопечных. Один аккаунт ведёт досье и на себя, и на своих детей.

2.3. Для создания карточки клиент передаёт следующий набор информации:

- **Имя** (обязательно). Минимальная длина 2 символа, максимальная 50.
- **Дата рождения** (обязательно). Не может быть в будущем.
- **Признак «это я сам»** (обязательно, логический). Определяет, ведёт ли пользователь досье на себя.
- **Департамент** (обязательно). Значение из справочника департаментов. Определяет территориально компетентную MDPH и ожидаемый срок рассмотрения. Обоснование: MDPH создаются на уровне департамента, и фактические сроки рассмотрения между ними различаются существенно.

2.4. Приложение вычисляет и хранит признак совершеннолетия подопечного на основании даты рождения. Признак используется для подбора применимых процедур.

2.5. Пользователь имеет доступ только к своим карточкам подопечных. Попытка обратиться к чужой карточке возвращает ошибку, не раскрывающую факт её существования.

2.6. Пользователь может редактировать и удалять свои карточки. Удаление карточки приводит к каскадному удалению всех связанных досье, шагов и документов.

2.7. Диагноз, медицинские заключения и любые сведения о характере нарушений в карточке **не хранятся**. Обоснование приведено в разделе «Защита персональных данных».

### 3. Справочник процедур

3.1. Справочник процедур — набор шаблонов, на основе которых строятся планы пользователей. Справочник заполняется сидером при инициализации базы данных.

3.2. Шаблон процедуры содержит:

- **Код** (обязательно). Уникальный машинный идентификатор, например `RENOUVELLEMENT_AEEH`.
- **Название** (обязательно). Отображаемое название на французском языке.
- **Описание** (обязательно). Максимальная длина 1000 символов.
- **Законный срок рассмотрения в месяцах** (обязательно). Целое число. Срок, установленный законодательством для данного типа обращения. Одинаков для всей территории страны.
- **Срок рассмотрения по умолчанию в месяцах** (обязательно). Целое число. Используется при расчёте рекомендуемой даты подачи, если для департамента подопечного нет отдельного значения. Задаётся консервативно, то есть не меньше законного срока.
- **Применимость по возрасту** (опционально). Ограничение вида «до 18 лет» / «от 18 лет». Используется для подбора процедур, применимых к подопечному.
- **Признак активности** (обязательно, логический).

3.3. Шаблон процедуры содержит упорядоченный набор шаблонов шагов. Шаблон шага содержит:

- **Название** (обязательно). Максимальная длина 200 символов.
- **Описание** (обязательно). Что именно нужно сделать. Максимальная длина 2000 символов.
- **Опорная точка** (обязательно). Одно из двух значений: `DATE_EXPIRATION` (дата истечения прав) или `DATE_DEPOT` (дата подачи досье).
- **Смещение в днях** (обязательно). Целое число, может быть отрицательным. Дата шага вычисляется как опорная дата плюс смещение.
- **Обязательность** (обязательно, логический).
- **Тип документа** (опционально). Ссылка на тип документа, который производится этим шагом. Связывает шаг с контролем сроков годности (раздел 6).
- **Порядок отображения** (обязательно). Целое число.

3.4. Любой авторизованный пользователь может запросить список активных процедур, применимых к конкретному подопечному. Фильтрация выполняется по возрасту подопечного на основании п. 3.2 и п. 2.4.

3.5. Создание, редактирование и удаление шаблонов доступно только пользователям с ролью `ADMIN`.

3.6. Изменение шаблона процедуры **не влияет** на уже созданные досье. Досье хранит копию плана на момент создания. Обоснование: пользователь не должен обнаружить, что его план изменился сам собой.

3.7. Справочник, поставляемый в MVP, содержит как минимум одну полностью заполненную процедуру: продление прав, назначенных CDAPH, для несовершеннолетнего подопечного.

3.8. Справочник департаментов заполняется сидером и содержит для каждого департамента: код, название, ожидаемый срок рассмотрения в месяцах, дату, по состоянию на которую указан срок.

3.9. При расчёте плана применяется срок рассмотрения департамента подопечного. При его отсутствии применяется срок по умолчанию из п. 3.2.

3.10. Пользователь может переопределить срок рассмотрения для конкретного досье. Указанное пользователем значение имеет приоритет над справочными. Обоснование: пользователь может располагать сведениями о своей MDPH, которых нет в справочнике.

3.11. Каждый шаблон процедуры и каждый шаблон шага содержит:

- **Ссылку на официальный источник** (обязательно). Адрес страницы или реквизиты нормативного акта, на основании которого заданы сроки и требования.
- **Дату последней сверки** (обязательно). Дата, когда содержание было в последний раз проверено по источнику.

3.12. Дата последней сверки и ссылка на источник отображаются пользователю в интерфейсе шага. Пользователь должен иметь возможность проверить любое утверждение приложения самостоятельно.

3.13. Если с даты последней сверки прошло более шести месяцев, приложение отображает предупреждение о том, что сведения могли устареть, и рекомендует уточнить их в своей MDPH.

3.14. Формулировки шагов не должны утверждать требования категорично там, где практика различается между департаментами. Используются формулировки, указывающие на необходимость уточнения.

### 4. Досье и расчёт плана

4.1. Досье (`dossier`) — один цикл продления прав от подготовки до получения решения. Создавать досье могут только авторизованные пользователи.

4.2. Для создания досье клиент передаёт следующий набор информации:

- **Идентификатор подопечного** (обязательно).
- **Код процедуры** (обязательно). Процедура должна быть активна и применима к подопечному по возрасту.
- **Дата истечения текущих прав** (обязательно). Должна быть в будущем.

4.3. При создании досье приложение выполняет расчёт плана:

- **Рекомендуемая дата подачи** вычисляется как дата истечения прав минус применимый срок рассмотрения, выраженный в месяцах. Применимый срок определяется по правилу из пп. 3.9 и 3.10: значение, заданное пользователем, иначе значение департамента подопечного, иначе значение процедуры по умолчанию.
- Для каждого шаблона шага создаётся шаг досье. **Плановая дата шага** вычисляется как опорная дата плюс смещение в днях, где опорной датой выступает либо дата истечения прав, либо рекомендуемая дата подачи — в соответствии с п. 3.3.

4.4. Пользователь может изменить дату подачи вручную. При изменении даты подачи все шаги, привязанные к опорной точке `DATE_DEPOT` и **не отмеченные как выполненные**, пересчитываются. Даты выполненных шагов не изменяются.

4.5. Если указанная пользователем дата подачи оставляет до истечения прав меньше, чем срок рассмотрения процедуры, приложение сохраняет дату, но возвращает предупреждение о риске перерыва в выплатах. Сохранение не блокируется: пользователь может знать о своей ситуации больше, чем приложение.

4.6. Досье находится в одном из состояний: `PREPARATION`, `DEPOSE`, `DECISION_RECUE`, `ARCHIVE`. Состояние после создания — `PREPARATION`.

4.7. Пользователь может иметь одновременно не более одного досье в состоянии `PREPARATION` или `DEPOSE` для одной пары «подопечный + процедура».

4.8. Пользователь имеет доступ только к досье своих подопечных.

4.9. Пользователь может запросить детальную информацию по досье. Ответ включает: данные подопечного, процедуру, обе даты, состояние, полный список шагов с их состояниями, список документов и сводку по ближайшему требующему внимания шагу.

### 5. Шаги плана

5.1. Шаг досье находится в одном из состояний, которое **вычисляется**, а не хранится, за исключением факта выполнения:

- `FAIT` — шаг отмечен пользователем как выполненный;
- `EN_RETARD` — шаг не выполнен, плановая дата в прошлом;
- `A_FAIRE` — шаг не выполнен, до плановой даты остаётся не более 30 дней;
- `A_VENIR` — шаг не выполнен, до плановой даты остаётся более 30 дней.

5.2. Пользователь может отметить шаг выполненным. При отметке фиксируется фактическая дата выполнения. По умолчанию — текущая дата, пользователь может указать другую. Фактическая дата не может быть в будущем.

5.3. Пользователь может отменить отметку о выполнении. Фактическая дата при этом очищается.

5.4. Отметка шага выполненным не блокируется порядком: пользователь может выполнить шаги в любой последовательности.

5.5. Пользователь может добавить в досье собственный шаг, не предусмотренный шаблоном. Для создания передаётся:

- **Название** (обязательно). Максимальная длина 200 символов.
- **Плановая дата** (обязательно).
- **Описание** (опционально). Максимальная длина 2000 символов.

5.6. Собственные шаги не пересчитываются при изменении даты подачи. Их даты задаются пользователем явно.

5.7. Пользователь может редактировать и удалять только собственные шаги. Шаги, созданные из шаблона, удалению не подлежат; их можно отметить как неприменимые.

5.8. Список шагов сортируется по плановой дате по возрастанию. Шаги с состоянием `EN_RETARD` дополнительно выделяются в отдельную группу в начале списка.

### 6. Документы и контроль сроков годности

6.1. Документ — запись о полученной справке, заключении или ином материале досье. Хранение самих файлов в MVP не реализуется; хранятся только сведения о документе. Обоснование приведено в разделе «Защита персональных данных».

6.2. Для регистрации документа клиент передаёт следующий набор информации:

- **Тип документа** (обязательно). Значение из справочника типов.
- **Дата выдачи** (обязательно). Не может быть в будущем.
- **Срок годности в месяцах** (опционально). Целое число. При отсутствии значения берётся значение по умолчанию из справочника типов документов. Отсутствие значения в обоих источниках означает бессрочный документ.
- **Комментарий** (опционально). Максимальная длина 500 символов. Поле предназначено для пометок вида «получен у психолога IME», но не для медицинского содержания.

6.3. Приложение вычисляет дату истечения документа как дату выдачи плюс срок годности.

6.4. При каждом обращении к досье приложение проверяет соответствие документов дате подачи. Документ считается **проблемным**, если его дата истечения раньше даты подачи досье.

6.5. Для каждого проблемного документа приложение возвращает предупреждение с указанием даты истечения и рекомендуемого интервала, в котором документ следует получить заново: не ранее чем дата подачи минус срок годности.

6.6. Справочник типов документов заполняется сидером и содержит как минимум:

- медицинский сертификат установленной формы, срок годности по умолчанию 12 месяцев;
- заключение специалиста, без срока годности по умолчанию;
- подтверждение места жительства, срок годности по умолчанию 3 месяца;
- удостоверение личности, без срока годности по умолчанию.

6.7. Сроки годности в справочнике являются значениями по умолчанию и могут быть переопределены пользователем для конкретного документа. Приложение не утверждает, что значение по умолчанию верно для случая пользователя: правило может отличаться в зависимости от департамента и характера нарушения.

### 7. Завершение цикла

7.1. Пользователь может зафиксировать факт подачи досье. При этом передаётся фактическая дата подачи, которая не может быть в будущем. Досье переходит в состояние `DEPOSE`.

7.2. После перехода в состояние `DEPOSE` приложение вычисляет ожидаемую дату решения как фактическую дату подачи плюс срок рассмотрения процедуры, и создаёт шаг-напоминание о том, что срок ответа истекает.

7.3. Пользователь может зафиксировать полученное решение. Передаётся:

- **Результат** (обязательно). Одно из значений: `ACCORDE`, `REFUSE`, `PARTIEL`.
- **Дата решения** (обязательно). Не может быть в будущем.
- **Дата истечения новых прав** (обязательно при результате `ACCORDE` или `PARTIEL`).

Досье переходит в состояние `DECISION_RECUE`.

7.4. При результате `ACCORDE` или `PARTIEL` приложение предлагает создать следующее досье, автоматически подставляя новую дату истечения прав. Создание нового цикла выполняется только по явному подтверждению пользователя.

7.5. При результате `REFUSE` приложение информирует пользователя о существовании установленного законом срока на обжалование и о том, что порядок обжалования следует уточнить в решении и у своей MDPH. Приложение **не** рассчитывает срок обжалования и **не** формирует документы для него. Обоснование приведено в разделе «Границы ответственности».

7.6. Пользователь может перевести досье в состояние `ARCHIVE`. Архивные досье не участвуют в напоминаниях и по умолчанию скрыты из списка.

7.7. Пользователь может запросить список завершённых циклов подопечного. Для каждого цикла возвращаются: процедура, дата подачи, дата решения, результат, срок действия назначенных прав.

### 8. Напоминания на электронную почту

8.1. Приложение рассылает напоминания о приближающихся и просроченных шагах.

8.2. Запуск рассылки выполняется по расписанию средствами планировщика, один раз в сутки.

8.3. Письмо отправляется пользователю, если для любого из его активных досье выполняется хотя бы одно условие:

- существует невыполненный шаг, до плановой даты которого осталось ровно 30, 14 или 3 дня;
- существует невыполненный шаг в состоянии `EN_RETARD`, о котором не напоминали последние 7 дней;
- существует проблемный документ по п. 6.4.

8.4. Все поводы для напоминания, накопившиеся для одного пользователя за сутки, объединяются в одно письмо. Приложение не отправляет пользователю более одного письма в сутки.

8.5. Письмо содержит: название подопечного и процедуры, перечень требующих внимания шагов с датами, ссылку на досье. Медицинские сведения в письмо не включаются.

8.6. Приложение фиксирует факт отправки напоминания по каждому шагу, чтобы исключить повторные уведомления об одном и том же поводе.

8.7. Пользователь может отключить напоминания полностью либо изменить набор интервалов из п. 8.3. Настройка хранится на уровне учётной записи.

8.8. Каждое письмо содержит ссылку для отказа от рассылки, работающую без предварительной авторизации.

8.9. Ошибка отправки письма не должна прерывать обработку остальных получателей. Сбои фиксируются в журнале.

### 9. Доступность

Требования настоящего раздела обязательны и проверяются наравне с функциональными.

9.1. Все интерактивные элементы доступны с клавиатуры. Порядок обхода соответствует визуальному порядку.

9.2. Фокус клавиатуры имеет постоянно видимое обозначение с контрастом не ниже 3:1 к соседним цветам. Обозначение фокуса не отключается ни при каких условиях.

9.3. Контраст текста к фону — не ниже 4.5:1, для крупного текста и элементов интерфейса — не ниже 3:1. Требование выполняется в обеих цветовых темах.

9.4. Состояние шага передаётся не только цветом. Каждому состоянию соответствует текстовая подпись, читаемая программой экранного доступа.

9.5. Все поля форм имеют программно связанные подписи. Сообщения об ошибках связаны с полями и объявляются программой экранного доступа при появлении.

9.6. Изменения состояния, происходящие без перезагрузки страницы, объявляются через область с ролью `status` или `alert` в зависимости от важности.

9.7. Модальные окна перехватывают фокус, закрываются по клавише `Escape` и возвращают фокус на вызвавший их элемент.

9.8. Приложение остаётся работоспособным при увеличении масштаба до 200% без горизонтальной прокрутки основного содержимого.

9.9. Анимации отключаются при установленном системном предпочтении `prefers-reduced-motion`.

9.10. Интерфейс корректно работает в обеих цветовых темах, включая режим повышенной контрастности операционной системы.

9.11. Формулировки интерфейса рассчитаны на пользователя, который проходит процедуру впервые. Административные сокращения при первом употреблении сопровождаются расшифровкой.

### 10. Границы ответственности

10.1. Приложение не оказывает юридических консультаций и не заменяет социального работника, врача или адвоката.

10.2. Все расчётные даты сопровождаются указанием на то, что они являются ориентировочными, а окончательные требования следует уточнять в своей MDPH. Сроки рассмотрения различаются по департаментам.

10.3. Приложение не подаёт документы, не взаимодействует с государственными информационными системами и не имеет к ним доступа. Государственные API для рассматриваемых процедур недоступны частным приложениям.

10.4. Приложение не рассчитывает процессуальные сроки обжалования. Ошибка в таком расчёте может привести к утрате прав, а условия исчисления зависят от обстоятельств, которые приложению неизвестны.

10.5. Приложение не оценивает право пользователя на пособия и не прогнозирует решение комиссии.

10.6. Тексты справочника процедур содержат ссылки на официальные источники.

### 11. Защита персональных данных

11.1. Приложение спроектировано так, чтобы **не хранить сведения о состоянии здоровья**. Диагнозы, медицинские заключения, содержание сертификатов и характер нарушений в базе данных отсутствуют. Хранятся только: тип документа, дата выдачи, срок годности и факт наличия.

11.2. Обоснование: данные о здоровье относятся к особой категории персональных данных, а их хранение во Франции требует размещения у сертифицированного хостинг-провайдера медицинских данных. Отказ от хранения таких данных выводит приложение из-под этого требования.

11.3. Загрузка файлов документов в MVP не реализуется. При появлении такой функции файлы размещаются на стороне клиента либо в хранилище, отвечающем требованиям п. 11.2; решение принимается отдельно.

11.4. Данные размещаются на территории Европейского союза.

11.5. Пользователь может выгрузить все свои данные в машиночитаемом формате.

11.6. Пользователь может удалить учётную запись. Удаление приводит к безвозвратному уничтожению всех подопечных, досье, шагов, документов и токенов. Операция подтверждается повторным вводом пароля.

11.7. В журналах приложения не фиксируются имена подопечных, адреса электронной почты и содержимое комментариев к документам.

### 12. Источники справочных данных и поддержание актуальности

12.1. Приложение опирается на два вида сведений, различающихся по природе и по способу поддержания.

12.2. **Общенациональные правила.** Порядок обращения, состав форм и законные сроки установлены законодательством и едины для всей страны: используется единая форма обращения, охватывающая все виды помощи, отдельная форма медицинского заключения, и установленный законом срок рассмотрения. Эти сведения меняются редко, но меняются: в апреле 2026 года форма обращения была разделена на несколько версий, включая упрощённую для продления прав на тех же условиях. Сведения этого вида задаются в шаблонах процедур и сверяются с официальными публикациями.

12.3. **Фактические сроки рассмотрения по департаментам.** Различаются существенно: по последним опубликованным сведениям рассмотрение укладывается в четыре месяца в большинстве департаментов, но превышает шесть месяцев в десяти из них. Источником служит ежеквартальная публикация показателей деятельности MDPH, ведущаяся национальным агентством в целях прозрачности, с разбивкой по департаментам. Сведения этого вида задаются в справочнике департаментов.

12.4. Справочник учреждений MDPH с адресами и территориальной привязкой доступен в составе открытых данных и может загружаться программно.

12.5. Обновление справочника департаментов выполняется не реже одного раза в квартал, вслед за публикацией новых показателей. Обновление шаблонов процедур выполняется по факту изменения нормативных требований.

12.6. Каждое обновление справочника фиксирует дату сверки. При невозможности подтвердить сведения по источнику дата сверки не обновляется: приложение должно показывать пользователю действительный возраст данных, а не создавать видимость свежести.

12.7. При расхождении между сведениями разной свежести применяется более консервативное значение — то, которое побуждает пользователя начать подготовку раньше. Ошибка в сторону преждевременного начала не влечёт утраты прав, ошибка в обратную сторону может повлечь.

12.8. Приложение не заявляет о полноте и безошибочности справочных сведений. Каждое утверждение сопровождается ссылкой на источник, позволяющей пользователю проверить его самостоятельно.

## Документирование

REST API документируется в формате OpenAPI средствами, встроенными в NestJS.

В файле `specification.md` описываются: требования к окружению, порядок запуска базы данных, применения миграций и заполнения справочников, запуск приложения в режимах разработки и продакшена, запуск тестов.

Справочник процедур сопровождается указанием источников, на основании которых заданы сроки и последовательность шагов.

## Тестирование

Сценарии из раздела «Общий список сценариев» покрываются тестами.

Обязательному покрытию модульными тестами подлежит логика расчёта дат: развёртывание плана по дате истечения прав (п. 4.3), определение применимого срока рассмотрения и его приоритетов (пп. 3.9, 3.10), пересчёт при изменении даты подачи (п. 4.4), вычисление состояний шагов (п. 5.1), определение проблемных документов (п. 6.4), формирование поводов для напоминания (п. 8.3).

Тесты на расчёт дат включают граничные случаи: последний день месяца, високосный год, смещение, попадающее на прошедшую дату, дата подачи в прошлом.

Проверка валидации DTO выполняется для всех сценариев, принимающих данные от клиента.

## Безопасность

В коде приложения не должно быть зашито конфиденциальной информации: паролей, секретов, ключей. Для их передачи используются переменные окружения. Файлы с реальными значениями переменных окружения не попадают в репозиторий.

Все обращения к данным подопечных, досье, шагов и документов проверяют принадлежность запрашиваемого объекта текущему пользователю. Проверка выполняется на уровне запроса к базе данных, а не после получения объекта.

Ответы на запросы к чужим объектам не позволяют установить факт их существования.

Эндпоинты аутентификации и восстановления доступа защищены ограничением частоты запросов.
