# Research: Veille — изменение состава коммун

**PRD**: docs/prd/veille-commune-change.md (план составляется после этого
отчёта)
**Дата**: 2026-08-17

> **Снапшот на дату.** Расхождения при реализации отмечаются врезкой
> «Исправлено при реализации», как в docs/research/veille-subscription-lifecycle.md.

Фича целиком живёт внутри уже реализованного контура veille (модуль
`apps/api/src/veille/`, страницы `apps/web/src/app/veille/`,
docs/research/veille-subscription-lifecycle.md — далее «lifecycle»).
**Новых зависимостей не требуется ни одной**; новых переменных окружения тоже.

Не переисследуется (решено раньше, применяется буквально):

- токены и хеши — только `generateVeilleToken` / `hashVeilleToken`
  (`veille-token.ts`, единственная точка по `src/veille/CLAUDE.md`);
- лимит 5 писем формы в сутки и композиция письма за гейтом лимита —
  `VeilleService.sendFormMail`; письмо изменения — тоже «письмо формы»
  (PRD: лимиты те же, что в lifecycle);
- токен в query, а не в сегменте пути; статусы в теле `200` вместо
  `404`/`410`; `GET` ничего не меняет — lifecycle, «Контракт API»;
- отписка: страницы, route handler, `@ThrottleByToken`, каскад — без
  изменений, письмо изменения несёт тот же `unsubscribePath`;
- перевыпуск хешей только внутри гейта лимита («подавленное письмо не должно
  гасить ссылки уже доставленных») — lifecycle, врезка к «Токенам».

## Решения

### Хранение отложенного состава: модель `VeilleChange`, 1:1 к `Veille`

**Решение:** отдельная модель; `data-model.md` § 6 правится тем же коммитом,
что и миграция (требование PRD).

```prisma
// Неподтверждённая заявка на смену состава коммун — docs/research/veille-commune-change.md.
// На рассылку не влияет: действующий состав — только VeilleCommune.
model VeilleChange {
  id              String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  veilleId        String   @unique @db.Uuid
  veille          Veille   @relation(fields: [veilleId], references: [id], onDelete: Cascade)
  changeTokenHash String   @unique
  communeCodes    String[]
  expiresAt       DateTime @db.Timestamptz(6)
  createdAt       DateTime @default(now()) @db.Timestamptz(6)
}
```

**Почему:**

- `veilleId @unique` даёт «действует только последняя выданная ссылка» на
  уровне БД: второй заявки у подписки существовать не может, повторная форма
  переписывает единственную строку.
- `onDelete: Cascade` выполняет критерий «отписка удаляет подписку и
  неподтверждённое изменение немедленно» без единой строчки кода — тем же
  `deleteMany`, что уже есть в `unsubscribe`; RGPD-обещание hard delete
  наследуется.
- `communeCodes` — скалярный массив, а не join-таблица: коды провалидированы
  формой при отправке (та же сверка `subscribe`), строки `Commune` из
  справочника никогда не удаляются (data-model § 3), а fan-out и прочие
  читатели действующего состава по заявке не ходят — FK и индекс
  `(codeInsee)` ей не нужны. При применении `createMany` в `VeilleCommune`
  FK всё равно проверяет каждый код.

**Отброшено:** группа nullable-колонок на `Veille`
(`changeTokenHash`/`pendingCommuneCodes`/`changeExpiresAt`) — инвариант «все
три заданы вместе» ничем не держится, а «отбросить просроченное» превращается
из `deleteMany` в `updateMany` с обнулением, непохожий на обе существующие
чистки; таблица `VeilleChangeCommune` — копия структуры `VeilleCommune` ради
staging-списка, у которого нет ни одного читателя-джойна; флаг `pending` в
`VeilleCommune` — каждый читатель действующего состава обязан был бы помнить
фильтр, один забытый `where` нарушает критерий «не влияет на рассылку».

### Ветка подтверждённого адреса в `subscribe`: заявка вместо «déjà inscrit·e»

**Решение:** в `upsertSubscription` ветка `claim.kind === 'confirmed'` вместо
`sendAlreadySubscribedMail` вызывает новый метод: `upsert` заявки
(состав + `expiresAt = now + VEILLE_CHANGE_TTL_DAYS`) — **вне** гейта лимита,
затем письмо через `sendFormMail`, внутри гейта которого перевыпускаются
`changeTokenHash` (по `veilleId`) и `unsubscribeTokenHash` (по `email`,
условие `confirmedAt: { not: null }`); `count === 0` любого из двух
`updateMany` → `null` (строка исчезла в гонке — письмо не уходит и попытку
лимита не тратит, готовый механизм `sendFormMail`). `claimUnconfirmed` для
этого возвращает `veilleId` и в ветке `confirmed`. Файл
`veille-already-subscribed-mail.ts` со спекой и строками `fr` **удаляется**:
PRD прямо заменяет это поведение, второго сценария для письма нет.

**Почему:** это то же разделение, что уже принято в lifecycle: изменения
данных, ради которых пользователь заполнял форму, происходят всегда
(как `claimUnconfirmed` переписывает состав неподтверждённой), а ротация
хешей — только когда письмо действительно уходит. Если лимит подавил письмо,
прежняя ссылка изменения остаётся действующей — «последней выданной» по PRD
остаётся последнее доставленное письмо, и страница по ней показывает
актуальный состав заявки (см. «Риски»). Ветки `absent` и неподтверждённого
адреса не меняются.

**Отброшено:** особый случай «новый состав совпадает с действующим» (письмо
«ничего не изменилось» или тихий no-op) — вторая ветка поведения без
сценария в PRD; заявка создаётся единообразно, подтверждение применит
идентичный состав. Сохранение `veille-already-subscribed-mail.ts` «на
всякий случай» — мёртвый код.

### Срок 7 дней: своя константа `VEILLE_CHANGE_TTL_DAYS`

**Решение:** `VEILLE_CHANGE_TTL_DAYS = 7` в `enums.ts` contracts, рядом с
`VEILLE_CONFIRM_TTL_DAYS`; там же `VEILLE_CHANGE_PATH = '/veille/changement'`
и `VEILLE_CHANGE_STATUSES = ['pending', 'applied', 'invalid'] as const` (+
тип и интерфейсы ответов в `models.ts`, включая
`{ name, departementName }` коммун для страницы).
**Почему:** сроки подтверждения подписки и подтверждения изменения — два
независимых продуктовых решения владельца (оба 02.08.2026), совпадающих
числом; одна константа связала бы их так, что смена одного молча двигает
другой. Массив статусов — рантайм-значения для Swagger DTO, тот же приём,
что `VEILLE_CONFIRMATION_STATUSES`.
**Отброшено:** переиспользование `VEILLE_CONFIRM_TTL_DAYS` — ложное
объединение фактов; статус `active`-аналог с хранением применённых заявок —
PRD не требует «повторный переход показывает „применено"», а хранить
исполненные заявки ради этого — лишние данные (после применения строка
удаляется, ссылка отвечает `invalid`).

### Контракт API: `GET`/`POST /veille/changement`, зеркало confirmation

**Решение:** два эндпоинта в существующем `VeilleController`:

| Эндпоинт                         | Вход                           | Ответ                                                      |
| -------------------------------- | ------------------------------ | ---------------------------------------------------------- |
| `GET /veille/changement?token=…` | query                          | `200 { status: 'pending' \| 'invalid', communes?: [...] }` |
| `POST /veille/changement`        | `{ token }` (`VeilleTokenDto`) | `200 { status: 'applied' \| 'invalid' }`                   |

`GET`: токен голым `@Query('token')` (как у confirmation — почтовые шлюзы
дописывают параметры, `forbidNonWhitelisted` отвечал бы 400); поиск по
`changeTokenHash` с условием `expiresAt: { gte: now }`; для `pending` в ответ
идут коммуны заявки — `commune.findMany({ codeInsee: { in: communeCodes } })`
(имена — данные, не тексты UI). `POST` — `@HttpCode(HttpStatus.OK)`, без
`@ThrottleByToken` (он нужен только отписке, где между клиентом и API стоит
route handler и IP один на всех; сюда пользователь ходит из браузера сам —
глобальных 100/мин достаточно, как у confirmation).
**Почему:** просроченная и несуществующая заявка неразличимы («lien
invalide» без раскрытия причины), статус — штатный ответ, не исключение;
`GET` ничего не меняет (сканеры и превью) — всё это дословно принятые
решения lifecycle, повод отступать не появился.
**Отброшено:** отдельный контроллер/модуль — фича живёт в тех же сущностях и
сервисе; `PATCH /veille` с email — изменение без double opt-in запрещено
ограничениями PRD.

### Применение изменения: claim удалением заявки

**Решение:** `POST` исполняется интерактивной транзакцией по образцу
`claimUnconfirmed` — ветку выбирает та же запись, что её исполняет:
`findUnique` по хешу → `tx.veilleChange.deleteMany({ where: { id,
expiresAt: { gte: now } } })`; `count === 0` → `invalid` (заявка исчезла,
просрочена или уже применена — причины наружу неразличимы); `count === 1` →
в той же транзакции `veilleCommune.deleteMany({ veilleId })` +
`createMany(communeCodes)` → `applied`. Состав при применении **не
перепроверяется** по `effectiveTo`: он был сверен со справочником при
отправке формы, строки `Commune` не удаляются, FK держит целостность.
**Почему:** удаление заявки и есть атомарный захват — повторный `POST`,
гонка двух вкладок и гонка с часовой чисткой разрешаются самим
`deleteMany` без `P2025`; применение «целиком» (критерий PRD «коммуны,
которых нет в новом составе, перестают отслеживаться») — та же пара
`deleteMany`+`createMany`, что уже переписывает состав в `claimUnconfirmed`.
**Отброшено:** повторная сверка `effectiveTo: null` при применении — отказ
«lien invalide» из-за коммуны, ставшей исторической за неделю ожидания,
наказывает пользователя за административную реформу; подписка на
исторический код — штатное состояние модели (`successorCodeInsee` резолвится
на чтении, data-model § 3).

### Чистка просроченных заявок: третья ветка `cleanupExpired`

**Решение:** в существующий часовой `@Cron` добавляется третий guarded-вызов:
`veilleChange.deleteMany({ where: { expiresAt: { lt: new Date() } } })`.
Индекс под неё **не нужен**, и это осознанное отличие от
`veille_cleanup_indexes`: та миграция спасала `deleteMany` от seq scan по
таблице, монотонно растущей подтверждёнными строками, а `VeilleChange`
содержит только живые заявки (строки уходят при применении, каскадом отписки
и этой чисткой) — seq scan по ней и есть правильный план. Подписка при
чистке не трогается — критерий PRD «подписка продолжает действовать в
прежнем составе» выполняется тем, что чистка вообще не знает о `Veille`.
**Почему:** обещание «изменение отброшено за 7 дней» — как в lifecycle,
данных в базе нет, а не «ссылка не работает»; проверка `expiresAt` в самих
запросах (`GET`/`POST` выше) закрывает зазор между прогонами.
**Отброшено:** отдельный `@Cron` — второе имя того же тика (докблок
`cleanupExpired`).

### Письмо изменения

**Решение:** `veille-change-mail.ts` по образцу `confirmationMailFor`, строки —
ветка `fr.mail.veille.change`: параграф-объяснение (запрошено изменение
состава; если не запрашивали — ссылка отписки в подвале), блок `list` с
**новым** составом (`communeLabel` из `veille-confirmation-mail.ts` —
общий, второго формата не заводить), блок `link` на
`${VEILLE_CHANGE_PATH}?token=…`, параграф о сроке из
`VEILLE_CHANGE_TTL_DAYS`. `reason` — та же `fr.mail.veille.reason` (повод
общий — адрес оставлен в форме veille), `unsubscribePath` — общий
`unsubscribePathFor`.
**Почему:** блочная модель гарантирует совпадение ссылок text/HTML; подвал
каркаса уже даёт отписку в один клик — сценарий «владелец адреса не
запрашивал изменение» закрыт существующими страницами отписки без нового
кода. Темы и тела фикстур — не короче 10 символов (Scaleway TEM,
docs/research/emails.md).

### Страница web: `/veille/changement`

**Решение:** `page.tsx` + клиентский компонент по образцу
`veille-confirmation.tsx`: `useSearchParams` под `<Suspense>` (иначе падает
пререндер `next build`); `useQuery` на `GET` (ключ — фабрика
`queryKeys.veilleChange(token)` в `src/lib/api/keys.ts`, по компонентам не
заводить); `pending` → заголовок, список нового состава коммун (`<ul>`,
данные из ответа `GET`) и кнопка «Confirmer la modification» →
`useMutation` на `POST`; `applied` → терминальный результат через
`AnnouncedResult` (объявление скринридеру); `invalid` → «lien invalide».
Терминальный успех мутации перекрывает фоновые рефетчи статуса — тот же
приём и той же причиной, что в `veille-confirmation.tsx` (после применения
заявки нет, рефетч `GET` ответит `invalid`, и без этого приоритета успех
на глазах превращался бы в «lien invalide»). Сетевые сбои — `RequestError`,
не «lien invalide». В `tests/pages.ts` страница попадает с
`?token=invalide`; ветка `pending`/`applied` — отдельным Playwright-тестом
со своей подпиской и заявкой, axe и клавиатура — общими сьютами.
**Почему:** все паттерны (Suspense, ключи, live-region, приоритет
терминального статуса) уже приняты и проверены на странице confirmation;
нового UI-примитива не требуется — список и кнопка.
**Отброшено:** переиспользование компонента confirmation с пропами — у
страниц разные данные (`communes`), разные словари и разные мутации, общий
компонент склеил бы два экрана условиями ради экономии одной кнопки.

## Ограничения и риски

- **Подавленное лимитом письмо не ротирует токены** — заявка при этом уже
  переписана, и прежняя (последняя доставленная) ссылка ведёт на страницу с
  **новым** составом заявки. Это не дыра: страница показывает ровно то, что
  будет применено, а кнопка применяет показанное; принцип «работает последнее
  доставленное письмо» принят в lifecycle.
- **Тайминг ответа формы не выравнивается** — унаследованный принятый риск
  lifecycle; ветка изменения его не ухудшает (те же запись + письмо).
- **Критерий «не влияет на рассылку» проверяется на данных**: fan-out ещё не
  реализован (PRD монитора JO), тест фиксирует, что `VeilleCommune` не
  меняется, пока заявка висит, и меняется целиком после применения.
- **Коммуна, ставшая исторической за время жизни заявки, применяется как
  есть** — осознанно (см. «Применение изменения»); подписчик получает
  уведомления через резолв преемника, как любой подписчик влившейся коммуны.
- **Email в логи не попадает по построению** (исключений с адресом нет,
  новые пути переиспользуют существующие механизмы), но тесты обязаны
  проверять все аргументы `Logger` — образец в docs/research/emails.md.
- **`prisma migrate` для `String[]`** — скалярный массив это `text[]`,
  первый в схеме; Prisma 7 выражает его штатно, ручной SQL не нужен.
