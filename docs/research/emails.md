## Решения

### Почтовый провайдер

**Решение:** Scaleway Transactional Email (TEM), регион `fr-par`, HTTP API
`v1alpha1` (выбор провайдера — решение владельца 03.08.2026).
**Почему:**

- Обработка данных в ЕС подтверждена самим провайдером документально, а не
  выведена из юрисдикции компании: «For our Transactional Email service, no
  personal data is transferred outside the EU. All data is hosted and processed
  entirely within the European Union»
  ([FAQ TEM](https://www.scaleway.com/en/docs/transactional-email/faq/),
  проверено 03.08.2026). Это ровно тот источник, на который сошлётся запись
  фазы 2 в `docs/decisions.md` (ограничение PRD «обработчик почты — в ЕС»).
- **Трекинга у TEM нет вообще** — ни open, ни click
  ([Anymail, раздел Scaleway](https://anymail.dev/en/stable/esps/scaleway/):
  «Anymail's `track_clicks` and `track_opens` options are unsupported»; у
  Scaleway click tracking висит в
  [feature requests](https://feature-request.scaleway.com/posts/528/click-tracking-on-transactional-emails)).
  Требование плана «переписывание ссылок провайдером выключено» выполняется
  структурно, а не настройкой: ссылку некому переписать, значит множества
  ссылок в text- и HTML-версиях не могут разойтись после отправки, а адреса
  получателей не попадают в чужую аналитику. Настройку в личном кабинете можно
  случайно включить; отсутствующую функцию — нельзя.
- Аутентификация — один заголовок `X-Auth-Token`, тело — плоский JSON: нативный
  `fetch` Node 24, ноль зависимостей, тот же образец, что `GeoApiClient`.
- Для верификации домена Scaleway требует **SPF, DKIM, DMARC и MX**
  ([how-to](https://www.scaleway.com/en/docs/transactional-email/how-to/configure-domain-with-transactional-email/)) —
  то есть DMARC, без которого письмо обычно и уезжает в спам у Outlook, не
  забывается: он условие начала отправки, а не необязательный совет из
  предусловий фазы 3.

**Отброшено:**

- **Brevo** — ЕС (Франция и Германия) и щедрый бесплатный тариф, но выключить
  переписывание ссылок на транзакционных письмах нельзя: возможность есть только
  у кампаний
  ([community](https://community.brevo.com/t/no-way-to-disable-by-option-tracking-in-transactional-e-mail/201)).
  Прямое нарушение требования фазы 2.
- **Mailjet** (Send API v3.1) — ЕС, и трекинг выключается по каждому письму
  (`TrackOpens`/`TrackClicks: "disabled"`), но у него есть закрытый список
  заголовков, которые нельзя задать через `Headers`, и вокруг `List-Unsubscribe`
  тянутся жалобы на блокировку
  ([mailjet-gem#135](https://github.com/mailjet/mailjet-gem/issues/135)).
  Обязательный заголовок — не то место, где проверку хочется отложить до живого
  аккаунта.
- **AWS SES** (eu-west-3) — либо SDK-зависимость, либо подпись SigV4 руками;
  плюс выход из песочницы отдельной заявкой. Дороже во внедрении при том же
  результате.
- **SMTP + nodemailer** (в том числе SMTP-релей самого Scaleway) — новая
  зависимость ради того, что HTTP API делает без неё; MIME собирает провайдер, а
  не мы. Переменные `SMTP_*` в `.env.example` остались от скелета и в фазе 2
  удаляются.

**Как применять:**

```
POST https://api.scaleway.com/transactional-email/v1alpha1/regions/fr-par/emails
X-Auth-Token: <SCW_SECRET_KEY>
Content-Type: application/json

{
  "from": { "name": "Mon Sinistre", "email": "no-reply@<домен>" },
  "to": [{ "email": "<адрес получателя>" }],
  "subject": "…",
  "text": "…",
  "html": "…",
  "project_id": "<SCW_PROJECT_ID>",
  "additional_headers": [
    { "key": "List-Unsubscribe", "value": "<https://…>" },
    { "key": "List-Unsubscribe-Post", "value": "List-Unsubscribe=One-Click" }
  ]
}
```

`additional_headers` — именно массив объектов `{ key, value }`, не словарь
([send-emails-with-api](https://www.scaleway.com/en/docs/transactional-email/api-cli/send-emails-with-api/),
проверено 03.08.2026). Ключ API нужен с правом
`TransactionalEmailEmailApiCreate`, `project_id` обязателен в теле.

Ограничения провайдера, которые обязаны знать код и фикстуры тестов
(проверено 03.08.2026):

- **тема, текстовая и HTML-версии — не короче 10 символов**, иначе письмо
  отклоняется. Фикстуры тестов не должны использовать `"x"` и `"тема"`;
- каждый получатель тарифицируется как отдельное письмо; по умолчанию не больше
  10 получателей на письмо (наш каркас шлёт одному — рассылка всегда по одному
  письму на адрес, это же требование RGPD: подписчики не видят друг друга);
- квота нового аккаунта — 10 000 писем в месяц, почасовых лимитов нет;
- регион только `fr-par` (есть ещё `nl-ams`, тоже ЕС) — URL с регионом хранить
  одной константой рядом с клиентом.

### Обращение к провайдеру из кода

**Решение:** класс `ScalewayMailTransport` с нативным `fetch`, переданным через
конструктор, и `AbortSignal.timeout(10_000)`.
**Почему:** повторяет уже принятый в проекте образец `GeoApiClient` — тесты
мокают HTTP подстановкой fetch-функции, без `nock`/`msw` (ноль зависимостей,
требование фазы 2 «тесты мокают HTTP без nock/msw» выполняется буквально).
Таймаут 10 с, а не 60 с как у импорта COG: письмо уходит внутри HTTP-запроса
пользователя (подтверждение veille), и минута ожидания — это минута белого
экрана у человека в стрессе.
**Отброшено:** `@nestjs/axios` + `axios` — две зависимости ради `POST` с одним
заголовком; глобальный `fetch` без инъекции — тест не смог бы подменить его
локально и пришлось бы трогать `globalThis`.
**Как применять:**

```ts
export type FetchFn = typeof globalThis.fetch;

export class ScalewayMailTransport implements MailTransport {
  private readonly logger = new Logger(ScalewayMailTransport.name);

  constructor(
    private readonly config: ScalewayMailConfig, // secretKey, projectId, url
    private readonly fetchFn: FetchFn = globalThis.fetch,
  ) {}

  async send(message: MailMessage): Promise<void> {
    let response: Response;
    try {
      response = await this.fetchFn(this.config.url, {
        method: 'POST',
        headers: {
          'X-Auth-Token': this.config.secretKey,
          'Content-Type': 'application/json',
        },
        body: JSON.stringify(toScalewayPayload(message, this.config.projectId)),
        signal: AbortSignal.timeout(SCALEWAY_TEM_TIMEOUT_MS),
      });
    } catch (cause) {
      // Таймаут и сетевой отказ: причина без тела письма и без адреса.
      throw new MailDeliveryError('Scaleway TEM request failed', { cause });
    }
    if (!response.ok) {
      throw new MailDeliveryError(`Scaleway TEM responded ${response.status}`);
    }
  }
}
```

**Исправлено при реализации:** образец выше отступает от того, что написано в
самом отчёте и в правилах проекта, — реализация следует правилам
(`docs/decisions.md`, 03.08.2026, запись о клиенте Scaleway TEM): поля `logger` в
классе нет (отказ логирует `MailService`, единственный, кто вычищает адрес), URL
не поле конфигурации, а константа с регионом (в конфигурации только `secretKey` и
`projectId`), и успешный ответ не принимается по одному статусу — тело обязано
быть JSON-объектом, а массив `emails`, если он в ответе есть, — непустым.

Отказ — **своё исключение `MailDeliveryError`**, не `HttpException`: почта не
знает, чем обернётся её ошибка для HTTP-ответа, и решает это вызывающая фича.
В сообщение исключения попадают только статус и повод, никогда — адрес и тело:
текст исключения доезжает до логов и до Sentry, если он появится. Ответ
провайдера в лог не выводить целиком — он содержит адрес получателя в поле
`to`.

### Механизм локализации `apps/api`

**Решение:** типизированный словарь на TypeScript — `src/i18n/fr.ts`, объект
`as const`, параметры подставляются функциями-полями; никакой библиотеки.
**Почему:** язык ровно один и второй в скоупе не появится («Языки, кроме
французского» — вне скоупа PRD), а значит вся ценность i18n-библиотеки
(резолвинг локали по заголовку, фолбэки, множественные числа по CLDR) не нужна.
Взамен TypeScript даёт то, чего JSON-словари не дают: пропущенный ключ и забытый
параметр — ошибка компиляции, а не пустая строка во французском письме. Правило
PRD «в contracts текстов нет» соблюдается тем, что словарь лежит в `apps/api`.
**Отброшено:** `nestjs-i18n` — новая зависимость, JSON без типов, и request-scoped
контекст, который каркасу писем не нужен (письмо собирает cron-задача, у которой
нет HTTP-запроса); свой резолвер поверх JSON-файлов — теряет типизацию, ничего не
добавляя.
**Как применять:**

```ts
// src/i18n/fr.ts — единственный файл пользовательских строк API.
export const fr = {
  mail: {
    senderName: 'Mon Sinistre',
    footer: {
      // «arrêté» и «CatNat» объясняются простыми словами при первом
      // употреблении — требование PRD, раздел «Ограничения».
      why: (reason: string) => `Vous recevez ce message parce que ${reason}.`,
      unsubscribe: 'Ne plus recevoir de messages',
      signature: 'Mon Sinistre — suivi des sinistres catastrophe naturelle',
    },
  },
} as const;
```

Импортируется напрямую (`import { fr } from 'src/i18n/fr'`) — состояния нет,
провайдер Nest не нужен. Строки конкретных писем добавляют фичи-владельцы в свои
ветки этого же объекта (`fr.mail.veille…`), каркас владеет только `fr.mail.footer`
и `fr.mail.senderName`. Второго файла с французскими строками в `apps/api`
заводить нельзя: разъедутся.

### Шаблонизация text + HTML

**Решение:** одна блочная модель тела письма, два рендерера (`renderText`,
`renderHtml`) из неё; шаблоны — обычные шаблонные строки TypeScript.
**Почему:** требование «множество ссылок в текстовой версии совпадает с
множеством ссылок в HTML» держится не тестом, а конструкцией: ссылка описана
один раз в блоке, оба рендерера обязаны её вывести, и разойтись им негде.
Два независимых шаблона (как в большинстве примеров) делают совпадение вопросом
дисциплины — текстовую версию правят реже, и тест ловит расхождение уже после
того, как его допустили. Ноль зависимостей.
**Отброшено:** `handlebars`/`eta`/`pug` — зависимость плюс runtime-ошибки вместо
ошибок компиляции; `mjml` — тяжёлая сборка ради адаптивной вёрстки, которой у
одноколоночного письма нет; готовить HTML и текст двумя файлами — см. выше.
**Как применять:**

```ts
export type MailBlock =
  | { kind: 'paragraph'; text: string }
  | { kind: 'link'; text: string; url: string }
  | { kind: 'list'; items: string[] };

// Текст: «Confirmer votre inscription : https://…» — полный URL, без разметки.
// HTML: <a href="https://…">Confirmer votre inscription</a>, текст экранируется.
```

**Исправлено при реализации:** блок ссылки несёт **путь**, а не готовый URL —
`{ kind: 'link'; text: string; path: string }`. С полем `url` фича могла бы
собрать адрес сама, и требование «второй склейки базы не заводить» держалось бы
только на дисциплине. Абсолютный адрес собирает каркас, принимая путь, только
если разобранный адрес остался на origin базы (`docs/decisions.md`, 03.08.2026 —
две записи: о блочной модели и о проверке по origin). Внешних ссылок в письмах
пока нет; когда понадобятся — это отдельный вид блока, а не свободный `url`.

Правила рендереров:

- **текстовая версия** — только видимый текст и полные URL; никаких `<`, `>`,
  `&nbsp;`, `&amp;`. Блоки разделяются пустой строкой, подвал — строкой `--`;
- **HTML-версия** — одна колонка внутри `<table role="presentation">`
  (Outlook на движке Word игнорирует `max-width` у `div`, таблица — единственная
  надёжная раскладка), инлайн-стили, никаких внешних картинок, шрифтов и
  `<style>`-блоков: они режутся почтовыми клиентами и ломают тёмную тему;
- **весь пользовательский текст экранируется** в HTML-рендерере (`&`, `<`, `>`,
  `"`), URL — через `encodeURI` на этапе сборки ссылки. В письме окажется
  название коммуны и другие внешние данные;
- **доступность** (WCAG AA — жёсткое ограничение проекта, письмо тоже
  интерфейс): `<html lang="fr">`, размер основного текста не меньше 16 px,
  контраст текста и ссылок не ниже 4.5:1, ссылки подчёркнуты и названы по
  действию («Confirmer votre inscription», не «cliquez ici») — иначе screen
  reader читает список из пяти одинаковых «cliquez ici»;
- ширина колонки 600 px, `padding` не меньше 24 px: письмо читают с телефона на
  улице после катастрофы.

Заголовки `List-Unsubscribe: <https://…>` (угловые скобки обязательны, RFC 2369)
и `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) каркас
проставляет из того же посчитанного URL — см. риски ниже про POST.

### Локальный транспорт (фаза 1)

**Решение:** `FileMailTransport` — пара файлов `<время>-<тема>.txt` и `.html` в
каталоге `MAIL_OUTBOX_DIR` (по умолчанию `apps/api/.mail-outbox`), функция
записи передаётся через конструктор.

**Исправлено при реализации:** имя файла — `<время>-<номер>-<тема>`. Тема письма
в рассылке одна на всех получателей, а отметка времени имеет разрешение в
миллисекунду: два письма одной рассылки попали бы в одно имя, и второе молча
затёрло бы первое (`docs/decisions.md`, 03.08.2026).
**Почему:** разработчик открывает `.html` в браузере и кликает ссылки, читает
`.txt` — это и есть текстовая версия, которую нужно глазами сверить; тест
подставляет вместо `fs.writeFile` функцию-накопитель и читает тот же «канал», не
трогая диск. Ноль зависимостей, ноль новых сервисов в docker-compose — фаза 1
остаётся автономной для Ralph Loop.
**Отброшено:** MailHog/Mailpit — новый контейнер, который цикл не поднимет
(`npm run db:up` стартует только `db`); `nodemailer` со `streamTransport` —
зависимость ради того же результата; dev-эндпоинт `GET /dev/mail` с письмами в
памяти — лишняя поверхность в API, которую в проде придётся отдельно закрывать,
и письма теряются при рестарте.
**Как применять:**

- `.txt` начинается с шапки `From/To/Subject/List-Unsubscribe`, затем текстовая
  версия — так у разработчика в одном файле и заголовки, и тело;
- в `Logger` уходит только тема и имя файла, **без адреса получателя** — иначе
  тест «email не встречается в логах» упадёт на локальном транспорте, и упадёт
  справедливо: это тот же лог приложения;
- каталог добавить в корневой `.gitignore` тем же коммитом: в файлах лежат
  реальные адреса, пусть и тестовые;
- `fs.mkdir(dir, { recursive: true })` перед первой записью; имя файла — из темы
  через транслитерацию в `[a-z0-9-]`, длина не больше 60 символов (тема
  французская, в ней есть пробелы и диакритика).

### Выбор транспорта и переменные окружения (фаза 2)

**Решение:** переменная `MAIL_TRANSPORT` (`file` | `scaleway`), читается **один
раз** в `useFactory` провайдера токена `MAIL_TRANSPORT`; переменные Scaleway
обязательны только при `scaleway` (`@ValidateIf`).
**Почему:** `MailService` не должен знать про окружение — он получает транспорт
через DI, и тесты обеих фаз подставляют свой, не трогая `process.env`
(требование плана). Значение по умолчанию — `file`: локальная разработка не
требует ни ключа, ни аккаунта.
**Как применять:**

```ts
// mail.module.ts
{
  provide: MAIL_TRANSPORT,
  inject: [ConfigService],
  useFactory: (config: ConfigService): MailTransport =>
    config.get<string>('MAIL_TRANSPORT') === 'scaleway'
      ? new ScalewayMailTransport(readScalewayConfig(config))
      : new FileMailTransport(config.get<string>('MAIL_OUTBOX_DIR') ?? '.mail-outbox'),
}
```

**Исправлено при реализации:** `?? '.mail-outbox'` в фабрике нет — значение
передаётся как есть, а умолчание остаётся в `FileMailTransport`. Второй литерал
каталога разошёлся бы с первым молча, а от адресов в файлах outbox защищает
ровно одна строка `.gitignore` (`docs/decisions.md`, 03.08.2026, запись об
умолчании outbox). Сравнение с `'scaleway'` в реализации — с константой
`SENDING_TRANSPORT` из `src/mail/mail-transport-name.ts`: тот же литерал
включает условную валидацию ключей, и разъехаться выбору с валидацией негде.
Имена транспортов объявлены там же, а не в схеме окружения: схема их
импортирует и проверяет значение, которое объявляет модуль почты.

Итоговый блок `.env.example` (фаза 2 заменяет им `SMTP_*`):

```
# --- почта ---
MAIL_TRANSPORT=file          # file (по умолчанию) | scaleway
MAIL_FROM=no-reply@mon-sinistre.fr
MAIL_FROM_NAME=Mon Sinistre
MAIL_SENDER_DOMAIN=mon-sinistre.fr
MAIL_OUTBOX_DIR=.mail-outbox # только для MAIL_TRANSPORT=file
SCW_SECRET_KEY=              # обязательны при MAIL_TRANSPORT=scaleway
SCW_PROJECT_ID=
```

`MAIL_FROM=no-reply@…` — осознанный выбор на MVP (владелец, 03.08.2026), а не
умолчание: ящика на домене нет, MX — заглушка, и ответ пользователя всё равно
пропал бы. Честнее сказать это адресом, чем дать человеку в стрессе написать
письмо, которое никто не прочтёт. Когда ящик появится, значение меняется на
`contact@mon-sinistre.fr` правкой одной строки `.env` — кода это не касается,
ради чего фаза 3 и требует брать адрес отправителя из конфигурации. Ящик за
адресом не нужен ни для отправки, ни для доставляемости: подлинность письма
подтверждают DKIM-подпись и SPF, а отбитые письма уходят на конверт-отправителя
Scaleway, где нашего домена нет.

Правила валидации в `src/config/env.validation.ts`:

- `MAIL_TRANSPORT` — `@IsOptional() @IsIn(['file', 'scaleway'])`;
- `SCW_SECRET_KEY`, `SCW_PROJECT_ID`, `MAIL_FROM`, `MAIL_SENDER_DOMAIN` —
  `@ValidateIf((env) => env.MAIL_TRANSPORT === 'scaleway')` + `@IsNotEmpty()`;
  **исправлено при реализации:** `MAIL_FROM` обязателен безусловно и проверяется
  как адрес — без отправителя письмо не собирается ни одним транспортом, включая
  записанное в файл локальным (`docs/decisions.md`, 03.08.2026). Условной
  валидации подлежат ключи провайдера, не адрес. Переменной `MAIL_FROM_NAME` из
  блока `.env.example` выше нет: имя отправителя — часть текста письма, оно живёт
  строкой локализации `fr.mail.senderName`;
- **страховка от молчаливого прода**: при `NODE_ENV=production` и
  `MAIL_TRANSPORT=file` приложение не стартует. Иначе продакшен спокойно
  поднимется и будет писать письма в файлы — а пострадавший не получит
  уведомления об arrêté и узнает об этом, пропустив срок. Для этого в схему
  добавляется `NODE_ENV` (`@IsOptional() @IsIn(['development','test','production'])`);
- `FRONTEND_URL` — `@IsNotEmpty() @IsUrl({ require_tld: false, require_protocol: true, protocols: ['http','https'] })`.
  `require_tld: false` обязателен: без него `http://localhost:3000` из
  `.env.example` не пройдёт валидацию и сломает локальный запуск;
- секреты в текст ошибки не попадают — `validateEnv` уже собирает только имена
  свойств и constraint-сообщения, менять его не нужно;
- `MAIL_FROM` внутри `MAIL_SENDER_DOMAIN` (фаза 3) — собственный декоратор через
  `registerDecorator`, сравнивающий часть после `@` с соседним свойством
  (регистронезависимо, точное равенство домена — поддомен не считается). Тест —
  на `validateEnv`, без поднятия приложения.

Абсолютный адрес каркас собирает через `new URL(path, frontendUrl).toString()`;
путь всегда начинается с `/`. Ограничение: если `FRONTEND_URL` когда-нибудь
получит путевой префикс (`https://example.com/app`), `new URL` его отбросит —
на этот случай в проекте один вызов, и чинить его придётся в одном месте.

**Исправлено при реализации:** проверка «путь начинается с `/`» недостаточна —
для `http(s)` парсер URL считает обратную косую слэшем и вырезает управляющие
символы, поэтому `/\чужой.хост` выглядит путём от корня, а ведёт на чужой сайт;
эта же ссылка уходит в `List-Unsubscribe`, куда почтовый клиент шлёт POST без
участия человека. Каркас сверяет `origin` разобранного адреса с origin базы, а
`FRONTEND_URL` с путевым префиксом приложение отвергает на старте
(`docs/decisions.md`, 03.08.2026).

## Ограничения и риски

- **Домен отправителя — `mon-sinistre.fr`**, зарегистрирован и верифицирован у
  Scaleway TEM 03.08.2026 (регистратор и DNS-зона там же, записи проставлены
  автонастройкой и подтверждены: SPF `v=spf1 include:_spf.tem.scaleway.com -all`,
  DKIM RSA-2048 с селектором по Project ID, `_dmarc` = `v=DMARC1; p=none`, MX —
  заглушка `blackhole.tem.scaleway.com.`). Это значение `MAIL_SENDER_DOMAIN`
  фазы 2 и та самая политика DMARC, которую фаза 3 переносит в
  `docs/decisions.md`. Автонастройку не отключать: ею же обновляется DKIM при
  ротации ключа.
- **Ответы на письма сейчас исчезают**: MX — blackhole, почтового ящика на
  домене нет. Когда ящик появится, его SPF-`include` дописывается **в
  существующую** TXT-запись; вторая запись SPF на домене даёт `permerror`, и
  аутентификацию перестают проходить все письма, включая наши.
- **DMARC ужесточать после первого потока писем**: `p=none` стоит осознанно,
  переход к `p=quarantine` — когда фаза 3 подтвердит, что весь легитимный поток
  проходит SPF и DKIM. `rua=` требует ящика на своём домене (внешний адрес
  вроде gmail без разрешающей записи на принимающей стороне не работает).
- **Аккаунт Scaleway требует карты и подтверждения личности**, а повышение квот
  проходит через поддержку. Квота нового аккаунта — 10 000 писем в месяц.
- **`List-Unsubscribe-Post` обязывает фичу-владельца принимать POST.** RFC 8058
  требует, чтобы почтовый клиент мог отправить на тот же URL `POST` с телом
  `List-Unsubscribe=One-Click` и отписка произошла без промежуточных экранов.
  Это **не противоречит** решению 03.08.2026 «переход по ссылке не меняет
  состояние»: `GET` открывает страницу с кнопкой, `POST` выполняет действие, а
  сканеры и превью ходят только `GET`. Но страница отписки veille обязана
  принимать `POST` без cookie, без сессии и без CSRF-токена (единственный
  credential — токен в URL), иначе штатная кнопка отписки в Gmail даст ошибку.
  Записать это требование в PRD/план veille, когда до него дойдёт очередь: в
  каркасе писем его выполнить негде.
- **Пропуск `List-Unsubscribe` через `additional_headers` документально не
  подтверждён.** Scaleway показывает в примере только `Reply-To`, списка
  запрещённых заголовков не публикует. Проверяется ручной проверкой фазы 3
  («почтовый клиент показывает штатную кнопку отписки») — она уже в
  предусловиях. Если заголовок не проходит, ссылка в подвале остаётся, а
  доставляемость немного теряет; смена провайдера из-за этого не нужна.
- **DMARC.** Начинать с `v=DMARC1; p=none; rua=mailto:…` — политика без
  отклонения, но с отчётами; ужесточать до `p=quarantine` после того, как
  отчёты покажут, что весь легитимный поток проходит SPF и DKIM. Ставить
  `p=reject` сразу опасно: любая ошибка в DNS превращается в молчаливую потерю
  всех писем продукта. Точные значения записей SPF/DKIM выдаёт консоль Scaleway
  при добавлении домена — брать их оттуда, не из статей.
- **Бесплатный тариф — 300 писем в месяц**, дальше 0,25 €/1000
  ([FAQ](https://www.scaleway.com/en/docs/transactional-email/faq/), проверено
  03.08.2026). Для veille на несколько десятков подписчиков это несколько евро в
  год, но при первом же массовом arrêté (каждый получатель — отдельное письмо)
  порог проходится за один прогон монитора. Следить за счётом, а не считать
  отправку бесплатной.
- **Версия API `v1alpha1`.** Сервис в проде и стабилен (его поддерживают
  сторонние библиотеки), но литерал версии живёт в URL — держать URL одной
  экспортируемой константой, чтобы смена версии была правкой одной строки.
- **Bounce и жалобы на спам вне скоупа** (решение владельца 02.08.2026), но
  провайдер следит за их долей сам и может ограничить отправку. Пока потока
  писем нет — риск теоретический; вернуться к нему вместе с очередью отправки в
  фиче монитора JO.
- **Очереди и повторных попыток нет**: отказ провайдера — исключение
  вызывающему коду, и письмо теряется. Для подтверждения veille это приемлемо
  (пользователь повторит подписку), для уведомления об arrêté — нет; очередь
  появится в фиче монитора JO, где лаг ≤ 24 ч требует ТЗ § 6.
- **Лимит «не больше одного письма в день» владельца не имеет** (раздел плана
  «Вне скоупа»). Единая точка отправки из фазы 1 — место, куда он встанет, когда
  PRD veille его опишет; закладывать сейчас нечего, но и потерять нельзя.
- **Тесты логов** должны проверять все аргументы вызова `Logger`, а не только
  первый: адрес может утечь вторым параметром (контекст) или внутри объекта
  ошибки. Перехват — `jest.spyOn(Logger.prototype, 'error')` и т. д.; в проверку
  включать `JSON.stringify` всех аргументов.
