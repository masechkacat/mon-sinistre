# Research: Справочник Commune

**План**: docs/plan/commune-referential.md
**Дата**: 2026-08-02

Подключение Prisma 7 здесь не переисследуется: процесс уже зафиксирован в
`apps/api/CLAUDE.md` («Текущее состояние») и `docs/decisions.md` (сборка
connection string из `DB_*`, без `DATABASE_URL`) — фаза 1 следует ему буквально.

## Решения

### Интеграционные тесты с реальным Postgres

**Решение:** отдельная тестовая база на уже поднимаемом docker-compose Postgres
(`${DB_NAME}_test` на том же инстансе) + отдельный jest-конфиг.
**Почему:** ноль новых зависимостей (`pg` уже в dependencies — им же создаётся
база в globalSetup); Postgres и так обязателен для локальной разработки
(`npm run db:up`); старт тестов мгновенный, без цикла «скачать образ → поднять
контейнер» на каждый прогон. Версия Postgres автоматически совпадает с
docker-compose (18), никакой рассинхронизации с прод-окружением.
**Отброшено:** testcontainers (`@testcontainers/postgresql`) — две новые
зависимости, секунды на старт контейнера при каждом прогоне, и главное — ничего
не добавляет к изоляции, пока тестовая база и так своя и truncate-ится между
тестами. Вернуться к нему, если появится CI без сервисного Postgres.
**Как применять:**

- Интеграционные спеки — `*.int-spec.ts` рядом с кодом в `src/`. Юнит-конфиг в
  `package.json` их не видит (его `testRegex` — `.*\.spec\.ts$`, а суффикс
  `-spec.ts` под него не подпадает), поэтому pre-commit хук и корневой
  `npm test` остаются быстрыми и без Docker-требования.
- Отдельный конфиг `jest.int.config.js` (тот же `rootDir: 'src'`,
  `moduleNameMapper`, `transform`, что в юнит-конфиге; `testRegex:
'.*\\.int-spec\\.ts$'`, `maxWorkers: 1` — тесты делят одну базу) + скрипт
  `"test:int": "jest --config jest.int.config.js"`.
- `globalSetup`: загрузить `.env` через `process.loadEnvFile()` в `try/catch`
  (нативно в Node 24, ноль зависимостей; `dotenv` напрямую не подключать — в
  package.json его нет, резолвится лишь как транзитивная зависимость
  `@nestjs/config`; catch — на случай отсутствия `.env`, когда переменные
  приходят из окружения, например в CI); клиентом `pg` подключиться к
  служебной базе и `CREATE DATABASE "${DB_NAME}_test"` (если нет); затем
  `execSync('npx prisma migrate deploy', { env: { ...process.env, DB_NAME:
`${DB_NAME}_test` } })` — `prisma.config.ts` собирает url из `DB_*`, поэтому
  переопределение одной переменной переключает базу и для CLI, и для
  `PrismaService` в тестах.
- Между тестами — `TRUNCATE` затронутых таблиц (`beforeEach`), не пересоздание
  схемы.
- В `tsconfig.build.json` к исключениям `*.spec.ts` добавить `*.int-spec.ts`.

### HTTP-клиент для geo.api.gouv.fr

**Решение:** нативный `fetch` Node 24 (undici), без новых зависимостей; клиент —
обычный класс `GeoApiClient` с fetch-функцией, передаваемой через конструктор
(по умолчанию `globalThis.fetch`) — так тесты фазы 2 мокают HTTP без nock/msw.
**Почему:** один GET-запрос раз в импорт — не тот случай, где нужны
interceptors и Observable-обёртки; `@nestjs/axios` не установлен и тянет axios.
**Отброшено:** `@nestjs/axios` + axios — две зависимости ради одного запроса.
**Как применять:** `GET
https://geo.api.gouv.fr/communes?fields=code,nom,codeDepartement,departement&format=json`
с `AbortSignal.timeout(60_000)`. Параметр `fields=departement` кладёт в каждую
запись вложенный объект `departement: { code, nom }` — отдельный запрос к
`/departements` и join не нужны.

Проверено живым запросом 2026-08-02 (`SourceReference` для отчёта):

- ответ — **один JSON-массив без пагинации**: 34 969 записей, ~3,7 МБ;
  «потерянная порция» невозможна как класс ошибки — обрыв ответа даёт
  невалидный JSON и падение импорта, что и требуется;
- у всех записей заполнены `code`, `nom`, `codeDepartement`, `departement.nom`;
  дублей `code` нет; корсиканские коды (`2A004` — Ajaccio) на месте;
- arrondissements municipaux в выдаче отсутствуют — совпадает со скоупом PRD.

Контроль полноты в клиенте: (1) валидация каждой записи — отсутствие любого из
четырёх полей это ошибка импорта, не пропуск записи; (2) нижний порог числа
записей (константа `MIN_EXPECTED_COMMUNES = 30_000`) — защита от смены формата
API или усечённого ответа, который остался валидным JSON.

### Стратегия импорта ~35 000 строк

**Решение:** по-строчный `prisma.commune.upsert` чанками по 500
(`Promise.all` внутри чанка, чанки последовательно); счётчик обработанных =
число успешно завершившихся upsert'ов, сверка с длиной массива источника.
**Почему:** типобезопасно, тривиально считается «число обработанных записей»
для итоговой сверки из плана, легко тестируется. Скорость (десятки секунд на
локальной базе) для разового seed не аргумент.
**Отброшено:** `createMany({ skipDuplicates })` — не обновляет изменившиеся
названия, ломает идемпотентность из PRD; raw `INSERT … ON CONFLICT DO UPDATE`
батчами — быстрее, но уводит главный запрос импорта в нетипизированный SQL;
преждевременная оптимизация, вернуться при переходе к регулярной актуализации
(вместе с монитором JO).
**Как применять:** upsert по `codeInsee`; `update` задаёт `name`,
`departementCode`, `departementName`, `sourceUrl`, `sourceVerifiedAt` и **не
трогает** `effectiveTo`/`successorCodeInsee` (их заполнит будущая логика
актуализации); удаления отсутствующих кодов нет вообще. `sourceUrl` — точный URL
запроса, `sourceVerifiedAt` — дата запуска импорта (`IsoDate`).

### Архитектура seed: без Nest-контекста

**Решение:** импорт-логика — обычный класс `CommuneImportService`, принимающий
в конструктор `PrismaClient` и `GeoApiClient`; seed-скрипт `prisma/seed.ts`
инстанцирует их напрямую. В `prisma.config.ts` — `migrations: { seed: 'ts-node
prisma/seed.ts' }` (ts-node уже в devDependencies).
**Почему:** `NestFactory.createApplicationContext(AppModule)` завалился бы на
валидации окружения (`env.validation.ts` требует JWT-секреты и прочие
переменные, не нужные импорту справочника) и требует собранный contracts. Seed
должен зависеть только от `DB_*` и сети.
**Отброшено:** bootstrap Nest-контекста в seed — лишняя связность; когда
появится регулярная актуализация по расписанию, тот же класс оборачивается
Nest-провайдером через `useFactory`, ничего переписывать не придётся.
**Как применять:** первой строкой seed-скрипта — `process.loadEnvFile()` в
`try/catch`, как в `prisma.config.ts` (процесс seed запускается CLI отдельно,
наследование env из `prisma.config.ts` не гарантировано); при несовпадении
счётчика — `process.exitCode = 1` и лог
без персональных данных (тут их и нет: только числа и коды INSEE).

### Нормализация поиска (фаза 3): колонка `nameNormalized`

**Решение:** отдельная колонка `nameNormalized`, заполняемая при импорте
TS-функцией `normalizeCommuneName`; та же функция нормализует `q` в поисковом
запросе. Индекс — btree с `text_pattern_ops` (SQL руками в файле миграции,
модель данных это явно разрешает).
**Почему:** одна функция для записи и чтения — расхождение нормализации
невозможно по построению; запрос остаётся типизированным Prisma `startsWith`
(генерирует `LIKE 'q%'`); функция тестируется юнит-тестом без базы. Заодно
решается сортировка: `orderBy: { nameNormalized: 'asc' }` не зависит от
collation базы (при C-collation `É…` сортировался бы после `z`).
**Отброшено:** Postgres `unaccent` + функциональный индекс — расширение в
`postgres:18-alpine` есть (проверено 2026-08-02), но `unaccent()` не
IMMUTABLE: для индекса нужна самописная immutable-обёртка в SQL, а главный
поисковый запрос уезжает в `$queryRaw`, потому что Prisma не выражает вызов
функции в `where`. Два слоя ручного SQL против одной TS-функции. Также
отброшен Prisma `mode: 'insensitive'` — снимает только регистр, диакритику не
трогает.
**Как применять:**

```ts
const normalizeCommuneName = (s: string): string =>
  s
    .toLowerCase()
    .normalize('NFD')
    .replace(/\p{M}/gu, '') // é è ô ÿ … → базовая буква
    .replace(/œ/g, 'oe') // NFD лигатуры не разбирает: Œuilly, Cricquebœuf
    .replace(/æ/g, 'ae');
```

Дополнено при реализации: шестым шагом `.replace(/[’ʼ]/gu, "'")` — COG хранит
прямой апостроф, мобильные клавиатуры подставляют типографский, и поиск по
«L’Isle-Adam» с телефона иначе не находил бы ничего (`docs/decisions.md`,
02.08.2026). Ограничение «апостроф не удаляется» этим не отменяется.

Миграция фазы 3: `ALTER TABLE … ADD COLUMN`, backfill существующих строк тем же
правилом на SQL (`lower(translate(unaccent-эквивалент)…)`) **не писать** —
backfill выполнить перезапуском импорта после миграции (импорт идемпотентен и
заполнит колонку), в миграции колонка добавляется nullable → после reimport
ужесточить NOT NULL второй миграцией, либо сразу заполнить в той же миграции
простым SQL только для случая «база уже засеяна». Индекс:
`CREATE INDEX "Commune_nameNormalized_prefix_idx" ON "Commune"
("nameNormalized" text_pattern_ops);` — при 35 000 строк он необязателен для
скорости, но дёшев и снимает вопрос навсегда.

Исправлено при реализации: колонка объявлена `COLLATE "C"`, а индекс — обычным
btree без класса оператора (`docs/decisions.md`, 02.08.2026). Причина не в
скорости: нормализация не трогает пунктуацию, а на ней collation'ы расходятся —
glibc игнорирует дефис на первичном уровне, musl и ICU нет, и порядок выдачи
поиска зависел бы от образа Postgres. Под байтовой collation префиксный `LIKE`
обслуживается обычным btree, поэтому `text_pattern_ops` отпадает сам.

### Поисковый запрос и DTO (фаза 1)

**Решение:** `findMany` с `where: { effectiveTo: null, OR: [{ name: {
startsWith: q } }, { codeInsee: q }] }`, `orderBy: { name: 'asc' }`, `take:
COMMUNE_SEARCH_LIMIT` (фаза 3 меняет `name` на `nameNormalized` в обоих
местах). DTO: `@IsString()`, `@MinLength(2)`, trim через `@Transform` —
глобальный `ValidationPipe` с whitelist уже включён. Формата «только цифры» у
`q` нет (Корсика: `2A004`). Эндпоинт публичный: guard'ов по умолчанию в
проекте нет, глобальный throttler (100/мин) покрывает его без дополнительной
настройки — выделенный rate limit по PRD не нужен.
**Почему:** ровно то, что заказано планом, средствами уже настроенного стека.
**Как применять:** в contracts — `COMMUNE_SEARCH_LIMIT = 10` и тип результата
поиска (`codeInsee`, `name`, `departementCode`, `departementName`); текстов UI
в contracts не появляется (названия коммун — данные). `sourceVerifiedAt` в
Prisma-схеме — `DateTime @db.Date` (правило проекта: доменные даты — `date`,
не `timestamp`), в границе API конвертируется в `IsoDate` через `toIsoDate`.

## Ограничения и риски

- **Апострофы и дефисы не нормализуются**: «lhay» не найдёт «L'Haÿ-les-Roses»
  (найдёт «l'hay»). PRD требует только регистр и диакритику; расширение
  нормализации — отдельным решением, если появятся жалобы.
- В названиях коммун встречаются скобки и апострофы — это данные, валидацию
  импорта на «только буквы» не писать.
- Сверка импорта сравнивает число upsert'ов с длиной массива источника; коды,
  отсутствующие в ответе (устаревшие), в базе остаются и в сверке не участвуют
  — счётчик считать по обработанным записям, не `count()` по таблице.
- `maxWorkers: 1` в интеграционном конфиге обязателен, пока тесты делят одну
  базу; если прогон станет медленным — база-на-воркера через
  `JEST_WORKER_ID`, не testcontainers.
- Живой ответ geo.api.gouv.fr от 2026-08-02: 34 969 коммун. Порог сверки
  `MIN_EXPECTED_COMMUNES = 30_000` — константа импорта (не юридический срок,
  в `DeadlineRule` ей не место).
- Интеграционные тесты требуют поднятого `npm run db:up`; в CI понадобится
  сервисный Postgres 18 — зафиксировать при настройке CI.
