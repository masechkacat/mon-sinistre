## Решения

### Схема данных: `Veille`, `VeilleCommune`, `VeilleFormEmail`

**Решение:** три модели Prisma; `data-model.md` § 6 правится тем же коммитом,
что и миграция (это требование PRD).

```prisma
model Veille {
  id                   String    @id @default(dbgenerated("uuidv7()")) @db.Uuid
  email                String    @unique            // нормализованный
  confirmedAt          DateTime? @db.Timestamptz(6) // null = не подтверждена
  confirmTokenHash     String    @unique            // SHA-256 hex токена
  unsubscribeTokenHash String    @unique
  confirmExpiresAt     DateTime  @db.Timestamptz(6) // действует, пока confirmedAt null
  createdAt            DateTime  @default(now()) @db.Timestamptz(6)
  communes             VeilleCommune[]
}

model VeilleCommune {
  veilleId  String  @db.Uuid
  codeInsee String
  veille    Veille  @relation(fields: [veilleId], references: [id], onDelete: Cascade)
  commune   Commune @relation(fields: [codeInsee], references: [codeInsee], onDelete: Restrict)
  @@id([veilleId, codeInsee])
  @@index([codeInsee])
}

// Одна строка = одно отправленное письмо формы. Единственное, что переживает
// удаление подписки; адреса здесь нет — только необратимый хеш (см. ниже).
model VeilleFormEmail {
  id        String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  emailHash String
  sentAt    DateTime @default(now()) @db.Timestamptz(6)
  @@index([emailHash, sentAt])
}
```

**Почему:** ровно модель данных § 6 плюс два поля, которых там осознанно не
хватало (срок жизни ссылки и счётчик писем — параграф сам называет эту фичу
местом решения). `confirmExpiresAt` хранится готовым моментом, а не
вычисляется из `createdAt`: повторная форма неподтверждённым адресом
отсчитывает 7 дней заново, значит точка отсчёта — не создание строки; хранение
срока делает и проверку в запросе, и чистку одним `deleteMany` без арифметики
в двух местах. Счётчик — таблица событий, а не колонка-счётчик: скользящее окно
24 ч считается `count` по индексу `(emailHash, sentAt)`, гонок инкремента нет.
**Отброшено:** колонка `sentCount + windowStart` — окно получается ступенчатым,
а не скользящим (лимит обходится на границе окна); отдельный срок у
`unsubscribeTokenHash` — по PRD ссылка отписки бессрочна, пока существует
подписка.
**Как применять:** правки `data-model.md` § 6 тем же коммитом: добавить оба
поля и таблицу счётчика; убрать фразу «повторная форма изменяет существующую
подписку» (отменено разбиением на два PRD — изменение состава уехало в
`veille-commune-change`, у подтверждённой подписки форма состава не меняет).

### Токены подтверждения и отписки

**Решение:** `crypto.randomBytes(32).toString('base64url')` (43 символа) —
токен уходит в ссылку; в базе — только `createHash('sha256')...digest('hex')`,
поиск `findUnique` по хешу. При повторной форме неподтверждённым адресом токен
подтверждения **не перевыпускается** — продлевается только `confirmExpiresAt`
и переписывается состав коммун.
**Почему:** 256 бит энтропии делают перебор невозможным, а хеш в базе — тот же
образец, что `RefreshToken.tokenHash` (§ 5 модели данных): утечка дампа не
даёт рабочих ссылок. Сохранение токена при повторной отправке — сознательный
выбор UX: пользователь, нашедший в спаме **первое** письмо, подтвердит подписку
по нему же; PRD требует лишь заново отсчитать срок и взять состав из последней
формы, что выполняется. Соль/bcrypt не нужны: по хешу нужен точный поиск, а
вход — не пароль, а 256 случайных бит.
**Отброшено:** перевыпуск токена на каждое письмо — все прежние письма получают
мёртвые ссылки без выигрыша в безопасности (подтверждает всё равно владелец
ящика); UUID как токен — v7 несёт время и меньше энтропии; хранение токена в
открытую — дамп базы равнялся бы праву отписать и подтвердить кого угодно.

> **Исправлено при реализации (фаза 3, issue #68; расширено по ревью PR 80).**
> Это решение не рассматривало письма, уходящие по повторной форме: они
> существуют именно для адреса, который мог потерять письмо создания, поэтому
> их ссылки не могут быть косметическими. Хеши перевыпускаются тем же вызовом,
> что отправляет письмо: письмо подтверждённому адресу (с фазы 1
> `veille-commune-change` — письмо изменения состава, ротация в нём —
> в `veille-commune-change.md`) — `unsubscribeTokenHash`, повторное
> письмо подтверждения — оба хеша (в базе только хеш, отправленный при
> создании токен восстановить нельзя). Перевыпуск выполняется только когда
> дневной лимит писем пропускает отправку — подавленное или не отправленное
> письмо не должно гасить ссылки уже доставленных. Плата — ссылки более
> раннего письма той же подписки перестают совпадать с хешем в базе: работает
> последнее доставленное письмо.

### Хеш адреса для счётчика писем

**Решение:** HMAC-SHA256 по нормализованному адресу с отдельным секретом —
новая переменная окружения `VEILLE_EMAIL_HASH_SECRET` (`IsSecret()`, добавить в
`env.validation.ts` и `.env.example` одним коммитом).
**Почему:** PRD обещает «хеш адресом не является и восстановлению не подлежит».
Голый SHA-256 этого не даёт: пространство email перебираемо словарём, и хеш
остаётся псевдонимом, обратимым для любого, у кого есть дамп. HMAC с секретом,
которого в базе нет, делает подбор невозможным без компрометации окружения —
это и есть честное «необратимо» для строки, пережившей RGPD-удаление. Отдельный
секрет, а не `JWT_SECRET`: разделение ключей по назначению — ротация JWT не
должна сбрасывать антиспам-счётчик и наоборот.
**Отброшено:** SHA-256 без ключа — словарная атака (выше); bcrypt/scrypt —
соль ломает точный поиск по индексу.
**Как применять:**

```ts
const emailHash = createHmac('sha256', secret)
  .update(normalizedEmail)
  .digest('hex');
```

### Лимит 5 писем формы за 24 часа: где живёт проверка

**Решение:** в сервисе veille, перед вызовом `MailService.send()`: `count`
строк `VeilleFormEmail` с этим `emailHash` за последние 24 ч; при `>= 5` —
письмо не отправляется и строка не пишется, DB-изменения подписки выполняются,
ответ формы обычный. При отправке строка счётчика пишется **до** `send()` и
**вне** транзакции подписки: транзакция коммитится раньше письма, а счётчик
обязан пережить и неудачную отправку.
**Почему:** лимит по PRD считает только «письма формы» — уведомления об arrêté
и будущие письма изменения состава под него не подпадают, значит различать вид
письма пришлось бы `MailService`, который сейчас о фичах не знает. Проверка у
владельца письма сохраняет каркас немым к содержимому. Строка до отправки —
консервативное направление: сбой между записью и отправкой съедает попытку, а
не дарит лишнюю. Фраза `src/mail/CLAUDE.md` «там же будут лимиты частоты»
правится тем же коммитом: общий лимит («не больше одного письма в день»,
вне скоупа этого PRD) — место в `MailService`, лимит конкретной фичи — в фиче.
**Отброшено:** лимит внутри `MailService` — каркасу пришлось бы знать
классификацию писем по фичам; `@nestjs/throttler` — он считает запросы по IP,
а лимит PRD — по адресу и не сбрасывается отпиской.

Отказ throttler'у касается только лимита PRD. Per-IP лимит самого `POST /veille`
он не отменяет и заменить не может: лимит по адресу ограничивает письма **одному**
адресату, а рассылку по сотне разных адресов останавливает только счёт запросов
(`VEILLE_FORM_RATE_LIMIT`, `veille.controller.ts`, фаза 1).

### Удаление неподтверждённых за 7 дней и чистка счётчика

**Решение:** фоновая задача `@nestjs/schedule`, `@Cron(CronExpression.EVERY_HOUR)`:
`veille.deleteMany({ confirmedAt: null, confirmExpiresAt: { lt: now } })`
(каскад сносит `VeilleCommune`) и
`veilleFormEmail.deleteMany({ sentAt: { lt: now − 24 ч } })`. Дополнительно
срок проверяется **в самих запросах** подтверждения: просроченная, но ещё не
удалённая строка отвечает «lien invalide».
**Почему:** PRD оставил выбор «фоновая задача или чистка при обращении» этому
ресерчу, и критерий готовности решает его сам: «подписка отсутствует в базе —
проверяется запросом». Чистка при обращении не выполняет обещание для строки,
к которой никто не обратился, — она лежала бы вечно. `ScheduleModule` уже
подключён в `AppModule`, часовой шаг достаточен (обещание — «удалена за 7
дней», не «в ту же секунду»), а проверка срока в запросе закрывает зазор между
прогонами. Тесты зовут метод чистки напрямую, cron-расписание не ждут.
**Отброшено:** чистка при обращении — см. выше; `pg_cron` — логика уезжает из
приложения в инфраструктуру базы без выгоды на этих объёмах.

> **Исправлено при реализации (фаза 4, ревью PR 81).** Решение не назвало
> индексов, а без них оба `deleteMany` идут последовательным сканом:
> подтверждённые подписки не удаляются никогда, таблица растёт монотонно, и
> часовой тик вставал бы на пути публичного `POST /veille`. Оба индекса
> добавлены миграцией `veille_cleanup_indexes`, там же — почему один из них
> частичный.

### Контракт API: четыре эндпоинта, статусы без исключений

**Решение:** модуль `src/veille/`; все ответы — фиксированные, токен никогда не
попадает в исключения:

| Эндпоинт                           | Вход                        | Ответ                                                |
| ---------------------------------- | --------------------------- | ---------------------------------------------------- |
| `POST /veille`                     | `{ email, communeCodes[] }` | всегда `204`                                         |
| `GET /veille/confirmation?token=…` | query                       | `200 { status: 'pending' \| 'active' \| 'invalid' }` |
| `POST /veille/confirmation`        | `{ token }`                 | `200 { status: 'active' \| 'invalid' }`              |
| `POST /veille/desinscription`      | `{ token }`                 | всегда `204` (идемпотентно)                          |

**Почему:**

- `204` формы — одинаковый ответ для нового, подтверждённого,
  неподтверждённого и залимиченного адреса (анти-enumeration по PRD); пустое
  тело выбрано ещё и потому, что `apiFetch` клиента распознаёт `204` как
  успех без тела, а `202` с пустым телом уронил бы `response.json()`.
- Статус в теле `200` вместо `404`/`410` для ссылок: неизвестный или
  просроченный токен — **штатный** ответ, не исключение, и клиенту не нужна
  ветка обработки ошибки там, где ошибки нет. Причина «просрочен/не
  существует» наружу не различается — критерий PRD «lien invalide без
  раскрытия причины».
- Токен — в query, а не в сегменте пути: `AllExceptionsFilter` логирует путь
  без query-строки (и только для 5xx), поэтому даже случайный сбой на этих
  эндпоинтах не унесёт в лог рабочую ссылку отписки; `/confirmation/:token`
  такой гарантии не даёт.
- `GET` подтверждения ничего не меняет (критерий PRD: превью почтовика не
  должно активировать подписку) — страница по нему решает, показывать кнопку
  (`pending`), «подписка активна» (`active`) или «lien invalide».
- Отписка: `deleteMany({ unsubscribeTokenHash })` и `204` независимо от числа
  удалённых строк — повторное нажатие и нажатие по уже удалённой подписке
  неотличимы и безошибочны (критерий PRD), заодно нечего зондировать.

`204` объявляется `@HttpCode(HttpStatus.NO_CONTENT)`: по умолчанию Nest
отвечает на `POST` кодом `201`.

Валидация формы (DTO + глобальный `ValidationPipe`): email —
`@Transform(trim + toLowerCase)` и `@IsEmail` (порядок декораторов роли не
играет: class-transformer отрабатывает при `plainToInstance`, всегда раньше
валидации). Нормализация из PRD живёт одной точкой в DTO — сервис получает уже
нормализованный адрес. `communeCodes` — `@IsArray`, `@ArrayMinSize(1)`,
`@ArrayMaxSize(VEILLE_MAX_COMMUNES)`, `@IsString({ each: true })`,
`@Length(5, 5, { each: true })`. Дальше сервис **сначала** дедуплицирует
коды, и только потом сверяет: одним запросом
`commune.findMany({ where: { codeInsee: { in }, effectiveTo: null } })`, число
найденных ≠ числу **уникальных** переданных → `400` (сравнение с длиной
исходного массива дало бы `400` на безобидном дубле в форме; FK-ошибку до
ответа не доводить).
**Отброшено:** `404` на неизвестный токен — исключение ради штатного ответа
(выше); токен в path-сегменте (`/confirmation/:token`) — он попал бы в лог
любой 5xx, в отличие от query.

### Сценарии формы и гонка уникальности

**Решение:** три ветки сценариев PRD по нормализованному адресу, DB-изменения —
в `$transaction`, письмо — после коммита:

1. адреса нет → `Veille` + `VeilleCommune`,
   `confirmExpiresAt = now + VEILLE_CONFIRM_TTL_DAYS`;
2. `confirmedAt = null` → состав переписывается (`deleteMany` + `createMany`),
   `confirmExpiresAt` продлевается, токен прежний;
3. подтверждена → база не меняется, уходит письмо «déjà inscrit·e» с коммунами
   действующей подписки.

Гонка двух одновременных форм новым адресом (`P2002` на `unique(email)`):
поймать и повторить обработку один раз — вторая попытка попадает в ветку 2.
Ловить у себя обязательно: в глобальном маппинге `P2002` отсутствует намеренно
(`src/prisma/prisma-error.ts`), непойманным он доедет до `500`, а `409` был бы
enumeration-оракулом.
**Почему:** письмо после коммита — чтобы сбой
провайдера не откатывал подписку (пользователь повторит форму и попадёт в
ветку 2 — ровно сценарий «не нашёл письмо»). Сбой доставки отдаёт обычную
ошибку (`500` → французское сообщение на клиенте): провайдерский отказ не
управляем атакующим и enumeration не создаёт, а «тихий успех» без письма
зарезервирован PRD только за лимитом частоты.
**Отброшено:** `upsert` по email — ветки 2 и 3 обновляют разное (upsert не
различает «подтверждена ли»); сериализация через advisory lock — тяжелее
retry ради вырожденной гонки.

> **Исправлено при реализации (фаза 4, ревью PR 81).** Решение читало строку и
> ветвилось по прочитанному, а между чтением и записью строка успевала
> исчезнуть — причём отписка и часовая чистка удаляют её неотличимо, так что
> повторить ветвление значило бы воскресить подписку, от которой только что
> отписались, и выслать ей ссылки. Ветку выбирает теперь та же запись, что её
> исполняет (`claimUnconfirmed`, механика — в его докблоке); повтор остался один
> и только на `P2002`, а вторая его потеря молчит наружу, но пишет `warn` —
> иначе потерянная заявка неотличима от недоставленного письма.

> **Исправлено при реализации (фаза 1 veille-commune-change).** У ветки 3 база
> всё-таки меняется, а письма «déjà inscrit·e» больше нет: решение и его
> механика — `veille-commune-change.md`, «Ветка подтверждённого адреса
> в `subscribe`».

### One-click отписка (RFC 8058): route handler в web, каркас писем не меняется

**Решение:** путь отписки в письме один — `/veille/desinscription?token=…`
(им заполняются и ссылка подвала, и `List-Unsubscribe`, как каркас уже делает).
В web на этом пути живёт **route handler** `src/app/veille/desinscription/route.ts`:

- `POST` (почтовый клиент шлёт `List-Unsubscribe=One-Click`,
  `application/x-www-form-urlencoded`, без cookie и CSRF) — серверный `fetch`
  на `POST <API>/veille/desinscription` с токеном из query → `200`;
- `GET` (человек из письма, сканеры, превью) — redirect на страницу с кнопкой
  `/veille/desinscription/confirmer?token=…` (`page.tsx` в дочернем сегменте —
  с `route.ts` в одном сегменте страница жить не может).

**Почему:** это единственный вариант, не трогающий инвариант каркаса «та же
ссылка уходит в `List-Unsubscribe`» и его проверку origin (`FRONTEND_URL`).
RFC 8058 требует, чтобы POST на URL из заголовка отписывал без промежуточных
экранов, — а решение проекта «переход по ссылке не меняет данных» касается
`GET`; route handler разводит методы на одном URL. Next.js route handlers не
требуют CSRF-токена — штатная кнопка Gmail сработает. Адрес API серверная
часть web берёт из того же `NEXT_PUBLIC_API_URL` (`src/lib/api/config.ts`).
**Отброшено:** `List-Unsubscribe` прямо на API — заголовок собирает каркас из
`unsubscribePath` относительно `FRONTEND_URL`, и ослаблять проверку origin ради
второй базы — расширение атакуемой поверхности, от которого проект уже
защитился; второй путь только для заголовка (расширение `ComposeMailInput`) —
правка контракта каркаса, которая не нужна, когда один URL обслуживает оба
метода; middleware с rewrite по методу — более хрупкая версия того же route
handler.

### Страницы web и форма подписки

**Решение:** три страницы App Router, все — в `tests/pages.ts`:

- `/veille` — форма (клиентский компонент): email + мультивыбор коммун +
  цель обработки и ссылка на `politique-de-confidentialite`; отправка —
  `useMutation` через `apiFetch`; после успеха — экран «письмо отправлено»
  с `role="status"`.
- `/veille/confirmation?token=…` — на загрузке `useQuery` статуса; `pending` →
  кнопка «Confirmer», по нажатию `useMutation` → «подписка активна»; `active` →
  сразу «подписка активна»; `invalid` → «lien invalide».
- `/veille/desinscription/confirmer?token=…` — всегда кнопка
  «Se désinscrire»; по нажатию `useMutation` → «désinscription effectuée»
  (повторные нажатия и заходы безошибочны, потому что API идемпотентен).

Обе страницы с токеном читают его `useSearchParams()` и потому обязаны быть
обёрнуты в `<Suspense>`: без границы `next build` падает на пререндере
статической страницы. В `tests/pages.ts` они попадают с заведомо невалидным
токеном (`?token=invalide`, статус `200`) — общие сьюты покрывают ветки «lien
invalide» и «кнопка отписки», а `pending`/`active` проверяются отдельным
тестом со своей подпиской.

Выбор коммун — **Base UI Combobox** (`@base-ui/react/combobox`, уже
установлен): `multiple`, чипы выбранных (`Combobox.Chips` / `Chip` /
`ChipRemove`), серверная фильтрация — контролируемый `inputValue` +
`useQuery` с ключом из общей фабрики (`queryKeys.communes(q)` в
`src/lib/api/keys.ts` — правило `apps/web/CLAUDE.md`: ключей по компонентам
не заводить) на `GET /communes?q=…` с задержкой ввода
(`enabled: q.length >= COMMUNE_SEARCH_MIN_QUERY_LENGTH`,
`placeholderData: keepPreviousData` — детали по скиллу tanstack-query,
обязательному перед кодом), результаты — проп
`filteredItems` (внутренняя фильтрация выключается сама). Объявление
результатов скринридеру — штатный `Combobox.Status` (live-region «N communes
trouvées» / `Combobox.Empty` «aucune commune trouvée» — строки из `fr.ts`);
компонент обязан оставаться смонтированным (требование Base UI к анонсам).
**Почему:** Base UI — принятая компонентная база (`apps/web/CLAUDE.md`),
Combobox 1.6 закрывает весь список требований критериев (клавиатура,
мультивыбор, анонсы) готовыми частями — ничего доступного руками писать не
нужно; если у shadcn-реестра есть Base UI-вариант combobox — взять его
(`npx shadcn add` выполняет владелец), это те же части с готовыми стилями.
**Отброшено:** `Autocomplete` Base UI — это поле со свободным значением и
подсказками, а форме нужен выбор строго из справочника; самописный
listbox — переизобретение доступности, которую библиотека уже гарантирует;
`Select` — нет поискового ввода.

### Константы и типы contracts

**Решение:** в `packages/contracts/src/enums.ts`, рядом с
`COMMUNE_SEARCH_LIMIT`: `VEILLE_MAX_COMMUNES = 20`,
`VEILLE_CONFIRM_TTL_DAYS = 7`, `VEILLE_FORM_EMAIL_DAILY_LIMIT = 5`,
`type VeilleConfirmationStatus = 'pending' | 'active' | 'invalid'` (+ интерфейс
ответа подтверждения). Туда же переезжает `MIN_QUERY_LENGTH` формы поиска
коммун под именем `COMMUNE_SEARCH_MIN_QUERY_LENGTH`: сейчас она объявлена в
`apps/api/src/communes/dto/search-communes-query.dto.ts`, а порог нужен обеим
сторонам — иначе combobox напишет `2` вторым местом. Правка DTO — тем же
коммитом, что и константа.
**Почему:** правило проекта — пороги живут в contracts и не дублируются:
20 нужен обеим сторонам (валидация DTO и подсказка формы), 7 — тексту письма и
странице, статус — общий словарь API и клиента. Это числа продуктовых решений
владельца (02.08.2026), не юридические сроки — `SourceReference` не требуется,
в `DeadlineRule` им не место (там только сроки с источником).
**Отброшено:** дублирование литералов в DTO и форме — главное правило проекта.

### Письма фичи

**Решение:** два письма через `MailService.send()`, строки — ветка
`fr.mail.veille` в `src/i18n/fr.ts`:

1. **Подтверждение**: параграф с целью, блок `list` с названиями выбранных
   коммун («Nîmes (Gard)»), блок `link` «Confirmer votre inscription» с путём
   `/veille/confirmation?token=…`, параграф о сроке 7 дней (число — из
   константы contracts).
2. **«Vous êtes déjà inscrit·e»**: параграф-объяснение, блок `list` с коммунами
   действующей подписки; ссылка отписки не дублируется — она уже в подвале
   каркаса (`unsubscribePath` обязателен типом).

`unsubscribePath` обоих писем — `/veille/desinscription?token=<unsubToken>`.
`reason` (обязательное поле `ComposeMailInput`, каркас вставляет его в подвал
через `fr.mail.footer.why`) — одна строка `fr.mail.veille.reason` на оба
письма: повод у них общий — адрес оставлен в форме veille на сайте. Коммуны в
неё не подставляются, они уже перечислены блоком `list`.
**Почему:** блочная модель гарантирует совпадение ссылок в text и HTML;
подвал каркаса уже даёт отписку в каждом письме — включая письмо-подтверждение
неподтверждённой подписки (критерий PRD). Названия коммун — данные, не тексты
UI, им можно приходить из базы.
**Как применять:** фикстуры тестов писем — темы и тела не короче 10 символов
(ограничение Scaleway TEM, `docs/research/emails.md`).

> **Исправлено при реализации (фаза 1 veille-commune-change).** Письмо 2
> заменено письмом изменения состава (`veille-change-mail.ts`) — причина во
> врезке «Сценарии формы и гонка уникальности» выше; ссылка на подтверждение
> заявки в нём есть, ссылка отписки по-прежнему только в подвале каркаса.

## Ограничения и риски

- **Тайминг ответа формы не выравнивается.** PRD требует одинаковый ответ, и
  он одинаков (204, пустое тело); ветки различаются длительностью (создание
  строк против письма «уже подписаны»). Выравнивание времени — не требование
  PRD; принятый риск, вернуться при появлении абьюза вместе с капчой.
- **Email в тексты ошибок не попадает по построению** (исключений с токеном и
  адресом нет, `AllExceptionsFilter` сообщений не логирует), но тесты «email не
  встречается в логах» обязаны проверять **все аргументы** `Logger` через
  `jest.spyOn` + `JSON.stringify` — образец в docs/research/emails.md.
- **`VEILLE_EMAIL_HASH_SECRET` без ротации**: смена секрета обнуляет действующее
  окно счётчика (старые хеши перестают совпадать). Приемлемо — окно живёт 24 ч.
- **Один-клик POST проходит через web** (route handler → API): отписка из
  почтового клиента требует, чтобы поднят был и web, и API. Ручная проверка
  кнопки отписки Gmail/Outlook после деплоя обязательна — зафиксировать
  результат в `src/mail/CLAUDE.md` рядом с проверкой доставки от 03.08.2026.
- **Лимит писем не атомарен**: два одновременных запроса, увидевшие по четыре
  строки в окне, отправят шестое письмо. Принятый риск — блокировка ради
  антиспам-счётчика дороже одного лишнего письма в сутки на адрес.
- **`Combobox` в shadcn-реестре не проверен** — если Base UI-варианта
  combobox у shadcn нет, собирать напрямую из `@base-ui/react/combobox`: это
  не «свой примитив», а та же принятая база. Сами части (`chips`, `chip`,
  `chip-remove`, `status`, `empty`) и проп `filteredItems` в установленной
  1.6 есть — сверено по пакету 15.08.2026. Арбитр доступности — axe-прогон и
  клавиатурный тест, не документация.
- **Сборка `next build` затронет `route.ts` с server-side fetch** — адрес API
  читается в рантайме сервера web (`NEXT_PUBLIC_API_URL` инлайнится и в
  серверный код при сборке; для MVP адрес одинаков в бандле и на сервере).
  Если когда-нибудь внутренний адрес API разойдётся с публичным — понадобится
  отдельная серверная переменная; сейчас не заводить.
