# Research: Аккаунт пострадавшего

**PRD**: docs/prd/user-account.md (план составляется после этого отчёта)
**Дата**: 2026-08-22

> **Снапшот на дату.** Отчёт фиксирует решения на момент ресерча; расхождения
> при реализации отмечаются врезкой «Исправлено при реализации», как в
> docs/research/emails.md.

Стек, от которого отталкиваются решения: NestJS 11 на Fastify, Prisma 7.9 +
PostgreSQL 18; **весь auth-стек уже установлен и настроен на будущее**:
`bcrypt` 6, `passport` + `passport-local` + `passport-jwt`, `@nestjs/jwt`,
`@nestjs/passport`, `@fastify/cookie`, `@nestjs/throttler`, а
`env.validation.ts` уже содержит `JWT_SECRET`, `JWT_REFRESH_SECRET`,
`COOKIE_SECRET`, `SALT_ROUNDS`, `ACCESS_TOKEN_EXPIRY`, `REFRESH_TOKEN_EXPIRY`
(последняя с тех пор убрана — врезка ниже).
Web — Next.js 16.2, React 19.2, TanStack Query 5.101, Playwright + axe.
**Новых зависимостей не требуется ни одной** — офлайн-предусловие Ralph Loop
выполнено из коробки; новая переменная окружения одна (см. § «Ограничение
попыток входа»).

Не переисследуется (решено раньше, фазы следуют буквально):

- Passport local + JWT, refresh с ротацией, схема `User`/`RefreshToken` —
  `docs/research/data-model.md` § 5; «refresh — в httpOnly-cookie, access — в
  теле ответа» — `apps/api/CLAUDE.md`;
- токены ссылок в письмах (`randomBytes(32).toString('base64url')`, в базе —
  SHA-256-хеш, `findUnique` по хешу; перевыпуск хешей только при фактической
  отправке нового письма), HMAC-хеш адреса для счётчиков, лимит писем в
  сервисе фичи, фоновая чистка `@nestjs/schedule` с индексами —
  `docs/research/veille-subscription-lifecycle.md`;
- отправка письма — только `MailService.send()` (`src/mail/CLAUDE.md`);
- слой API клиента (`src/lib/api/`), TanStack Query, тесты Playwright + axe —
  `docs/research/web-foundation.md`.

## Решения

### Правила пароля: CNIL, cas n° 2 — 50 бит + ограничение попыток

**Решение:** политика cas n° 2 délibération CNIL n° 2022-100 (21.07.2022):
минимум **8 символов с 3 из 4 категорий** (прописные, строчные, цифры,
спецсимволы) **плюс обязательное ограничение попыток входа** (см. отдельный
раздел). Максимум — **72 байта** (предел bcrypt, дальше вход усекается
молча). Константы и `SourceReference` — в contracts:
`url: https://www.legifrance.gouv.fr/cnil/id/CNILTEXT000046437451`,
`verifiedAt: 2026-08-22`.
**Почему:** PRD требует правила CNIL с источником, не выдуманные. CNIL считает
энтропией: 80 бит для пароля «в одиночку», 50 бит — когда доступ к аккаунту
ограничен; ограничение попыток у нас обязательно по PRD (перебор), поэтому
честно берётся cas n° 2 — 12-символьный минимум cas n° 1 для пожилой
аудитории в стрессе был бы лишним трением без выигрыша по букве рекомендации.
**Отброшено:** cas n° 1 (80 бит, ≥12 символов 4 категорий) — см. выше;
парольные фразы «от 5 французских слов» (другой пример 50 бит) — валидация
«слова французского языка» нереализуема честно; проверка по спискам утёкших
паролей — внешний сервис (HIBP) в MVP не нужен, локальный словарь — новая
зависимость без требования в PRD.
**Как применять:** класс-валидатор DTO регистрации и смены пароля один на оба
эндпоинта; сообщение об ошибке — из `fr.ts`, называет все требования сразу.

### Хеширование пароля: bcrypt, cost из `SALT_ROUNDS`

**Решение:** установленный `bcrypt` 6.0, cost — существующая переменная
`SALT_ROUNDS`, умолчание поднять до 12 в `env.validation.ts`.
**Почему:** уже в зависимостях (вместе с `@types/bcrypt`) — правило «предпочитай
установленное»; OWASP признаёт bcrypt с work factor ≥ 10; ограничение 72 байта
закрыто максимумом длины из раздела выше. Асинхронные `hash`/`compare` не
блокируют event loop.
**Отброшено:** `argon2` — CNIL называет scrypt/Argon2 примерами, но это новая
нативная зависимость (Ральф офлайн), а bcrypt остаётся признанной
специализированной функцией; при желании мигрировать позже — rehash при
успешном входе, без сброса паролей.

### Схема данных: `User` + `PasswordReset` + счётчики

**Решение:** `User` по `docs/research/data-model.md` § 5 **плюс** поля
подтверждения по образцу veille: `confirmedAt` (null = не подтверждён),
`confirmTokenHash` `unique`, `confirmExpiresAt`. Отдельные таблицы:
`PasswordReset` (id, userId → User cascade, tokenHash `unique`, expiresAt,
usedAt null), `AccountFormEmail` (emailHash, sentAt) — счётчик писем по
образцу `VeilleFormEmail`, `LoginAttempt` (emailHash, attemptedAt) — счётчик
неудачных входов. Модель данных § 5 полей подтверждения не знает — расхождение
правится в `data-model.md` тем же коммитом, что и миграция (прецедент — veille).
**Почему:** поля подтверждения в `User`, а не отдельной таблицей — состояние
одно на аккаунт, как у veille; `PasswordReset` отдельно — заявок может быть
несколько, «одноразовость» это `usedAt`, а чистка не трогает `User`.
Счётчики — по хешу адреса, а не `userId`: лимиты обязаны работать и для
несуществующих адресов (анти-enumeration), у которых `userId` нет.
**Отброшено:** reset-токен полями в `User` — повторный запрос сброса гасил бы
предыдущую ссылку и усложнил «одноразовость»; хранение попыток входа в
Redis/памяти — новая инфраструктура, при рестарте счётчик обнуляется.

> **Расхождение с реализацией (фаза 3, ревью PR 141).** Заявок по-прежнему
> может быть несколько, но успешная смена пароля гасит (`usedAt`) все
> непогашенные заявки аккаунта, а не только предъявленную — иначе ссылка из
> более раннего письма могла бы перезаписать только что выбранный пароль и
> отозвать сессии владельца. Тогда же смена пароля по токену подтверждает
> неподтверждённый аккаунт (`confirmedAt`): доставленный и потраченный токен
> доказывает владение ящиком так же, как ссылка подтверждения, а без этого
> сброс ставил пароль, с которым вход всё равно отвечает 401.

### Сессия: access 15 минут в теле, refresh 30 дней в httpOnly-cookie

**Решение:** access-токен (`@nestjs/jwt`, `JWT_SECRET`,
`ACCESS_TOKEN_EXPIRY` умолчание `15m`) возвращается в теле ответа и живёт в
памяти клиента; refresh (`JWT_REFRESH_SECRET`, `REFRESH_TOKEN_EXPIRY`
умолчание `30d`) — httpOnly-cookie: `path=/auth`, `SameSite=Strict`,
`secure` вне dev, подпись `COOKIE_SECRET` (`@fastify/cookie` уже
регистрируется в `main.ts`). Ротация — по data-model § 5: вставка нового
`RefreshToken` + revoke старого; каждый новый живёт 30 дней, так что «предел
давности» PRD означает 30 дней **неактивности**. Сброс пароля и удаление
аккаунта revoke'ают все refresh-токены пользователя.
**Почему:** схема прямо предписана `apps/api/CLAUDE.md`; httpOnly-cookie
недоступна XSS, `path=/auth` не шлёт её на каждый запрос, `SameSite=Strict`
закрывает CSRF на refresh-эндпоинте (web и API — same-site: localhost:3000/3001
в dev, поддомены одного домена в проде). Повторное использование уже
отозванного refresh-токена — признак кражи: revoke всей цепочки пользователя.

> **Расхождение с реализацией (фаза 2, ревью PR 140).** `REFRESH_TOKEN_EXPIRY`
> как переменной нет: срок берётся из `SESSION_INACTIVITY_DAYS` (contracts),
> чтобы число, которое web показывает людям, не могло разойтись с реальным.
> Повторное предъявление отозванного токена — кража только по истечении
> короткого grace-окна после ротации; раньше — вторая вкладка или ретрай, и
> ей выдаётся своя пара. Выход и чистка цепочки удаляют строки, не помечают:
> иначе запоздалый refresh после logout выглядел бы как кража. Как именно —
> `apps/api/src/auth/CLAUDE.md`.

**Отброшено:** access в localStorage — доступен XSS; сессии в базе вместо JWT —
второй механизм при уже выбранном и заведённом в env JWT; `SameSite=Lax` —
Strict работает для same-site fetch, а большего не нужно.

### Guard: глобальный `JwtAuthGuard` + `@Public()`

**Решение:** jwt-стратегия Passport + глобальный guard через `APP_GUARD`;
публичные эндпоинты (все существующие: veille, здоровье, будущие auth-формы)
помечаются декоратором `@Public()` (метаданные + `Reflector`).
**Почему:** fail-closed: новый эндпоинт синистра защищён по умолчанию, забытая
аннотация даёт 401, а не утечку. Разовая расстановка `@Public()` по
существующим контроллерам дешевле, чем вечная обязанность помнить guard на
каждом новом приватном.
**Отброшено:** guard точечно на приватных контроллерах — fail-open, забыть
guard проще, чем заметить лишний 401.

### Ограничение попыток входа: счётчик по адресу + throttler по IP

**Решение:** два слоя. (1) `LoginAttempt` по HMAC-SHA256 нормализованного
адреса — новая переменная `ACCOUNT_EMAIL_HASH_SECRET` (`IsSecret()`, в
`env.validation.ts` и `.env.example` одним коммитом); после **10 неудачных
попыток за час** ответ 429 «trop de tentatives» — одинаковый для существующего
и несуществующего адреса, успешный вход счётчик не сбрасывает раньше времени
чистки. (2) Существующий глобальный `@nestjs/throttler` + ужесточённый
`@Throttle` на `POST /auth/*` по IP.
**Почему:** «10 essais par heure» — дословно один из механизмов restriction
d'accès из délibération 2022-100, он же делает законным cas n° 2 для правил
пароля. Счётчик по адресу, а не по аккаунту: блокировка «аккаунта» с особым
ответом раскрывала бы его существование; по хешу адреса лимит един для всех
адресов. Throttler по IP отдельно — распределённый перебор сотней адресов
счётчик одного адреса не остановит (та же пара слоёв, что у формы veille).
**Отброшено:** блокировка аккаунта до разблокировки письмом — DoS на жертву
одним скриптом; экспоненциальная задержка ответа — держит соединения открытыми
на Fastify без выгоды против распределённого перебора; отдельный секрет не
переиспользуется из veille — разделение ключей по назначению (прецедент:
`VEILLE_EMAIL_HASH_SECRET` против `JWT_SECRET`).

> **Исправлено при реализации (фаза 4, issue #132; отмечено по ревью PR 142).**
> Счётчик проверяется **после** пароля, а не до: с проверкой до него отброшенный
> выше DoS возвращался в скользящем виде — десять неверных паролей в час,
> раскиданных по IP, и владелец не входит с верным. Верный пароль проходит
> всегда и счётчик обнуляет; то же делает завершённый сброс пароля. Счёт и
> вставка идут под `withAddressLock` (`src/common/address-lock.ts`) — без него
> одновременный залп читает один и тот же долимитный счёт и покупает себе
> лишние попытки. Подробности — докблоки `validateCredentials` и
> `chargeFailedLogin`.

### Письма аккаунта и лимит 5/24 ч

**Решение:** три письма фичи — подтверждение регистрации, сброс пароля, «у вас
уже есть аккаунт» (уходит на повторную регистрацию подтверждённым адресом,
внутри — ссылка запроса сброса); все через `MailService.send()`, блочная
модель, `link` несёт путь. Лимит — счётчик `AccountFormEmail` в auth-сервисе
перед `send()`, строка пишется до отправки и вне транзакции; письма veille и
будущие напоминания под лимит не подпадают.
**Почему и как применять:** дословно паттерн
`docs/research/veille-subscription-lifecycle.md` (лимит у владельца письма,
каркас нем к содержимому); HMAC-утилита адреса выносится в общий модуль с
секретом-параметром — вторая копия функции нарушила бы правило дубликатов.
**Отброшено:** общая таблица счётчика с veille — миграция выполненной фичи
ради экономии одной таблицы; подпадание писем сброса под отдельный лимит —
PRD называет один лимит на все «письма аккаунта».

> **Исправлено при реализации (фаза 4, issue #131; отмечено по ревью PR 142).**
> Лимит остаётся один и общий (пять писем в сутки на адрес), но регистрационные
> письма берут из него только `ACCOUNT_REGISTRATION_MAIL_LIMIT`: их вызывает
> кто угодно на чужой адрес, и пятью регистрациями иначе гасится письмо сброса
> — единственное, которым владелец возвращает себе аккаунт. Токен подтверждения
> при повторной регистрации ротируется **внутри** лимита (`compose` в
> `sendAccountMail`, как у `resendConfirmationMail` veille): ротация до
> проверки лимита обесценивала ссылку предыдущего письма и не слала нового.
> И `POST /auth/register` с `POST /auth/password-reset` получили свой
> `AUTH_MAIL_RATE_LIMIT` (5/мин по IP, как у формы veille) вместо общего
> `AUTH_FORM_RATE_LIMIT`: 30/мин с одного IP — это 30 адресов в минуту, мимо
> счётчика по адресу.

### Чистка: один cron-час, индексы в той же миграции

**Решение:** фоновая задача `@Cron(CronExpression.EVERY_HOUR)`:
`user.deleteMany({ confirmedAt: null, confirmExpiresAt: { lt: now } })`
(каскад сносит его `RefreshToken`/`PasswordReset`),
`passwordReset.deleteMany({ expiresAt: { lt: now } })`,
`refreshToken.deleteMany({ expiresAt: { lt: now } })` (чистка из data-model
§ 5), `accountFormEmail`/`loginAttempt` старше 24 ч. Срок дополнительно
проверяется в самих запросах подтверждения/сброса («lien invalide»).
Частичные индексы под каждый `deleteMany` — **в той же миграции**, что и
таблицы.
**Почему:** решение и аргументы — чистка veille (обещание «отсутствует в
базе — проверяется запросом» выполняет только фоновое удаление); индексы
сразу — урок ревью PR 81, где их пришлось добирать отдельной миграцией.
**Отброшено:** чистка при обращении и `pg_cron` — по тем же причинам, что в
veille.

### Web: сессия на клиенте и защита страниц

**Решение:** access-токен живёт в памяти слоя `src/lib/api/` (модульное
состояние рядом с `client.ts`), в браузерное хранилище не пишется. При
старте приложения и при 401 клиент делает «тихий» `POST /auth/refresh`
(`credentials: 'include'`); нет валидной сессии после попытки — редирект на
страницу входа. Страницы: inscription, connexion, mot-de-passe-oublié,
réinitialisation (по токену из ссылки), confirmation (по токену, кнопка —
GET не мутирует), espace personnel. Защита espace — **клиентский guard плюс
401 от API**; Next.js middleware не используется.
**Почему:** refresh-cookie принадлежит origin'у API — Next-серверу и его
middleware она не видна в принципе, «защита» в middleware была бы
декоративной; настоящая граница — guard API, клиентский редирект — только UX.
Память вместо localStorage — недоступность XSS; цена — лишний refresh при
перезагрузке страницы, что PRD не нарушает.
**Отброшено:** проксирование API через Next rewrites ради общего origin —
перестройка выполненного слоя `src/lib/api/` без необходимости (same-site
cookie работает и так); хранение access в cookie web-домена — второй носитель
той же сессии.

### Contracts

**Решение:** в `@mon-sinistre/contracts` — DTO-типы auth-эндпоинтов и
константы с source рядом: `PASSWORD_MIN_LENGTH = 8`, `PASSWORD_MAX_BYTES =
72`, `PASSWORD_MIN_CHAR_CLASSES = 3` (+ `SourceReference` на délibération
2022-100), `ACCOUNT_CONFIRM_TTL_DAYS = 7`, `PASSWORD_RESET_TTL_HOURS = 24`,
`SESSION_INACTIVITY_DAYS = 30`, `ACCOUNT_EMAIL_LIMIT`/`WINDOW` (5/24 ч),
`LOGIN_ATTEMPT_LIMIT`/`WINDOW` (10/час). Текстов UI в contracts нет.
**Почему:** правило проекта — пороги и интервалы живут в contracts один раз;
web валидирует пароль теми же константами, что API.

## Ограничения и риски

- **bcrypt использует только первые 72 байта** — без максимума длины две
  разные парольные фразы длиннее 72 байт были бы «равны». Закрыто константой
  `PASSWORD_MAX_BYTES` и валидацией по байтам (не символам: UTF-8).
- **CNIL называет scrypt/Argon2 примерами** функций хранения; bcrypt —
  признанная альтернатива (OWASP), но при будущем ужесточении миграция —
  rehash при успешном входе, поле алгоритма не требуется (формат `$2b$…`
  самоописателен).
- **`SameSite=Strict` полагается на same-site** web и API: в проде оба обязаны
  жить на поддоменах одного registrable domain, иначе cookie не уйдёт вовсе.
  Зафиксировать при выборе хостинга.
- **Глобальный guard меняет поведение всех существующих эндпоинтов** — фаза,
  которая его вводит, обязана пройтись по каждому контроллеру с `@Public()` и
  прогнать интеграционные тесты veille/monitor: забытая аннотация ломает
  выполненные фичи.
- **Ответ 429 по адресному счётчику технически отличим** от 401 — это
  осознанно: он одинаков для существующих и несуществующих адресов, поэтому
  существования аккаунта не раскрывает, а CNIL требует именно видимого
  ограничения попыток.
- Удаление аккаунта в этой итерации каскадирует только `RefreshToken` и
  `PasswordReset`; расширение каскада на `Sinistre`/файлы — фича синистра
  (`docs/research/data-model.md` § 7 уже описывает целевую цепочку).
- Ralph Loop: новых зависимостей нет; до запуска фаз вручную добавить только
  `ACCOUNT_EMAIL_HASH_SECRET` в локальный `.env` (сгенерировать), остальное —
  штатные правки схемы/`.env.example` внутри фаз.
