### Источник данных: выгрузки DILA JORFSIMPLE

**Решение:** берём открытые выгрузки DILA, вариант **JORFSIMPLE**
(https://echanges.dila.gouv.fr/OPENDATA/JORFSIMPLE/): анонимный HTTPS,
Licence Ouverte, инкрементальные дельты `JORFSIMPLE_YYYYMMDD-HHMMSS.tar.gz`
дважды в сутки (~00:20–01:15 — полный свежий номер JO, ~20:50–22:10 —
обогащённые повторные поставки; Europe/Paris).
**Почему:**

- один самодостаточный XML на текст: корень `<TEXTE>` несёт `<NOR>`,
  `<DATE_PUBLI>` (формат `YYYY-MM-DD` — та самая дата публикации из XML,
  жёсткое ограничение ТЗ § 7), `<DATE_TEXTE>` (подписание), `<NATURE>`,
  `<TITREFULL>`, `<NUM_PARUTION>`, `<ORIGINE_PUBLI>` («JORF n°0137 du 13 juin
  2026» — готовое значение `Arrete.jorfNumber`) и обе annexes с таблицами
  inline. Проверено на арретé 12.06.2026 (`JORFTEXT000054245373`, 604 КБ);
- оглавление номера (`JORFCONT<id>.xml`, лежит в том же каталоге
  `jorf/simple/JORF/CONT/…/JORFCONT<id>/`) перечисляет тексты строками
  `<LIEN_TXT idtxt="JORFTEXT…" titretxt="…"/>` — отбор по титулу не требует
  открывать каждый текст;
- дата обнаружения = дата прогона, письма уходят в день дельты — лаг ≤ 24 ч
  ТЗ § 6 выполняется двумя прогонами в сутки без «пуш»-механики, которой у
  DILA нет.

**Отброшено:**

- **JORF («global»)** — те же данные, но каждый текст разложен на 4–5 связанных
  файлов (`texte/version`, `texte/struct`, `section_ta`, `article`) с
  адресацией по ID, порезанному в путь. Сборка текста из кусков — лишний код
  без выигрыша: единственное, чего нет в JORFSIMPLE, — заполненный `<LIENS>`
  (ссылки на цитируемые тексты), монитору он не нужен.
- **API Légifrance (PISTE)** — регистрация, OAuth client_credentials,
  недокументированные квоты, статус «bêta»; сама Légifrance в FAQ отсылает к
  echanges.dila.gouv.fr как каналу массового доступа.

**Как применять:** листинг каталога — обычный Apache-индекс; имена дельт
вынимаются из HTML регулярным выражением
`/JORFSIMPLE_\d{8}-\d{6}\.tar\.gz/g`, обрабатываются по возрастанию имени
(имя = таймстамп генерации). HTTP — нативный `fetch` с fetch-функцией через
конструктор клиента (образец `GeoApiClient`), таймаут листинга 60 с.

### Распаковка дельты: node-tar

**Решение:** новая зависимость **`tar` (node-tar) ^7.5**; поток
`fetch body → tar.Parse` (gzip node-tar распознаёт сам), из архива читаются
только пути `jorf/simple/JORF/CONT/**/*.xml`, каждый нужный файл собирается в
строку в памяти.
**Почему:** формат отдаётся только тарболами, парсер tar руками не пишут;
node-tar — стандарт де-факто с потоковым API (`onReadEntry`), дельты
28 КБ–18 МБ обрабатываются без записи на диск. Это первая обязательная новая
зависимость проекта с фазы 0 — обоснование и есть этот раздел.
**Отброшено:** `tar-stream` — ниже уровнем (gunzip и маршрутизацию потоков
пришлось бы собирать самим) при тех же транзитивных зависимостях; распаковка
через `child_process` + системный `tar` — непереносимо и непригодно для мока в
тестах.

### XML-парсер: @rgrove/parse-xml

**Решение:** новая зависимость **`@rgrove/parse-xml` ^4.2** — маленький
строгий XML-парсер без зависимостей, возвращающий дерево узлов с сохранением
порядка детей.
**Почему:** монитору нужен обход дерева, а не объектный маппинг: метаданные —
поиск тега по имени, annexes — таблицы со смешанным содержимым (`<br/>`
внутри `<td>`, многострочные ячейки motivations), где порядок узлов — это
данные. `children`-массив parse-xml даёт склейку текста ячейки с `\n` на
`<br/>` тривиальным обходом. Типы TS встроены.
**Отброшено:** `fast-xml-parser` v5 — тянет 6 зависимостей, а его основной
режим (объектный маппинг) на смешанном содержимом склеивает текстовые узлы,
теряя границы; режим `preserveOrder` возвращает структуры громоздче, чем
дерево parse-xml. `@xmldom/xmldom` — полный DOM API ради задачи, которой
хватает узлов и обхода. SAX (`saxes`) — потоковость не нужна: самый большой
встреченный файл 604 КБ.

### Отбор текстов и структура annexe

**Решение:** текст берётся в обработку, если `titretxt` в оглавлении номера
содержит подстроку `portant reconnaissance de l'état de catastrophe
naturelle` (регистронезависимо); после открытия файла проверяется
`<NATURE>ARRETE</NATURE>`.
**Почему:** титул — единственный стабильный признак. NOR-префикс — код
министерства и меняется с переименованиями (`INTE…` 1993, `IOME…` 2023,
`INTE…` 2026) — фильтровать по нему нельзя. Историческая формулировка
«portant **constatation**…» встречается только до ~2000-х — вне скоупа
бэкфилла с 2026 года.
**Как применять:** annexe в `<TEXTE>` — это `<SECTION_TA>` с
`<TITRE_TA>Annexe</TITRE_TA>` и статьёй без номера; тело —
`<BLOC_TEXTUEL><CONTENU>` c HTML-подобной таблицей в нижнем регистре
(`<table border="1">`, строки `<tr>`, ячейки `<td>`, шапка — тоже `<td>`, не
`<th>`; текст ячеек начинается с `<br/>`). Проверенные колонки:

- Annexe I (reconnues): Département, Commune, Phénomène naturel, Date de
  début…, Date de fin…, Nombre de reconnaissances… (бывает пустой `<td/>`),
  Motivations de la décision;
- Annexe II (non reconnues): то же без «Nombre de reconnaissances».

Шапку сопоставлять по текстам заголовков (склеенным из кусков, разорванных
`<br/>`), а не по позициям: `align`/`valign` варьируются даже между annexes
одного арретé. Какая annexe что значит, определять по подписи перед таблицей
(«Communes reconnues…» / «Communes non reconnues…»), не по порядку следования.
Таблица, чья шапка не сопоставилась с ожидаемыми колонками, — алерт
`UNPARSEABLE_ANNEXE`, остальные тексты дельты обрабатываются дальше (PRD:
прогон не падает). Даты ячеек — `DD/MM/YYYY` → `toIsoDate` из contracts;
кодов INSEE в annexe **нет** — только названия департамента и коммуны.
`legifranceUrl` собирается как
`https://www.legifrance.gouv.fr/jorf/id/<JORFTEXT id>`.

### Сопоставление коммун со справочником

**Решение:** матч по паре (департамент, коммуна), обе стороны — через
существующий `normalizeCommuneName` (единственная точка входа поискового
ключа, `apps/api/CLAUDE.md`): `nameNormalized` коммуны уже в базе, название
департамента из ячейки нормализуется тем же правилом и сравнивается с
нормализованным `departementName`.
**Почему:** одна функция для записи и чтения — то же обоснование, что в
`docs/research/commune-referential.md`; annexe печатает актуальные названия,
которые обязаны совпасть со справочником COG с точностью до регистра и
диакритики.
**Как применять:** сначала среди актуальных строк (`effectiveTo: null`);
если не нашлось — среди устаревших (арретé может опоздать к слиянию коммун).
Ноль кандидатов или больше одного — `codeInsee: null` + алерт
`UNMATCHED_COMMUNE`; строка сохраняется с `communeLabelRaw`/`departementRaw`
как напечатано (data-model § 4), ручная починка mapping'а — разбор алерта.

### Дедупликация, contentHash и rectificatifs

**Решение:** `contentHash` — SHA-256 канонической JSON-сериализации
**распарсенного** содержимого (метаданные арретé + отсортированный список
entries), не сырого XML-файла.
**Почему:** вечерняя дельта повторно поставляет тексты утреннего номера в
обогащённом виде — файл меняется, содержимое арретé нет. Хэш по файлу считал
бы каждое обогащение rectificatif'ом; хэш по распарсенному содержимому
стабилен ровно к тем изменениям, которые монитору безразличны. Семантика
data-model § 4 сохраняется: совпадение — только `lastSeenAt`, несовпадение —
настоящий rectificatif (upsert entries + письма новым коммунам).
**Как применять — два наблюдаемых механизма rectificatif:**

1. **Повторная поставка того же NOR с изменившимся содержимым** (у исходного
   текста есть блок `<RECT>` под ректификацию) — штатный путь: upsert entries
   существующего арретé, новые entries дают письма их наблюдателям
   (идемпотентность `unique(veilleId, arreteId)` отсекает уже уведомлённых).
   Смена `outcome` существующей entry — алерт `OUTCOME_CHANGED`, писем нет
   (решение 02.08.2026, data-model § 4).
2. **Отдельный текст-rectificatif**: новый JORFTEXT, титул исходного +
   « (rectificatif)», NOR исходного с последней буквой `A` → `Z` (проверено
   на данных: `MICA2518811A` → `MICA2518811Z`; catnat-пример 1993 —
   `INTE9300315Z`). Тело — проза «Au lieu de… lire…», парсить её не пытаемся:
   титул проходит отбор, табличной annexe нет → срабатывает штатный алерт
   нераспознаваемой структуры, человек разбирает руками. Такой текст **не**
   создаёт новый Arrete.

Связь Z-текста с оригиналом (первые 11 символов NOR) — в тексте алерта, чтобы
разбор начинался с готовой ссылки.

### Расписание прогонов

**Решение:** `@Cron('0 6,23 * * *', { timeZone: 'Europe/Paris' })` в новом
модуле `src/jorf/`; `@nestjs/schedule` уже подключён (`ScheduleModule.forRoot`
в `AppModule`), образец тика с самостоятельным `try/catch` — часовая чистка
veille.
**Почему:** утренние дельты наблюдались до 01:15, вечерние до 22:06
(Europe/Paris) — прогоны в 06:00 и 23:00 ловят обе с запасом, «не реже двух
раз в сутки» ТЗ § 5 выполнено, письмо о ночной публикации уходит утром того
же дня. Часовой пояс обязателен в декораторе: серверные часы не обязаны быть
парижскими, а границы «в день публикации» — парижские.
**Как применять:** состояние — новая таблица **`JorfDelta`** (`fileName` text
PK, `processedAt` timestamptz): прогон листает каталог, берёт имена больше
последнего обработанного, помечает дельту после полной обработки (алерты
обработке не мешают; сетевой сбой или битый архив — дельта не помечена и
переигрывается следующим прогоном — идемпотентность по NOR/contentHash делает
переигрывание безопасным). Дни без утренней дельты (понедельники, после
праздников) — норма, не сбой. Планировщик в интеграционных тестах не
взводится — правило `createIntTestApp` уже действует. Дополнение data-model
(§ 4) на таблицу `JorfDelta` — правкой `docs/research/data-model.md` в фазе
схемы.

> **Исправлено при реализации (фаза 1, issue #98; отмечено по ревью PR 110).**
> «Переигрывается следующим прогоном» описывает дельту, но не очередь: сбой на
> одной дельте прогон не останавливает, и за прогон берётся не больше
> `MAX_DELTAS_PER_RUN` дельт. Почему именно так — у обоих решений в
> `apps/api/src/jorf/jorf-monitor.service.ts`.

### Рассылка: outbox на VeilleNotification

**Решение:** `VeilleNotification.sentAt` становится **nullable** —
outbox-паттерн: строки создаются в той же транзакции, что запись
арретé/entries (по одному на пару veille × арретé, только в notify-режиме),
отправка идёт вторым шагом и проставляет `sentAt`; каждый прогон сначала
досылает строки с `sentAt: null`.
**Почему:** это та самая «очередь отправки», отложенная в
`docs/research/emails.md` до фичи монитора, — без Redis и новых сервисов.
Вставка-до-отправки не теряет письмо при сбое (строка остаётся pending и
досылается следующим прогоном ≤ 12 ч — лаг ТЗ § 6 соблюдён), а
`unique(veilleId, arreteId)` держит «ровно одно письмо» на уровне БД при
ретраях и rectificatifs. Сбой одного получателя — `try/catch` вокруг каждого
`MailService.send()`, остальные уходят (ТЗ § 6).
**Отброшено:** очередь на BullMQ/Redis — новый инфраструктурный сервис ради
потока в единицы писем в сутки; «отправить, потом записать» — сбой между
отправкой и записью терял бы факт отправки и дублировал письмо, а сбой
отправки при уже записанной строке (вариант «записать с sentAt сразу») терял
бы письмо молча — хуже обоих.
**Как применять:** получатели — fan-out `VeilleCommune(codeInsee)` по кодам
entries арретé **плюс** подписчики влившихся коммун через итеративный резолв
`successorCodeInsee` (data-model § 3, только на чтении); только подтверждённые
(`confirmedAt != null`). Одно письмо на (veille, арретé) перечисляет все его
коммуны наблюдателя с их исходами; для reconnu — срок déclaration из
`DeadlineRule` (резолв по `publishedAt`), для refusé — прямой текст отказа без
срока. Сборка — тем же каркасом, что письма veille: блочная модель,
`fr.mail.jorf…` в `src/i18n/fr.ts`, `unsubscribePath` с токеном подписки.
Правка `VeilleNotification` в data-model § 6 — тем же коммитом фазы схемы.

> **Исправлено при реализации (фаза 3, issue #106; отмечено по ревью PR 112).**
> Досылка идёт **дважды за прогон** — до ingest и после него: письмо о найденном
> арретé уходит в тот же прогон, а не через 12 ч (ТЗ § 6, «в день обнаружения»).
> Строку, отправка которой сбойнула, вторая досылка не переигрывает — ретрай
> принадлежит следующему прогону. Прочее, что удерживает код и чего здесь нет:
> шаг досылки изолирован от ingest, состав подписчиков читается в транзакции
> ingest, токен отписки ротируется под конкретное письмо, а строка, падающая
> раз за разом, становится алертом `NOTIFICATION_STUCK`. Почему именно так — в
> `apps/api/src/jorf/jorf-monitor.service.ts`.

### Бэкфилл с 01.01.2026

**Решение:** отдельный скрипт `ts-node` без Nest-контекста (образец —
`prisma/seed.ts` и обоснование в `docs/research/commune-referential.md`),
использующий те же классы монитора с флагом `notify: false`: дельты
`JORFSIMPLE_2026*` с `JORFSIMPLE_20260101-000000` по текущую, фильтр
арретé — `DATE_PUBLI >= 2026-01-01`.
**Почему:** дельты сейчас лежат с 13.07.2025 (проверено 18.08.2026) — полный
дамп Freemium (1,0 ГБ) не нужен; `notify: false` означает «строки
`VeilleNotification` не создаются вовсе», поэтому ни бэкфилл, ни последующие
штатные прогоны не разошлют старьё: повторная встреча NOR без изменений — это
только `lastSeenAt` (критерий PRD «бэкфилл не отправляет ни одного письма»
держится конструкцией, не проверкой даты).
**Как применять:** прогресс — та же таблица `JorfDelta`, прерванный бэкфилл
продолжает с недообработанной дельты; обработанные бэкфиллом дельты штатный
монитор не переигрывает. Скрипт и штатный тик взаимно исключаются арендой
`MonitorLock`: скрипт держит её на весь прогон, и тик живого приложения,
который иначе заингестил бы недообработанные исторические дельты с
`notify: true`, пропускает себя; занятую аренду скрипт не перехватывает, а
просит подождать конца тика.

### Алерты администратору: таблица + email

**Решение** (владелец, 18.08.2026): новая таблица **`MonitorAlert`** (id,
`kind` enum: `UNPARSEABLE_ANNEXE` / `UNMATCHED_COMMUNE` / `OUTCOME_CHANGED`,
`detail` text, `arreteId` uuid null, `createdAt`) + письмо на новую
переменную окружения `ADMIN_EMAIL` через существующий `MailService`.
**Почему:** строка пишется в той же транзакции, что породившая её обработка, —
алерт не теряется даже при сбое почты (требование PRD «нельзя потерять
молча»), а «возникновение проверяемо тестом» — это буквально строка в таблице;
email — push-канал поверх. Ноль новых зависимостей.
**Отброшено:** только email — сбой отправки теряет алерт молча;
Sentry/GlitchTip — внешний сервис и SDK ради трёх типов доменных событий,
которые не являются ошибками приложения.
**Как применять:** сбой отправки алертного письма логируется и не прерывает
прогон (pending-алерты видны в таблице; ретрай письма не строим — разбор
руками и так начинается с таблицы). В `detail` — идентификаторы (NOR,
`communeLabelRaw`, имя дельты), никогда — email наблюдателей (ТЗ § 7).
Rectificatif-Z-текст и нераспознаваемая annexe — один kind
`UNPARSEABLE_ANNEXE` с разным `detail`. Таблица — дополнение data-model,
правкой документа в фазе схемы.

### DeadlineRule: срок déclaration

**Решение:** seed-запись (тем же механизмом `prisma db seed`, что справочник
коммун):

| поле             | значение                                                              |
| ---------------- | --------------------------------------------------------------------- |
| code             | `DECLARATION_ASSUREUR`                                                |
| duration / unit  | 30 / `DAYS`                                                           |
| anchor           | `DATE_PUBLICATION_ARRETE`                                             |
| effectiveFrom    | 2023-01-01                                                            |
| sourceUrl        | https://www.legifrance.gouv.fr/codes/article_lc/LEGIARTI000006792617/ |
| sourceVerifiedAt | 2026-08-18                                                            |

**Источник** (проверено 18.08.2026, дословно по действующей редакции):
article **L125-2 Code des assurances** — «…dès qu'il en a eu connaissance, et
au plus tard **trente jours après la publication de l'arrêté** de
reconnaissance de l'état de catastrophe naturelle». Срок 30 дней введён
loi n° 2021-1837 du 28.12.2021 (art. 6), в силе с 01.01.2023 (до того —
10 дней в clauses types); редакция от 28.05.2026 (loi n° 2026-403) клаузу не
меняла. Отсчёт — от даты публикации арретé в JO (не от «узнал»), что совпадает
с якорем `DATE_PUBLICATION_ARRETE`. Для sécheresse отдельного срока нет.

### Фикстуры тестов парсера

**Решение:** реальные XML из выгрузок DILA (ТЗ § 9) кладутся рядом со спеками
модуля `src/jorf/`: полный арретé 12.06.2026 (`JORFTEXT000054245373.xml`,
604 КБ, обе annexes) + оглавление его номера; краевые случаи (нераспознаваемая
структура, Z-rectificatif, пустая ячейка «Nombre de reconnaissances») —
минимальные производные от реального файла с сохранением его структуры.
**Почему:** 604 КБ в git терпимы и дают тест «оба приложения» на настоящей
структуре; краевые случаи в природе редки — их фикстуры честнее собирать из
реального образца, чем ждать живого сбоя.

## Ограничения и риски

- **Глубина дельт привязана к регенерации Freemium**: дельты хранятся с даты
  генерации текущего полного дампа (сейчас — 13.07.2025). Если DILA
  перегенерирует Freemium до реализации бэкфилла и дельты начнутся позже
  01.01.2026, бэкфиллу придётся читать полный дамп JORFSIMPLE (1,0 ГБ)
  потоково — тот же парсер, другой источник файлов. Проверить листинг на дату
  реализации.
- **Annexe I тоже несёт «Motivations de la décision»** — докблоки contracts
  (`ArreteEntry.motivation`) и data-model § 4 говорят «только для REFUSE».
  Решение: сохранять мотивацию для обеих annexes (доказательный текст, терять
  незачем), докблок contracts и data-model поправить в фазе схемы — по правилу
  «отступление — правкой самой модели».
- **Историческая структура таблиц не гарантирована**: колонки проверены на
  арретé 2026 года; бэкфилл идёт с 01.01.2026, но внутри года формат мог
  плавать. Несопоставившаяся шапка деградирует в алерт, не в тихий пропуск, —
  ровно для этого он и есть.
- **Мониторинг молчания источника не строится**: «дельт нет» — норма для
  понедельников и праздников, а долгий сбой echanges.dila.gouv.fr монитор сам
  не распознаёт. Еженедельная сверка с GASPAR (отдельная итерация вне этого
  PRD) — та страховка, которая это молчание поймает.
- **`NUM_PARUTION` и `ORIGINE_PUBLI`** наблюдались заполненными во всех
  проверенных текстах; `signedAt` берётся из `<DATE_TEXTE>`. Пустое любое из
  обязательных полей (`NOR`, `DATE_PUBLI`) — текст не пишется, алерт
  `UNPARSEABLE_ANNEXE` с детальностью «метаданные».
- **Пре-1987 «NOR technique»** (`LGFX…`) в скоупе не встретится (бэкфилл с
  2026), но парсер NOR не должен на нём падать — просто не пройдёт отбор.
- Тексты приходят повторно (обогащение вечерней дельтой) — любой код после
  парсинга обязан быть идемпотентным; это уже заложено в NOR/contentHash и
  outbox, новых механизмов не требуется.
