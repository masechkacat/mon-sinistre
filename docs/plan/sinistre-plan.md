**Research**: docs/research/sinistre-plan.md

## Фаза 1: Синистр создаётся и отдаёт план (Tracer Bullet)

**Цель:** сквозной путь contracts → база → API: человек создаёт синистр и
получает копию плана — шаги первых дней с датами, шаги поздних якорей без дат,
но со сроком и ссылкой на норму. Без привязки arrêté и без писем.
**Затрагивает:** contracts, db, api
**Задачи:**

- [ ] Contracts: enum `RisqueCatnat` (шесть значений), три новых значения
      `StepAnchor` (`DATE_ETAT_ESTIMATIF`, `DATE_ETAT_ESTIMATIF_OU_EXPERTISE`,
      `DATE_ACCORD_INDEMNISATION`), `StepTemplate.offsetDays` → nullable,
      `Sinistre.risque` → `RisqueCatnat`, `SINISTRE_PATH = '/sinistres'`.
      **Проверяется тестами (до кода):** `npm run build:contracts` — API и web
      собираются против нового типа `risque`; спека `stepStatus` фазы (ниже)
      компилируется с шагом без `offsetDays`.
- [ ] Миграция `Sinistre`, `Step`, `StepTemplate` по data-model §§ 3, 5 +
      enum'ы Prisma `SinistreStatus`, `StepPersistedStatus` (**только** `FAIT`
      и `NON_APPLICABLE`), `RisqueCatnat`; `StepTemplate.offsetDays` nullable и
      новый `deadlineRuleCode`; `unique(planKey, "order")` — SQL руками.
      Индексы `Sinistre(codeInsee, status)` и частичный
      `Step(plannedDate) where persistedStatus is null` **не создаются** — их
      заводят те фазы, что пишут их запросы. Правка `docs/research/data-model.md`
      (§ 3 — три формы шага шаблона, отложенный индекс) — тем же коммитом.
      **Проверяется тестами (до кода):** schema int-spec — каскад
      `User → Sinistre → Step`, restrict на `Step.deadlineRuleId` и
      `Sinistre.arreteEntryId` (удаление справочной строки под досье не
      проходит), отказ дубля `(planKey, order)`, шаг с пустыми `offsetDays` и
      `deadlineRuleCode` сохраняется.
- [ ] Справочник и его резолв: `seedStepTemplates(prisma)` рядом с
      `seedDeadlineRules` (13 шагов `planKey = 'CATNAT'` по таблице research,
      французские тексты в базе), пять правил сроков страховщика в
      `seedDeadlineRules` (article L125-2, `effectiveFrom` по сверенной
      редакции — research), вынос запроса из приватного
      `JorfMonitorService.loadDeclarationRule` в
      `DeadlineRuleService.resolveActive(code, anchor, onDate)`
      (`src/deadline-rules/`), монитор зовёт его **до** открытия транзакции
      ingest. **Проверяется тестами (до кода):** оба seed идемпотентны при
      повторном запуске; ни один текст шага не содержит юридического числа
      (шаг несёт либо `offsetDays`, либо `deadlineRuleCode`, либо ничего);
      `resolveActive` отдаёт строку, действующую на дату, и **бросает**, когда
      действующей нет; существующие int-spec монитора остаются зелёными.
- [ ] Чистые функции чтения плана (`src/sinistres/`, `src/common/`):
      `todayInParis()` в `src/common/time/` (`Intl.DateTimeFormat('en-CA')`,
      без зависимостей), `anchorDatesOf(sinistre)` — `DATE_DECLARATION` даёт
      **max(дата декларации, дата публикации)** и не даёт ничего без одной из
      них, `stepStatus(step, today)`, `toSourceReference(url, verifiedAt,
      today)` с первой реализацией `possiblyOutdated` через `resolveDeadline` и
      `REFERENCE_DATA_STALE_AFTER_MONTHS`. **Проверяется тестами (до кода):**
      `plannedDate === null` → `A_VENIR` (ни в просроченных, ни в ближайших,
      критерий PRD № 16); `persistedStatus` перекрывает вычисление; границы
      `SOON_THRESHOLD_DAYS` и `plannedDate < today` (критерий № 15); якорь
      декларации при декларации раньше публикации и при `declarationDate = null`
      с опубликованным arrêté; `possiblyOutdated` на дате ровно шестимесячной
      давности и на 31 августа (конец месяца).
- [ ] Модуль `src/sinistres/`: `POST /sinistres` (`{ codeInsee, risque,
      eventDate }` → 201 `SinistreDetail`) и `GET /sinistres/:id`; копия плана
      из `StepTemplate` в `Step` тянет `anchor`, `offsetDays`,
      `deadlineRuleId` и `sourceUrl`/`sourceVerifiedAt` — правило резолвится
      **всегда**, в том числе когда якорь неразрешим (тогда на дату создания);
      DTO с `IsoDate` (`@ApiProperty({ type: String, format: 'date' })`) и
      французским сообщением из `src/i18n/fr.ts` на дату в будущем. Ресурс под
      глобальным `JwtAuthGuard`, чтение — `findFirst({ where: { id, userId } })`.
      **Проверяется тестами (до кода):** int-spec — созданный синистр отдаёт
      шаги якоря `DATE_SINISTRE` с датами и шаги `DATE_PUBLICATION_ARRETE` /
      `DATE_DECLARATION` без `plannedDate`, но со сроком и `SourceReference`
      (критерий PRD № 2); дата события завтрашним днём — 400 с французским
      текстом (критерий № 1); правка `StepTemplate` после создания не меняет
      шаги существующего синистра (критерий № 17); статус нового синистра —
      `AVANT_ARRETE`.

**Когда готова:** int-spec «синистр, созданный до публикации arrêté, отдаёт
план: шаги первых дней с датами, шаги поздних якорей без дат и со ссылкой на
норму» зелёный; `npm run lint && npm test && npm run test:int` проходят.

## Фаза 2: Список, отметки шагов, дата декларации, удаление

**Цель:** досье живёт: пострадавший видит свои синистры, отмечает шаги,
вписывает дату декларации и получает шаги, отсчитываемые от неё, удаляет
ненужное. Чужое досье неотличимо от несуществующего.
**Затрагивает:** api
**Задачи:**

- [ ] `GET /sinistres` → `SinistreSummary[]` (только свои, свежие сверху) и
      `DELETE /sinistres/:id` → 204. **Проверяется тестами (до кода):**
      int-spec — список второго пользователя не показывает чужие синистры;
      удаление сносит шаги (каскад); чужой и несуществующий `id` дают
      одинаковый 404 с тем же телом (критерий PRD № 19); удаление аккаунта с
      синистром проходит и не падает на внешнем ключе (критерий № 20).
- [ ] `PATCH /sinistres/:id/etapes/:stepId` — `{ status: 'FAIT' |
      'NON_APPLICABLE' | null }` → `StepResponse`; запись через
      `updateMany({ where: { id: stepId, sinistre: { id, userId } } })` с
      `count === 0` → 404. **Проверяется тестами (до кода):** отмеченный шаг
      перестаёт числиться предстоящим, остальные шаги не меняются (критерий
      PRD «отметка шага»); снятие отметки возвращает вычисленный статус; шаг
      чужого синистра — 404, и чужой шаг не изменился.
- [ ] `PATCH /sinistres/:id` — `{ declarationDate: IsoDate | null }`; статус
      назначает единственная чистая функция `sinistreStatus(link,
      declarationDate)` (дата задана → `DECLARE`; иначе `ARRETE_PUBLIE` /
      `ARRETE_REFUSE` по привязке, без привязки — `AVANT_ARRETE`), шагам якоря
      `DATE_DECLARATION` проставляется `plannedDate`. **Проверяется тестами
      (до кода):** указание даты переводит в `DECLARE` и даёт даты шагам якоря,
      очистка убирает их и возвращает статус (критерий PRD № 18); очистка у
      непривязанного синистра даёт `AVANT_ARRETE`, а не `ARRETE_PUBLIE`; дата
      декларации раньше публикации не сдвигает срок ответа страховщика раньше
      законного.

**Когда готова:** критерии PRD № 18–20 и «отметка шага» зелёные в int-spec;
все шесть эндпоинтов ресурса отвечают, `/docs` показывает `IsoDate` как
`format: 'date'`.

## Фаза 3: Привязка arrêté к синистру

**Цель:** синистр получает юридические сроки сам: монитор привязывает entry к
уже заведённым досье, а досье, заведённое по письму-уведомлению, привязывается
к уже загруженному arrêté в момент создания. Без писем — они в фазе 4.
**Затрагивает:** api, db
**Задачи:**

- [ ] `classifyRisques(label): Set<RisqueCatnat>` в `src/jorf/parse/` — свёртка
      восьми официальных категорий в шесть, нормализация через существующий
      `normalizeCommuneName` (второй реализации не заводить; строка таблицы
      «Единственные точки входа» в `apps/api/CLAUDE.md` переписывается на
      «нормализация названия (коммуна, phénomène)» тем же коммитом); пустое
      множество → `MonitorAlert(UNPARSEABLE_ANNEXE)` один раз на (arrêté,
      метка). **Проверяется тестами (до кода):** формулировки из фикстур
      `test/fixtures/jorf/` (ТЗ § 9) — «Inondations et coulées de boue»,
      «Inondations par remontée de nappe phréatique», «Inondations, coulées de
      boue et mouvements de terrain» (два значения); формулировка про
      «différentiels consécutifs à la sécheresse» даёт **только** `SECHERESSE`,
      несмотря на «mouvements de terrain» в тексте; выдуманная метка даёт
      пустое множество и ровно один алерт на повторе.
- [ ] `matchSinistres(entries, sinistres, successorOf): Link[]` в
      `src/sinistres/` — чистая функция, кандидаты «все непривязанные плюс
      привязанные к `ARRETE_REFUSE`», совпадение по форвардному резолву обеих
      сторон (`resolveCurrentCode` из `src/jorf/recipients/` экспортируется, не
      переписывается), `sinistre.risque ∈ classifyRisques(entry.risque)` и
      `eventStart ≤ eventDate ≤ eventEnd`. **Проверяется тестами (до кода):**
      arrêté по другому риску той же коммуны с подходящим периодом синистр не
      трогает (критерий PRD № 7); синистр влившейся коммуны находит arrêté
      преемника (критерий № 8); из нескольких подходящих entries побеждает
      `RECONNU`, среди нескольких `RECONNU` — самый ранний `publishedAt`
      (критерий № 9); код, у которого резолв дал `null`, не совпадает ни с чем;
      дата события на день раньше `eventStart` не совпадает.
- [ ] Привязка при создании синистра: `SinistresService.create` зовёт
      `matchSinistres` по уже загруженным arrêtés, проставляет `arreteEntryId`,
      `plannedDate` шагам якоря `DATE_PUBLICATION_ARRETE` и `deadlineRuleId` по
      правилу, действующему на **дату публикации**; статус — через
      `sinistreStatus`. **Проверяется тестами (до кода):** синистр, созданный
      после публикации, привязывается при создании и получает дедлайн от даты
      публикации, а не от даты создания; истёкший срок показывается
      просроченным (критерий PRD № 5); дедлайн от публикации 31 января и в
      високосном феврале — календарная дата, а не +30 суток (критерий № 4);
      `REFUSE`-entry даёт `ARRETE_REFUSE` без дедлайна декларации (критерий
      № 6); дедлайн равен `publishedAt` + длительность действующего правила
      (критерий № 3).
- [ ] Привязка на прогоне монитора: `JorfMonitorService` после ingest зовёт ту
      же функцию для уже заведённых синистров, правило `DeadlineRule` резолвит
      снаружи транзакции и передаёт внутрь. **Проверяется тестами (до кода):**
      int-spec — прогон по дельте-фикстуре переводит синистр в `ARRETE_PUBLIE`
      и даёт шагам даты; повторный прогон той же дельты не создаёт второй
      привязки (критерий PRD № 11); синистр в `ARRETE_REFUSE` при arrêté с
      новым NOR, признавшим его коммуну, уходит в `ARRETE_PUBLIE` с дедлайном
      от новой даты публикации (критерий № 10); синистр в `DECLARE`,
      привязанный прогоном, остаётся `DECLARE`.

**Когда готова:** критерии PRD № 3–11 (кроме письма) зелёные в int-spec; ни
одного захардкоженного срока — все даты пришли из `DeadlineRule`.

## Фаза 4: Письмо владельцу синистра

**Цель:** человек узнаёт о признании своей коммуны в день публикации — письмом
с датой дедлайна; наблюдатель, подписанный на ту же коммуну, получает по
одному arrêté ровно одно письмо.
**Затрагивает:** api, db
**Задачи:**

- [ ] Миграция `SinistreNotification` — форма `VeilleNotification` (`sentAt`
      nullable, `attempts`) плюс `kind` (`PUBLICATION` /
      `RECTIFICATIF_RECONNU`) в ключе `unique(sinistreId, arreteId, kind)`;
      каскад `Sinistre → SinistreNotification`, restrict на `arreteId`.
      Правка `docs/research/data-model.md` § 5 — тем же коммитом. **Проверяется
      тестами (до кода):** schema int-spec — две строки одного (sinistreId,
      arreteId) с разными `kind` проходят, с одинаковым — нет; удаление
      синистра сносит строки, удаление arrêté под строкой не проходит.
- [ ] Вынос цикла досылки в `src/jorf/mail/drain-outbox.ts` («взять pending →
      сгруппировать по arrêté → try/catch на получателя → отметить или
      посчитать попытку», счётчик `attempts`, алерт `NOTIFICATION_STUCK`),
      параметризованный адаптером; veille-outbox переключается на него.
      **Проверяется тестами (до кода):** существующие int-spec рассылки veille
      остаются зелёными без правок ожиданий; сбой на первом получателе не
      прерывает остальных, недоставленное уходит следующим прогоном.
- [ ] Композитор `src/jorf/mail/sinistre-arrete-mail.ts` рядом с
      `veille-arrete-mail.ts`: тот же блочный каркас, ветка `fr.mail.jorf…`,
      ссылка на экран синистра из `FRONTEND_URL` + `SINISTRE_PATH`,
      `unsubscribePath` — `ACCOUNT_MAIL_UNSUBSCRIBE_PATH` (письмо
      транзакционное, ротации токена подписки нет). **Проверяется тестами (до
      кода):** спека сборки — письмо называет коммуну, риск, дату публикации и
      дату дедлайна из правила; отписка ведёт на транзакционный обработчик, не
      на отписку veille; в письме нет чужих адресов.
- [ ] Постановка в outbox в транзакции ingest и отправка вторым шагом;
      дедупликация с veille — **на отправке и по коммунам**: из списка коммун
      veille-письма вычитаются те, о которых этому же адресу сказано письмом
      синистра по тому же arrêté (чистая функция рядом с `resolveRecipients`),
      пустой остаток — письмо не уходит, строка сразу получает `sentAt`.
      Синистр, привязанный при создании, письма не получает. **Проверяется
      тестами (до кода):** int-spec — письмо уходит в тот же прогон, что привязал
      entry, сбой одному получателю не прерывает остальных (критерий PRD № 13);
      владелец, подписанный в veille на ту же коммуну, получает ровно одно
      письмо, а про вторую свою коммуну — по-прежнему узнаёт (критерий № 14);
      повторный прогон второго письма не шлёт (критерий № 11); синистр,
      привязанный при создании, писем не порождает.

**Когда готова:** критерии PRD № 11, 13, 14 зелёные в int-spec; оба письма
проверены глазами в `.mail-outbox` (текст и HTML).

## Фаза 5: Пересчёт при rectificatif

**Цель:** исправление arrêté доходит до досье: сроки, назначенные по прежним
данным, пересчитываются, коммуна, добавленная rectificatif, привязывается и её
пострадавший получает письмо, а всякое изменение чужих сроков видит
администратор.
**Затрагивает:** api, db
**Задачи:**

- [ ] `MonitorAlertKind` += `LINKED_ENTRY_CHANGED` (миграция + правка
      `docs/research/data-model.md` § 4 тем же коммитом). **Проверяется тестами
      (до кода):** schema int-spec — алерт нового вида вставляется и переживает
      удаление arrêté по существующему правилу.
- [ ] Пересчёт в `applyRectificatif`: по привязанным синистрам тронутых
      entries — статус по новому `outcome`, `plannedDate` шагов якоря
      `DATE_PUBLICATION_ARRETE` по новой `publishedAt`, а для уже
      задекларированного синистра и шагов якоря `DATE_DECLARATION`, который
      равен `max(декларация, публикация)`; правило `DeadlineRule` резолвится
      заново на новую дату, **до** открытия транзакции. Каждое изменение
      поднимает `LINKED_ENTRY_CHANGED`. Синистр, переставший подходить по
      риску, периоду или переставшей резолвиться коммуне, **не отвязывается**
      — только алерт, называющий причину. **Проверяется тестами (до кода):**
      int-spec на фикстуре rectificatif — `REFUSE → RECONNU` переводит в
      `ARRETE_PUBLIE` и назначает дедлайн, изменённая дата публикации
      пересчитывает `plannedDate` шагов обоих якорей (критерий PRD № 12);
      обратный переход `RECONNU → REFUSE` снимает дедлайн и не шлёт письма;
      ставший неподходящим синистр остаётся привязанным и даёт алерт.
- [ ] Привязка синистров к добавленным и исправленным entries: rectificatif
      только помечает свои строки, `matchSinistres` по ним делает общий проход
      `linkSinistres` в конце прогона — победитель выбирается по всем entries
      окна, иначе поздний rectificatif обошёл бы arrêté с более ранней
      публикацией и дедлайн уехал бы вперёд. Новая привязка по помеченной
      строке и переход `REFUSE → RECONNU` пишут `SinistreNotification` с
      `kind = RECTIFICATIF_RECONNU`. **Проверяется тестами (до кода):** int-spec
      — синистр коммуны, добавленной rectificatif, привязывается и получает
      письмо; arrêté, опубликованный раньше в том же прогоне, забирает
      привязку и дедлайн считается от его даты; повторный прогон того же
      rectificatif второго письма не шлёт; отобранное признание письма не
      порождает.

**Когда готова:** критерий PRD № 12 зелёный; ни одно изменение привязанного
entry не проходит без `MonitorAlert`.

## Фаза 6: Web — список синистров и создание

**Цель:** пострадавший заводит синистр в браузере: находит коммуну, выбирает
риск словами, указывает дату события — и видит свои досье списком из личного
кабинета.
**Затрагивает:** web
**Задачи:**

- [ ] Слой запросов `src/lib/api/sinistres.ts` + ключи в `keys.ts` (все вызовы

## Фаза 7: Web — экран синистра

**Цель:** экран досье отвечает на единственный вопрос человека в стрессе — что
и когда сделать: хронология с ближайшим шагом, остаток критического срока
числом дней, отметка сделанного, дата декларации.
**Затрагивает:** web
**Задачи:**

- [ ] `/sinistres/[id]` — хронология семантическим `<ol>`: дата, статус
      **текстом**, ближайший предстоящий шаг с `aria-current="step"`, остаток
      срока отдельной строкой «Il reste N jours» (число приходит от API),
      просрочка словами; шаг без даты объясняет, чего он ждёт. Даты — только
      `formatDateFr`, подписи статусов — `fr.ts`, пороги — из contracts.
      **Проверяется тестами (до кода):** просроченный шаг назван словами, а не
      только цветом (критерий PRD № 21); шаг без `plannedDate` не выглядит ни
      просроченным, ни ближайшим; ровно один элемент несёт `aria-current`.
- [ ] Расчётная дата подаётся как ориентировочная: ссылка на норму своего
      правила, пометка «источник давно не сверялся» при `possiblyOutdated`,
      предложение сверить с договором страхования. **Проверяется тестами (до
      кода):** каждая расчётная дата на экране сопровождается ссылкой на
      источник; устаревшее правило даёт пометку текстом (критерий PRD № 22).
- [ ] Отметка шага выполненным и неприменимым, снятие отметки — `useMutation` с
      инвалидацией ключа синистра, результат объявляется в заранее
      смонтированном `role="status"`. **Проверяется тестами (до кода):**
      отметка объявляется скринридером и не перерисовывает остальные шаги;
      ошибка мутации возвращает прежнее состояние с французским сообщением.
- [ ] Дата декларации страховщику (указание и очистка) и удаление синистра с
      подтверждением: модальное окно с focus trap, `Escape` и возвратом фокуса.

      отсчитываемые от неё, очистка их убирает; отмена удаления возвращает
      фокус на кнопку.

**Когда готова:** критерии PRD № 21, 22 зелёные; страница проходит axe в обеих
