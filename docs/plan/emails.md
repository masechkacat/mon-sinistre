# Plan: Письма приложения

**PRD**: docs/prd/emails.md
**Research**: docs/research/emails.md (написан 03.08.2026). Технические решения
(почтовый провайдер в ЕС и способ обращения к нему, механизм локализации в
`apps/api`, способ доставки писем разработчику в локальном режиме, шаблонизация
text + HTML) приняты там; задачи ниже их применяют, а не перевыбирают. Там, где
реализация отступила от отчёта, действует врезка «Исправлено при реализации» в
самом отчёте.
**Дата**: 2026-08-03

Фича целиком серверная: письма собирает и отправляет `apps/api`. Страницы, на
которые ведут ссылки из писем, принадлежат фичам-владельцам писем (veille,
монитор JO, напоминания синистра) — в этом плане их нет, поэтому фазы web
отсутствуют. `packages/contracts` эта фича не меняет: текстов для пользователя
в нём не бывает, а типы каркаса письма наружу не выходят.

## Ограничение research: без новых зависимостей

Фазы 1 и 2 задуманы как автономные для Ralph Loop, а он зависимости не ставит:
`npm install`, `npx`, `npm exec` и правка `package.json` не входят в
`allowedTools` (`.claude/ralph.config.json`), а `npm run db:up` поднимает только
сервис `db` — новый контейнер в docker-compose цикл тоже не запустит. Поэтому
решения research по провайдеру и по локальному транспорту выбираются так, чтобы
не требовать ни новой npm-зависимости, ни нового сервиса в docker-compose:
образец — `GeoApiClient` (нативный `fetch` Node 24 с `AbortSignal.timeout`,
fetch-функция передаётся через конструктор). Если лучшее решение зависимость всё
же требует — это допустимо, но тогда research-отчёт обязан сказать об этом
прямо: установку выполняет владелец вручную **до** фазы, и фаза перестаёт быть
автономной.

## Владелец пути «прекратить получение писем»

Каркас принимает путь входным параметром, но сам путь — один факт, нужный и
`apps/api` (сборка абсолютного URL), и `apps/web` (роут страницы). Объявляет его
константой в `packages/contracts` фича-владелец письма — для veille в той её
фазе, где появляется страница отписки; каркас писем константу только использует.
Двух литералов пути в репозитории быть не должно: расхождение тихо ломает
обязательную ссылку, а тест каркаса этого не увидит — он проверяет наличие
ссылки, а не её достижимость.

## Ручные действия и issues

Все ручные действия владельца собраны в блоке «Предусловия (владелец)» фазы 3 и
в списке задач не значатся: скилл `issues` заводит issue на каждую задачу плана
и пометку «вручную» не разбирает, а Ralph Loop берёт из milestone все открытые
issues. Задачи фаз выполняются автономно; фиксация результата ручной проверки
(фаза 3) опирается на данные, которые владелец оставляет в комментарии к issue —
см. предусловия.

## Тесты не выделены в отдельную задачу

Проверки названы внутри той задачи, поведение которой подтверждают, и пишутся до
кода в её же сессии. Отдельной задачи «Тесты» в фазах нет намеренно: она
означала бы коммит с одними красными тестами, а pre-commit прогоняет `npm test`
и такой коммит не пропускает — задача оказалась бы невыполнимой (первая редакция
этого плана на ней и застряла, `docs/decisions.md`, 03.08.2026).

## Вне скоупа, владелец не назначен

Лимит «не больше одного письма пользователю в день» (`apps/api/CLAUDE.md`) и
счётчик писем на адрес, переживающий рестарт (`docs/decisions.md`, 02.08.2026),
этим PRD не покрываются: «настройки частоты писем» вынесены из скоупа. Владельца
требования определяет PRD veille. Единая точка отправки из фазы 1 — естественное
место для такого лимита, когда владелец появится; закладывать его сейчас не
нужно, потерять из виду — нельзя.

## Фаза 1: Каркас письма и локальная доставка (Tracer Bullet)

**Цель:** любой модуль API может отправить письмо одним вызовом и получить
собранное письмо с темой, отправителем, текстовой и HTML-версией, французским
подвалом и ссылкой прекращения писем (она же — в заголовке `List-Unsubscribe`);
при локальном запуске письмо не уходит наружу, а его текст и ссылки доступны
разработчику. Реального провайдера ещё нет — он в фазе 2.
**Затрагивает:** api

**Задачи:**

- [ ] Механизм локализации `apps/api`: французские строки каркаса и подвала в
      файле локализации, не в коде сервиса; в `packages/contracts` текстов нет.
      Административные термины в подвале объясняются простыми словами (§
      «Ограничения» PRD). Способ — по research-отчёту.
- [ ] Каркас письма: сборка темы, отправителя, text- и HTML-версии из общего
      шаблона с подвалом. Ссылка прекращения писем — обязательный вход сборки
      (тип не даёт её опустить, отсутствие проверяется и на рантайме); её текст
      и подпись — в локализации, целевой путь задаёт вызывающая фича (константой
      в contracts — см. «Владелец пути» выше). Абсолютный адрес из пути собирает
      сам каркас, из базового адреса в конфигурации (`FRONTEND_URL`, читается
      через `ConfigService`) — второй склейки базы по фичам не заводить. Раз
      ссылка обязательна, обязательна и переменная: ужесточить `FRONTEND_URL` в
      `src/config/env.validation.ts` (сейчас `@IsOptional`) до непустого
      абсолютного URL и поправить `.env.example` тем же коммитом — иначе адрес
      соберётся как `undefined/…`, а тест «ссылка есть» этого не заметит. Ту же
      ссылку каркас кладёт в заголовки `List-Unsubscribe` и
      `List-Unsubscribe-Post: List-Unsubscribe=One-Click`: они работают на
      доставляемость фазы 3 и стоят одной строки, раз URL уже посчитан.
      **Проверяется тестами (до кода):** собранное письмо содержит тему, адрес и
      имя отправителя, непустые текстовую и HTML-версии; множество ссылок в
      текстовой версии совпадает с множеством ссылок в HTML; текстовая версия не
      содержит HTML-тегов и HTML-сущностей, а ссылки в ней даны полным URL,
      собранным от `FRONTEND_URL`; подвал каждого письма содержит объяснение,
      почему письмо пришло, и ссылку прекращения писем (ими же подтверждается,
      что французские строки берутся из локализации); та же ссылка попадает в
      заголовки `List-Unsubscribe` и `List-Unsubscribe-Post`; попытка собрать
      письмо без ссылки прекращения писем завершается ошибкой и отправки не
      происходит.
- [ ] `MailModule`/`MailService` с единственной точкой отправки, которой
      пользуются все фичи продукта: успех и отказ различимы вызывающим кодом
      (отказ — исключение, «тихий успех» невозможен), логирование через
      `Logger` с контекстом класса, без адреса получателя ни в успехе, ни в
      ошибке. Транспорт — зависимость за токеном (интерфейс `MailTransport` +
      провайдер через `useFactory`), а не ветвление по окружению внутри
      `MailService`: тесты обеих фаз подставляют транспорт через DI, а не через
      переменные окружения. Модуль глобальный, как `PrismaModule`, — его
      импортируют все фичи продукта. **Проверяется тестами (до кода):** email
      получателя не встречается ни в одной записи перехваченного `Logger` — ни
      при успешной отправке, ни на отказном пути (сборка без ссылки прекращения
      писем); отказ различим вызывающим кодом, «тихий успех» невозможен.
- [ ] Транспорт локального режима по research-отчёту: письмо не уходит на
      внешний адрес, его тема, обе версии тела, заголовки и ссылки попадают в
      канал, доступный и разработчику, и тесту. Отразить модуль, локализацию и
      локальный режим в `apps/api/CLAUDE.md` в том же коммите. **Проверяется
      тестами (до кода):** локальный транспорт не обращается к сети и записывает
      тему, обе версии тела, заголовки и ссылки в канал, который читает тест.

**Когда готова:** зелёные тесты «собранное письмо содержит тему, отправителя и
обе версии тела, множества ссылок в них совпадают», «письмо, собранное без
ссылки прекращения писем, не отправляется», «локальный транспорт не ходит в
сеть, а тема, обе версии тела и ссылки доступны из его канала» и «email
получателя отсутствует в перехваченных логах и при успехе, и при ошибке»; при
локальном запуске отправка тестового письма не идёт наружу, а его текст и ссылки
видны разработчику.

## Фаза 2: Провайдер отправки в ЕС

**Цель:** письма реально уходят через почтового провайдера, обрабатывающего
адреса в ЕС; отказ провайдера виден вызывающему коду и в логах; конфигурация
провайдера проверяется при старте приложения, не ломая локальную разработку.
**Затрагивает:** api

**Задачи:**

- [ ] Клиент провайдера, выбранного в research-отчёте: обращение через
      зависимость, переданную в конструктор (тесты мокают HTTP без nock/msw),
      явный таймаут; регион обработки — ЕС; переписывание ссылок провайдером
      (click- и open-tracking) выключено — иначе HTML-версия разойдётся с
      текстовой, а адреса получателей уедут в чужую аналитику. **Проверяется
      тестами (до кода, обращение к провайдеру замокано):** отказ провайдера
      (ошибка HTTP, таймаут, невалидный ответ) возвращается вызывающему коду как
      ошибка, а не как успех; факт отказа попадает в лог уровня `error` без
      адреса получателя и без тела письма.
- [ ] Переменные окружения почты: привести `.env.example` и
      `src/config/env.validation.ts` в соответствие с выбранным транспортом
      одним коммитом — неиспользуемые `SMTP_*` удалить, нужные добавить,
      комментарий «tighten them when the mail module lands» снять, а из
      `apps/api/CLAUDE.md` убрать ставшую неверной фразу «SMTP-переменные
      необязательны, пока нет модуля рассылки». Обязательные только при
      транспорте «провайдер» (`@ValidateIf`). Сюда же — домен отправителя, к
      которому фаза 3 сверяет `MAIL_FROM`. Секреты в логи и в тексты ошибок
      валидации не попадают. **Проверяется тестами (до кода):** валидация
      переменных провайдера условная — при транспорте «провайдер» неполная
      конфигурация валит приложение при bootstrap, а не при первой отправке, а в
      локальном режиме приложение стартует без них.
- [ ] Выбор транспорта по окружению: явная переменная транспорта читается один
      раз в `useFactory` провайдера транспорта, локальный режим из фазы 1
      остаётся умолчанием для разработки, провайдер включается конфигурацией.
      **Проверяется тестами (до кода):** выбор транспорта зависит от окружения —
      в локальном режиме провайдер не вызывается ни разу (транспорт
      подставляется через токен из фазы 1).
- [ ] Зафиксировать в документации, где обрабатываются адреса получателей
      (провайдер, регион ЕС, что именно ему передаётся, выключенный трекинг):
      запись в `docs/decisions.md` и раздел в `apps/api/CLAUDE.md` — в том же
      коммите.

**Когда готова:** интеграционно проверено на моке провайдера — успешная
отправка возвращает успех, ответ провайдера с ошибкой поднимает исключение и
пишет `error` в лог; ни в одном из двух случаев адреса получателя в логах нет;
приложение не стартует с пустой конфигурацией провайдера в режиме отправки и
стартует без неё в локальном режиме.

## Фаза 3: Домен отправителя и проверка доставки

**Цель:** письмо с собственного домена приходит во «Входящие» крупных почтовых
служб, а не в спам; результат проверки зафиксирован в документации.
**Затрагивает:** api / docs

**Предусловия (владелец, issues не заводятся):**

- Настроить аутентификацию домена у провайдера и дождаться подтверждения домена
  на его стороне: SPF и DKIM по инструкции провайдера **и DMARC** — политику
  DMARC минимальные инструкции провайдеров обычно не упоминают, а без неё письмо
  чаще всего и попадает в спам у Outlook.
- Отправить проверочное письмо каркасом фазы 1 на адрес Gmail и на адрес
  Outlook; убедиться, что оба пришли во «Входящие», что ссылки из текстовой
  версии кликабельны и что почтовый клиент показывает штатную кнопку отписки
  (заголовок `List-Unsubscribe` из фазы 1).
- Оставить исходные данные проверки комментарием к issue задачи «зафиксировать
  проверку в документации»: дата, домены-приёмники (домены, не сами адреса),
  результат по каждой службе, применённая политика DMARC. Пока комментария нет,
  issue в работу не берётся: результат непроведённой проверки в
  `docs/decisions.md` сочинять нельзя.

**Задачи:**

- [ ] Адрес отправителя — из конфигурации, а не из кода. **Проверяется тестами
      (до кода):** `MAIL_FROM` вне настроенного домена отправителя (переменная из
      фазы 2) отклоняется при старте приложения — страховка от опечатки в
      конфигурации, настоящую защиту от чужого домена даёт провайдер, отклоняя
      неверифицированный.
- [ ] Текст отказа провайдера несёт причину, а не только статус (замечание
      ревью фазы 2): причина берётся из тела ошибочного ответа по явному
      allowlist полей — перечислением, не «всё, кроме адреса»; остальное тело
      по-прежнему не читается. Запись `docs/decisions.md` о клиенте Scaleway TEM
      правится тем же коммитом: она фиксирует нынешнее «в текст ошибки попадают
      только статус и повод». **Проверяется тестами (до кода):** ответ с
      ошибкой, несущий в теле адрес получателя и фрагмент письма, не отдаёт ни
      того ни другого — ни в тексте исключения, ни в цепочке причин, ни в логе
      `MailService`; поле вне allowlist в текст не попадает; невалидный JSON в
      теле ошибочного ответа не ломает отчёт об отказе.
- [ ] Зафиксировать проверку в документации: перенести данные из комментария к
      issue в `docs/decisions.md` (дата, домены-приёмники, результат по каждой
      службе, политика DMARC); ссылку на запись — в `apps/api/CLAUDE.md`.

**Когда готова:** письмо с настроенного домена лежит во «Входящие» Gmail и
Outlook, почтовый клиент показывает штатную кнопку отписки, дата и результат
проверки записаны в `docs/decisions.md`; все критерии готовности PRD закрыты.

## Сверка с критериями готовности PRD

| Критерий PRD                                        | Фаза |
| --------------------------------------------------- | ---- |
| Тема, отправитель, text + HTML, совпадение ссылок   | 1, 2 |
| Объяснение «почему пришло» + ссылка прекращения     | 1 \* |
| Письмо без ссылки прекращения не собирается         | 1    |
| Email получателя отсутствует в логах (успех/ошибка) | 1, 2 |
| Локальный запуск: письмо не уходит, текст доступен  | 1    |
| Отказ провайдера — ошибка вызывающему коду и в логе | 2    |
| Тексты на французском в локализации, не в contracts | 1    |
| Доставка во «Входящие» Gmail и Outlook              | 3    |
| Обработчик в ЕС, зафиксировано в документации       | 2    |

\* Фаза 1 закрывает критерий наполовину: каркас обязывает каждое письмо нести
объяснение и ссылку прекращения писем. Вторая половина — «ссылка доступна без
аккаунта и без ввода данных» — свойство страницы за ссылкой, а она принадлежит
фиче-владельцу (PRD veille) и проверяется её критерием готовности, как и
требование «переход по ссылке сам по себе ничего не меняет».
