# Plan: Veille — подписка и отписка

**PRD**: docs/prd/veille-subscription-lifecycle.md
**Research**: docs/research/veille-subscription-lifecycle.md — **ещё не написан**,
пишется до фазы 1. Задачи с пометкой «по research-отчёту» применяют его решения,
а не перевыбирают их. За отчётом закреплены: формат и хеширование токенов
подтверждения и отписки, механизм удаления неподтверждённых подписок и записей
счётчика писем (фоновая задача или чистка при обращении), способ необратимого
хеширования адреса для счётчика, реализация выбора коммун на клиенте.
**Дата**: 2026-08-15

Фича сквозная: `packages/contracts` (пути страниц и лимиты), схема БД, `apps/api`
(форма, письма, подтверждение, отписка) и `apps/web` (форма и страницы из писем).
Зависимости PRD выполнены: справочник Commune с поиском (`GET /communes`),
`MailService.send()` с обязательной ссылкой прекращения писем, фундамент клиента
(локализация, компонентная база, слой API, axe-прогон).

## Владелец пути страниц из писем

`docs/plan/emails.md`, раздел «Владелец пути „прекратить получение писем“»:
путь объявляет константой в `packages/contracts` фича-владелец письма — то есть
эта. Пути страниц подтверждения и отписки объявляются там же и оттуда берутся и
API (сборка ссылки письма), и web (роут страницы): двух литералов пути в
репозитории быть не должно — расхождение тихо ломает обязательную ссылку.
Contracts собирается первым (`npm run build:contracts`).

## Новые зависимости ставит владелец до фазы

Ralph Loop зависимости не ставит (`npm install`, `npx` и правка `package.json`
не входят в `allowedTools`), а выбор коммун на клиенте, скорее всего, потребует
добавить компонент shadcn/ui (Base UI-вариант). Research-отчёт обязан перечислить
точный список пакетов и команд по фазе; владелец выполняет их вручную **до**
запуска фазы — как в планах `emails` и `web-foundation`.

## Тесты не выделены в отдельную задачу

Проверки названы внутри той задачи, поведение которой подтверждают. Почему иначе
нельзя — `docs/plan/emails.md`, раздел «Тесты не выделены в отдельную задачу».
Правила доступности и обязательная визуальная проверка UI не пересказываются в
задачах web-фаз: они в `apps/web/CLAUDE.md` и обязательны для каждой такой фазы.

## Правка модели данных идёт с миграцией

PRD («Ограничения») требует: расхождения с `docs/research/data-model.md` § 6 —
отсутствие срока жизни токена и счётчика писем, отменённое решение «повторная
форма изменяет подписку» — правятся в модели **тем же коммитом**, что и
миграция. Это часть задач с миграцией в фазах 1 и 4, не отдельная работа.

## Фаза 1: Подписка и её подтверждение (Tracer Bullet)

**Цель:** форма API принимает адрес и коммуны, создаёт неподтверждённую подписку,
на адрес уходит письмо со ссылкой; переход по ссылке ничего не активирует, а
отдельное действие подтверждения делает подписку активной. Сквозной путь через
contracts, БД, API и письма; клиента ещё нет — проверяется тестами и письмом в
локальном outbox.
**Затрагивает:** contracts / db / api

**Задачи:**

- [ ] Миграция `prisma migrate`: `Veille` (нормализованный `email` с `unique`,
      `confirmTokenHash`, `unsubscribeTokenHash`, срок жизни подтверждения,
      `confirmedAt`, `createdAt`) и `VeilleCommune` (составной PK, `codeInsee` →
      `Commune`, каскад от `Veille`) по `docs/research/data-model.md` § 6 и
      research-отчёту фичи; § 6 модели правится тем же коммитом (см. раздел
      выше). Хранятся хеши токенов, не сами токены. **Проверяется тестами (до
      кода, интеграционные):** удаление `Veille` сносит `VeilleCommune` каскадом;
      второй `Veille` с тем же email не создаётся; ссылка на несуществующий
      `codeInsee` отвергается базой.
- [ ] `POST /veille`: нормализация email (trim, lowercase) до проверки
      уникальности, валидация состава — от 1 до 20 коммун (границы — константы
      `packages/contracts`, не литералы в DTO), все коды существуют в справочнике;
      создание неподтверждённой подписки с токенами (сырой уходит в письмо, в базе
      хеш) и сроком 7 дней (константа contracts). Ответ не зависит от того, был ли
      адрес известен; в этой фазе существующий адрес получает тот же ответ, его
      данные не меняются и письмо не уходит — полное поведение повторной формы
      определяет фаза 3. **Проверяется тестами (до кода):** « User@Example.fr » и
      «user@example.fr» дают одну подписку; 0 коммун, 21 коммуна и несуществующий
      код INSEE — ошибка валидации; статус и тело ответа для нового и уже
      существующего адреса совпадают; email не встречается в перехваченных логах
      ни на успешном, ни на отказном пути.
- [ ] Письмо подтверждения через `MailService.send()`: французские строки — в
      `src/i18n/fr.ts` API (ветка фичи), ссылка подтверждения собирается из пути
      в contracts и сырого токена, `unsubscribePath` — из константы отписки той же
      фазы. Второй склейки базового адреса не заводить — её делает каркас.
      **Проверяется тестами (до кода, транспорт подставляется через токен):**
      письмо содержит ссылку на путь подтверждения из contracts с токеном и
      обязательную ссылку отписки; множества ссылок в text- и HTML-версии
      совпадают (гарантия каркаса — здесь проверяется, что фича её не ломает);
      адрес получателя отсутствует в логах.
- [ ] Чтение состояния и подтверждение: `GET` по токену возвращает состояние
      ссылки (ожидает подтверждения / подписка активна / lien invalide) и **ничего
      не меняет**; отдельный `POST` активирует подписку. Причина невалидности
      наружу не раскрывается — просрочка, удаление и выдуманный токен дают один
      ответ. Устройство модуля и правило «GET ничего не меняет» зафиксировать в
      `apps/api/src/veille/CLAUDE.md` тем же коммитом. **Проверяется тестами (до
      кода):** после `GET` подписка всё ещё не подтверждена (проверяется запросом
      к базе); `POST` проставляет `confirmedAt`; повторный `GET` и повторный
      `POST` по той же ссылке отвечают «подписка активна» без ошибки; `GET`
      подтверждённой подписки отвечает так же и по истечении 7 дней от создания;
      несуществующий токен даёт тот же ответ, что просроченный.

**Когда готова:** интеграционно — форма создаёт неподтверждённую подписку,
письмо со ссылкой лежит в локальном outbox, переход по ссылке (`GET`) подписку не
активирует, действие подтверждения активирует, повторный переход показывает
«подписка активна»; email отсутствует в логах всех этих шагов.

## Фаза 2: Отписка в один клик

**Цель:** ссылка отписки из любого письма — включая письмо-подтверждение ещё не
подтверждённой подписки — приводит к немедленному удалению подписки и всех
связанных данных одним действием, без ввода данных и без второго подтверждения.
**Затрагивает:** api

**Задачи:**

- [ ] `GET` по токену отписки: возвращает состояние страницы (подписка есть /
      уже удалена) и **ничего не меняет**; срока у ссылки нет — она действует,
      пока существует подписка. **Проверяется тестами (до кода):** после `GET`
      строки `Veille` и `VeilleCommune` на месте; токен неподтверждённой подписки
      обслуживается наравне с подтверждённым; `GET` по токену удалённой подписки
      отвечает без ошибки и не раскрывает, существовал ли адрес.
- [ ] `POST` отписки: hard delete подписки каскадом, немедленно и без
      промежуточных шагов; операция идемпотентна. Дополнить
      `apps/api/src/veille/CLAUDE.md` тем же коммитом. **Проверяется тестами (до
      кода):** после `POST` строк `Veille` и `VeilleCommune` в базе нет
      (проверяется запросом); повторный `POST` по той же ссылке отвечает успехом,
      а не ошибкой; отписка неподтверждённой подписки удаляет её так же; email
      отсутствует в логах.

**Когда готова:** интеграционно — по ссылке отписки из письма-подтверждения одно
действие удаляет подписку и её коммуны, повторное действие и повторный переход
ошибок не дают, `GET` данные не трогает.

## Фаза 3: Повторная форма и истечение неподтверждённых

**Цель:** второй раз отправленная форма ведёт себя по PRD — подтверждённая
подписка не меняется и получает письмо с перечнем своих коммун, неподтверждённая
переписывается последней формой с новым семидневным сроком; подписка, не
подтверждённая за 7 дней, физически исчезает из базы.
**Затрагивает:** api

**Задачи:**

- [ ] Повторная форма **подтверждённым** адресом: вторая подписка не создаётся,
      состав коммун не меняется; уходит письмо «вы уже подписаны» с перечнем
      коммун действующей подписки и ссылкой отписки (строки — в локализации API).
      **Проверяется тестами (до кода):** число подписок и состав `VeilleCommune`
      после повторной формы прежние; письмо содержит названия всех коммун
      подписки и ссылку отписки; статус и тело ответа совпадают с ответом на
      форму нового адреса.
- [ ] Повторная форма **неподтверждённым** адресом: состав коммун берётся из
      последней формы, выдаётся новый токен подтверждения, семидневный срок
      отсчитывается заново, уходит новое письмо подтверждения. Токен отписки
      **не перевыпускается**: PRD обещает, что ссылка отписки из любого письма
      действует, пока существует подписка, — включая первое письмо. **Проверяется
      тестами (до кода):** после повторной формы подписка одна, её коммуны — из
      второй формы; прежняя ссылка подтверждения больше не действует, новая
      действует; ссылка отписки из первого письма всё ещё удаляет подписку; срок
      отсчитан от второй формы.
- [ ] Удаление подписок, не подтверждённых за 7 дней — механизм по
      research-отчёту (фоновая задача или чистка при обращении). **Проверяется
      тестами (до кода):** после срабатывания механизма чистки (тест вызывает
      его так, как определяет research-отчёт) строк `Veille` и `VeilleCommune` в
      базе нет — проверяется запросом, а не только ответом ссылки; ссылка
      подтверждения после этого отвечает «lien invalide» тем же ответом, что и
      выдуманный токен; подтверждённая подписка того же возраста не трогается.

**Когда готова:** интеграционно — три сценария повторной формы (новый,
подтверждённый, неподтверждённый адрес) дают неразличимый ответ и разные письма;
неподтверждённая подписка старше 7 дней отсутствует в базе.

## Фаза 4: Ограничение частоты писем формы

**Цель:** на один адрес уходит не более 5 писем формы за скользящие 24 часа;
превышение не видно по ответу формы, а цикл «подписаться — отписаться» лимит не
обходит.
**Затрагивает:** db / api

**Задачи:**

- [ ] Миграция `prisma migrate` для счётчика писем: необратимый хеш адреса
      (способ — по research-отчёту), время отправки, срок жизни записи 24 часа;
      самого адреса в таблице нет. Правка `docs/research/data-model.md` § 6 тем
      же коммитом: счётчик — единственное, что переживает удаление подписки.
      **Проверяется тестами (до кода):** запись счётчика не содержит адреса ни в
      одной колонке; удаление подписки каскадом записи счётчика не сносит.
- [ ] Лимит 5 писем формы (подтверждение, повторное подтверждение, «вы уже
      подписаны») на адрес за скользящие 24 часа — предел константой в contracts;
      при превышении письмо не отправляется, а ответ формы не отличается от
      обычного. **Проверяется тестами (до кода):** шестая форма за сутки письма
      не отправляет, а её статус и тело совпадают с первой; после отписки и новой
      подписки с того же адреса счётчик продолжается, а не начинается заново;
      письмо, отправленное более 24 часов назад, в лимит не входит (скользящее
      окно, не календарные сутки).
- [ ] Удаление записей счётчика старше 24 часов — тем же механизмом, что чистка
      фазы 3: обещание «хеш живёт 24 часа» держится данными, а не только чтением.
      **Проверяется тестами (до кода):** после срабатывания механизма чистки
      запись старше суток в базе отсутствует (проверяется запросом).

**Когда готова:** интеграционно — пятое письмо уходит, шестое нет, ответ формы во
всех случаях одинаков; лимит переживает отписку; записи счётчика старше суток
удалены и адреса в них никогда не было.

## Фаза 5: Страницы подтверждения и отписки (web)

**Цель:** ссылки, которые API уже кладёт в каждое письмо, ведут на рабочие
французские страницы: переход показывает страницу с единственной кнопкой, нажатие
подтверждает подписку или удаляет её, а неудачный запрос к API даёт сообщение об
ошибке, а не пустой экран.
**Затрагивает:** web

**Задачи:**

- [ ] Роут страницы подтверждения по пути из `packages/contracts` (второго
      литерала пути в репозитории нет): состояние читается на сервере, страница
      показывает единственную кнопку; состояния «подписка активна» и «lien
      invalide» — отдельные экраны без кнопки. Все строки — в `src/i18n/fr.ts`.
      **Проверяется тестами (до кода, Playwright):** после открытия страницы
      подписка не активирована — проверяется состоянием, а не перехватом сетевых
      запросов (чтение серверное, браузерного трафика нет); нажатие кнопки
      активирует подписку и показывает
      результат; повторное открытие показывает «подписка активна» без кнопки;
      невалидный токен даёт экран «lien invalide».
- [ ] Роут страницы отписки по пути из contracts: единственная кнопка, после
      нажатия — сообщение об удалении данных; повторное нажатие и повторный
      переход ошибки не дают. **Проверяется тестами (до кода, Playwright):**
      открытие страницы данные не трогает; нажатие удаляет подписку; повторный
      переход показывает штатный экран, а не ошибку.
- [ ] Действия обеих страниц — через `useMutation` слоя `src/lib/api/`, ключи и
      функции запроса в общем слое; отказ запроса показывает французское
      сообщение об ошибке, объявляемое скринридером (первая живая проверка слоя
      API из `docs/prd/web-foundation.md`). **Проверяется тестами (до кода,
      Playwright):** при недоступном API нажатие кнопки показывает французское
      сообщение об ошибке в области с ролью, объявляемой скринридером, а не
      пустой экран; повторная попытка после восстановления API проходит.

**Когда готова:** axe без ошибок на обеих страницах в обеих темах, обе полностью
проходимы с клавиатуры с видимым фокусом; переход по ссылке из письма ничего не
меняет, нажатие кнопки подтверждает или удаляет подписку; отказ API даёт
французское сообщение; выполнена визуальная проверка по `apps/web/CLAUDE.md`.

## Фаза 6: Публичная форма подписки (web)

**Цель:** житель без аккаунта находит форму, выбирает коммуны поиском, оставляет
адрес и получает письмо — сценарий PRD доступен целиком без обращения к API
вручную.
**Затрагивает:** web

**Задачи:**

- [ ] Страница формы и вход на неё с главной страницы (иначе форма недостижима):
      поле email и выбор коммун; строки — в `src/i18n/fr.ts`. **Проверяется
      тестами (до кода, Playwright):** с главной страницы форма достижима
      ссылкой; отправка формы с валидными данными показывает сообщение об успехе.
- [ ] Выбор коммун поиском через `GET /communes` (слой `src/lib/api/`,
      `useQuery`): поиск по названию и по коду INSEE, выбранные коммуны видны и
      удаляются, выбор от 1 до 20 — границы из констант contracts. Реализация
      элемента выбора — по research-отчёту. **Проверяется тестами (до кода,
      Playwright):** «chateau» и код INSEE находят одну и ту же коммуну; выбор
      целиком выполняется с клавиатуры; появление результатов объявляется
      скринридером (`role="status"`/`aria-live`); попытка отправить форму без
      коммун даёт сообщение об ошибке, связанное с полем; верхняя граница —
      ошибка при попытке выбрать 21-ю коммуну или при отправке, смотря что
      позволяет элемент выбора из research-отчёта.
- [ ] Информирование при сборе данных: форма называет цель обработки email и
      ведёт ссылкой на politique de confidentialité (страница уже есть, путь — из
      существующего реестра юридических страниц, не литералом). **Проверяется
      тестами (до кода, Playwright):** на странице формы есть текст о цели
      обработки и работающая ссылка на politique de confidentialité.
- [ ] Отправка формы через `useMutation`: сообщение об успехе одинаково для
      нового и уже подписанного адреса (анти-enumeration на клиенте не должно
      разъезжаться с API), отказ запроса — французское сообщение из фазы 5.
      **Проверяется тестами (до кода, Playwright):** ответ формы для нового и для
