# Plan: Veille — подписка и отписка

**PRD**: docs/prd/veille-subscription-lifecycle.md
**Research**: docs/research/veille-subscription-lifecycle.md (15.08.2026).
Технические решения (схема трёх моделей, токены и их хеши, HMAC-хеш адреса для
счётчика, место проверки лимита, фоновая чистка, контракт четырёх эндпоинтов,
route handler one-click, Base UI Combobox) приняты там; задачи ниже их
применяют, а не перевыбирают. Отступления реализации фиксируются врезкой
«Исправлено при реализации» в самом отчёте.
**Дата**: 2026-08-15

Фича трогает все три пакета: `packages/contracts` (пороги и словарь статусов),
`apps/api` (модуль `src/veille/`, миграция, два письма, фоновая чистка),
`apps/web` (форма и три страницы за ссылками из писем). Предпосылки —
справочник Commune с поиском, каркас писем и фундамент клиента — выполнены.

## Константы contracts объявляются задачей-потребителем

Отдельной задачи «завести константы» в плане нет: `VEILLE_MAX_COMMUNES` и
`VEILLE_CONFIRM_TTL_DAYS` появляются в фазе 1 вместе с формой и письмом,
`VeilleConfirmationStatus` — в фазе 2 вместе с эндпоинтом статуса,
`VEILLE_FORM_EMAIL_DAILY_LIMIT` — в фазе 3 вместе с лимитом,
`COMMUNE_SEARCH_MIN_QUERY_LENGTH` переезжает из DTO API в фазе 5, где порог
впервые нужен обеим сторонам. Иначе получилась бы задача-подготовка без
работающего результата, а число всё равно проверяется только тестом
потребителя. Каждая такая задача помнит: contracts собирается первым
(`npm run build:contracts`), правка DTO или письма — тем же коммитом.

## Путь отписки — одно написание на репозиторий

`docs/plan/emails.md` («Владелец пути») оставил объявление пути за
фичей-владельцем письма: путь нужен и API (каркас собирает от него абсолютный
адрес), и web (роут страницы). Константа `VEILLE_UNSUBSCRIBE_PATH`
(`/veille/desinscription`) объявляется в contracts в фазе 1 и используется
route handler'ом фазы 6. Второго литерала в репозитории быть не должно:
расхождение молча ломает обязательную ссылку, а тест каркаса этого не увидит —
он проверяет наличие ссылки, а не её достижимость.

## Тесты не выделены в отдельную задачу

Проверки названы внутри той задачи, поведение которой подтверждают, и пишутся
до кода в её же сессии — отдельная задача «Тесты» означала бы коммит с одними
красными тестами, который pre-commit не пропустит.

## Фаза 1: Подписка создаётся и уходит письмо подтверждения (Tracer Bullet)

**Цель:** сквозной путь через все слои — форма (пока только HTTP) принимает
email и коммуны, в базе появляется неподтверждённая подписка с хешами токенов и
сроком, на адрес уходит французское письмо с ссылкой подтверждения и ссылкой
отписки в подвале. Повторные заявки, подтверждение и отписка — следующие фазы.
**Затрагивает:** contracts / db / api

**Задачи:**

- [ ] Миграция `prisma migrate`: модели `Veille`, `VeilleCommune`,
      `VeilleFormEmail` по схеме research; `docs/research/data-model.md` § 6
      правится тем же коммитом — добавляются `confirmExpiresAt` и таблица
      счётчика писем, убирается фраза «повторная форма изменяет существующую
      подписку» (отменена разбиением на два PRD). **Проверяется тестами (до
      кода):** удаление `Veille` каскадом сносит её `VeilleCommune`; вторая
      подписка на тот же нормализованный email отвергается уникальным индексом;
      коммуна, на которую ссылается подписка, не удаляется (`Restrict`).
- [ ] Письмо подтверждения: ветка `fr.mail.veille` в `src/i18n/fr.ts`
      (параграф с целью, блок `list` названий выбранных коммун, блок `link`
      «Confirmer votre inscription» на `/veille/confirmation?token=…`, параграф
      о сроке из `VEILLE_CONFIRM_TTL_DAYS`, `reason` для подвала);
      `unsubscribePath` — `VEILLE_UNSUBSCRIBE_PATH` + токен отписки. Обе
      константы объявляются в contracts этим же коммитом. **Проверяется тестами
      (до кода):** письмо несёт ссылку подтверждения с токеном и ссылку отписки
      в подвале; перечислены все выбранные коммуны; срок в тексте равен
      константе contracts; тема и тело — не короче 10 символов (ограничение
      Scaleway TEM); в contracts текстов UI нет.
- [ ] `POST /veille` и модуль `src/veille/`: DTO (`@Transform` trim +
      lowercase, `@IsEmail`, `@ArrayMinSize(1)`,
      `@ArrayMaxSize(VEILLE_MAX_COMMUNES)`, коды длиной 5) и сервис для ветки
      «адреса ещё нет» — дедупликация кодов, сверка их с действующими
      `Commune` одним запросом, подписка и её коммуны появляются вместе или не
      появляются вовсе (вложенная запись Prisma атомарна сама по себе, внешняя
      `$transaction` вокруг одного запроса не нужна),
      токены `randomBytes(32).base64url` с хранением только SHA-256, письмо
      после записи, ответ всегда `204` (`@HttpCode`). Тем же коммитом —
      `src/veille/CLAUDE.md` (точки входа модуля, почему токен живёт в query) и
      строка о модуле в `apps/api/CLAUDE.md`. **Проверяется тестами (до кода):**
      « User@Example.fr » и «user@example.fr» дают одну подписку; 0 коммун и
      `VEILLE_MAX_COMMUNES + 1` — `400`; неизвестный код INSEE — `400` без
      обращения к FK; повторённый в форме код не даёт `400` и создаёт одну
      строку `VeilleCommune`; в базе лежат хеши, а не токены из письма; ответ —
      `204` с пустым телом; email не встречается ни в одном аргументе
      перехваченного `Logger`.

**Когда готова:** `POST /veille` новым адресом создаёт неподтверждённую
подписку со сроком `VEILLE_CONFIRM_TTL_DAYS`, отдаёт `204` и кладёт в
`.mail-outbox` французское письмо с рабочей ссылкой подтверждения и ссылкой
отписки; email в логах отсутствует.

## Фаза 2: Подтверждение и отписка по ссылкам

**Цель:** ссылки из письма работают — страница подтверждения знает своё
состояние, кнопка активирует подписку, кнопка отписки удаляет её со всеми
связанными данными; переход по ссылке сам по себе ничего не меняет.
**Затрагивает:** contracts / api

**Задачи:**

- [ ] `GET /veille/confirmation?token=…` → `200 { status }`,
      `VeilleConfirmationStatus` (`pending | active | invalid`) объявляется в
      contracts этим же коммитом. Просроченная, но ещё не удалённая подписка —
      `invalid`, как и неизвестный токен: причина наружу не различается.
      **Проверяется тестами (до кода):** после `GET` по действующей ссылке
      подписка всё ещё не подтверждена (`confirmedAt` null) — превью почтовика
      её не активирует; неподтверждённая в срок → `pending`; подтверждённая →
      `active`; неизвестный токен и подписка с истёкшим `confirmExpiresAt` →
      `invalid`, ответ обеих неотличим.
- [ ] `POST /veille/confirmation` — активация: проставляется `confirmedAt`,
      ответ `200 { status: 'active' }`; повторный вызов тем же токеном тоже
      `active` без ошибки; истёкшая и неизвестная → `invalid`. У подтверждённой
      подписки срок больше не проверяется. **Проверяется тестами (до кода):**
      подписка становится активной только после `POST`; второй `POST` и
      последующий `GET` тем же токеном дают `active` и позже
      `confirmExpiresAt`; истёкшая неподтверждённая не активируется.
- [ ] `POST /veille/desinscription` — `deleteMany` по хешу токена отписки,
      ответ `204` независимо от числа удалённых строк. **Проверяется тестами (до
      кода):** подписка и её `VeilleCommune` исчезают из базы; повторный вызов и
      вызов с неизвестным токеном дают тот же `204` без ошибки; ссылка отписки
      неподтверждённой подписки (та, что ушла в письме фазы 1) удаляет её
      целиком; после подтверждения та же ссылка по-прежнему работает — срока у
      неё нет.

**Когда готова:** полный цикл проходится по ссылкам из письма — переход не
меняет данных, `POST` подтверждения активирует подписку, `POST` отписки
удаляет её и её коммуны; повторы обоих действий безошибочны; email в логах
отсутствует.

## Фаза 3: Повторная форма и лимит писем

**Цель:** форма ведёт себя по PRD для уже известного адреса — состав коммун
неподтверждённой подписки переписывается, подтверждённая не меняется и получает
письмо со своим составом, — а число писем формы на адрес ограничено пятью в
скользящие сутки; ответ формы во всех случаях неразличим.
**Затрагивает:** contracts / api

**Задачи:**

- [ ] Ветка неподтверждённого адреса: состав коммун переписывается данными
      последней формы (`deleteMany` + `createMany` в той же транзакции),
      `confirmExpiresAt` отсчитывается заново, токен подтверждения **не**
      перевыпускается, уходит новое письмо подтверждения. Гонка двух
      одновременных форм новым адресом (`P2002` на `unique(email)`) ловится в
      сервисе и обработка повторяется один раз. **Проверяется тестами (до
      кода):** вторая форма тем же неподтверждённым адресом не создаёт вторую
      подписку, оставляет состав из последней формы и продлевает срок; ссылка из
      первого письма продолжает работать; `P2002` не доезжает до `500` и не даёт
      `409` (он был бы enumeration-оракулом).
- [ ] Ветка подтверждённого адреса и письмо «Vous êtes déjà inscrit·e»: база не
      меняется, уходит письмо с блоком `list` коммун действующей подписки;
      ссылка отписки — из подвала каркаса, вторая в теле не заводится; строки —
      в `fr.mail.veille`. **Проверяется тестами (до кода):** форма
      подтверждённым адресом не создаёт вторую подписку и не меняет состав
      коммун даже при другом списке в форме; уходит письмо со списком
      действующей подписки и рабочей ссылкой отписки; ответ — тот же `204`, что
      и для нового адреса.
- [ ] Лимит писем формы: `VEILLE_FORM_EMAIL_DAILY_LIMIT` в contracts, HMAC-хеш
      адреса на секрете `VEILLE_EMAIL_HASH_SECRET` (`env.validation.ts` +
      `.env.example` одним коммитом), `count` строк `VeilleFormEmail` за
      скользящие 24 часа перед отправкой; при достижении лимита письмо не
      отправляется и строка не пишется, изменения подписки выполняются, ответ
      обычный. Строка счётчика пишется до `send()` и вне транзакции подписки.
      Фраза «там же будут лимиты частоты» в `src/mail/CLAUDE.md` правится тем же
      коммитом: лимит фичи живёт в фиче, каркас остаётся немым к содержимому.
      **Проверяется тестами (до кода):** шестая форма за 24 часа письма не шлёт,
      но отвечает неотличимо от обычной; отписка и новая подписка тем же
      адресом счётчик не сбрасывают; в `VeilleFormEmail` нет адреса — хеш не
      равен ни адресу, ни его хешу без секрета; строка счётчика остаётся, если
      отправка провалилась.

**Когда готова:** три ветки формы различимы только письмом и содержимым базы —
ответ во всех случаях `204` с пустым телом; шестое письмо формы за сутки не
уходит; секрет хеша обязателен при старте, а email по-прежнему отсутствует в
логах.

## Фаза 4: Истечение и чистка

**Цель:** обещание RGPD выполняется данными, а не только недоступностью ссылки:
неподтверждённой за 7 дней подписки в базе физически нет, а счётчик писем не
хранит хеши дольше своего окна.
**Затрагивает:** api

**Задачи:**

- [ ] Удаление просроченных подписок: метод сервиса
      `deleteMany({ confirmedAt: null, confirmExpiresAt: { lt: now } })` (каскад
      сносит `VeilleCommune`), вызываемый по `@Cron(CronExpression.EVERY_HOUR)`;
      тесты зовут метод напрямую, расписания не ждут. **Проверяется тестами (до
      кода):** после прогона строки просроченной неподтверждённой подписки и её
      коммун отсутствуют — проверяется запросом к базе, а не ссылкой;
      подтверждённая подписка с давно истёкшим `confirmExpiresAt` не удаляется;
      ссылка подтверждения удалённой отвечает `invalid` без раскрытия причины.
- [ ] Чистка счётчика писем: `deleteMany` строк `VeilleFormEmail` старше 24
      часов тем же часовым прогоном; `src/veille/CLAUDE.md` дополняется
      описанием жизненного цикла подписки и того, что переживает удаление.
      **Проверяется тестами (до кода):** строки старше окна исчезают, строки
      внутри окна остаются и продолжают считаться лимитом.

**Когда готова:** часовой прогон чистки не оставляет в базе ни одной
неподтверждённой подписки старше `VEILLE_CONFIRM_TTL_DAYS` и ни одной строки
счётчика старше суток; ссылки удалённых подписок отвечают «lien invalide».

## Фаза 5: Форма подписки в web

**Цель:** житель коммуны подписывается со страницы: вводит email, находит
коммуны поиском по названию или коду INSEE, видит цель обработки данных и
ссылку на politique de confidentialité, получает экран «письмо отправлено» — а
при недоступном API французское сообщение об ошибке, а не пустой экран.
**Затрагивает:** contracts / api / web

**Задачи:**

- [ ] Мультивыбор коммун на Base UI Combobox: `multiple`, чипы выбранных,
      контролируемый `inputValue` + `useQuery` через `apiFetch` на
      `GET /communes?q=…` с ключом из `queryKeys` (ключей по компонентам не
      заводить), `filteredItems` вместо внутренней фильтрации, анонсы
      `Combobox.Status` / `Combobox.Empty` строками из `fr.ts`, потолок выбора —
      `VEILLE_MAX_COMMUNES`. Порог запроса переезжает в contracts как
      `COMMUNE_SEARCH_MIN_QUERY_LENGTH`, DTO поиска коммун в API правится тем же
      коммитом. Перед кодом на Query вызвать скилл **tanstack-query**.
      **Проверяется тестами (до кода):** коммуна находится и по названию, и по
      коду INSEE и выбирается только с клавиатуры; выбранная снимается чипом;
      число найденных и «ничего не найдено» объявляются скринридером; при
      достигнутом потолке добавить 21-ю нельзя.
- [ ] Страница `/veille`: форма email + мультивыбор, текст о цели обработки
      email со ссылкой на `politique-de-confidentialite`, отправка
      `useMutation` через `apiFetch`, экран «письмо отправлено» с
      `role="status"`, ошибка запроса — французское сообщение с `role="alert"`.
      Страница добавляется в `tests/pages.ts`, поэтому попадает в общие сьюты
      (axe, клавиатура, лендмарки, reflow, reduced-motion). Завершается
      визуальной проверкой в браузере и прогоном скилла **ui-ux-pro-max** —
      правило `apps/web/CLAUDE.md`. **Проверяется тестами (до кода):** форма без
      коммун и с невалидным email не отправляется и сообщает об ошибке
      программно связанным с полем текстом; успешная отправка показывает
      подтверждающий экран, объявляемый скринридером; недоступный API даёт
      французское сообщение об ошибке, а не пустой экран; все видимые строки
      берутся из `fr.ts` (правило `i18next/no-literal-string`).

**Когда готова:** со страницы `/veille` подписка создаётся вживую (письмо видно
в `.mail-outbox`), выбор коммун полностью проходим с клавиатуры и объявляется
скринридером, axe не находит ошибок ни на форме, ни на экранах успеха и ошибки.

## Фаза 6: Страницы подтверждения и отписки, отписка в один клик

**Цель:** ссылки из письма ведут на французские страницы с единственной
кнопкой, а штатная кнопка отписки почтового клиента (Gmail, Outlook) работает
без промежуточных экранов — при том, что переход по ссылке данных не трогает.
**Затрагивает:** web / docs

**Предусловия (владелец, issues не заводятся):**

- После деплоя фазы отправить себе письмо veille на адрес Gmail и на адрес
  Outlook, нажать штатную кнопку отписки почтового клиента и убедиться, что
  подписка удалена без открытия страницы; отдельно перейти по ссылке отписки
  из тела письма и убедиться, что она открывает страницу с кнопкой и ничего не
  удаляет.
- Оставить исходные данные комментарием к issue задачи «зафиксировать проверку
  one-click»: дата, почтовые службы, результат по каждой. Пока комментария нет,
  issue в работу не берётся: результат непроведённой проверки сочинять нельзя.

**Задачи:**

- [ ] Страница `/veille/confirmation?token=…`: токен из `useSearchParams()`
      внутри `<Suspense>` (без границы `next build` падает на пререндере),
      `useQuery` статуса; `pending` → кнопка «Confirmer» и `useMutation` →
      «подписка активна»; `active` → сразу «подписка активна»; `invalid` →
      «lien invalide». Страница попадает в `tests/pages.ts` с заведомо
      невалидным токеном. Визуальная проверка и **ui-ux-pro-max** —
      обязательны. **Проверяется тестами (до кода):** страница с действующим
      токеном показывает кнопку и не активирует подписку до нажатия; нажатие
      активирует и меняет экран, объявляя результат скринридером; повторный
      заход тем же токеном показывает «подписка активна» без кнопки и без
      ошибки; неизвестный токен даёт «lien invalide».
- [ ] Страница `/veille/desinscription/confirmer?token=…`: кнопка «Se
