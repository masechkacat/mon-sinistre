# Plan: Veille — изменение состава коммун

**PRD**: docs/prd/veille-commune-change.md
**Research**: docs/research/veille-commune-change.md (17.08.2026).
Технические решения (модель `VeilleChange` 1:1, ветка подтверждённого адреса в
`subscribe`, константа `VEILLE_CHANGE_TTL_DAYS`, контракт
`GET`/`POST /veille/changement`, claim удалением заявки, третья ветка чистки,
письмо изменения, страница web) приняты там; задачи ниже их применяют, а не
перевыбирают. Отступления реализации фиксируются врезкой «Исправлено при
реализации» в самом отчёте.
**Дата**: 2026-08-17
**Статус**: выполнен (17.08.2026). План — снимок на момент планирования и
ретроактивно не правится.

Фича живёт внутри готового контура veille: `packages/contracts` (константы и
типы ответов изменения), `apps/api` (модуль `src/veille/`, миграция, письмо,
чистка), `apps/web` (одна страница). Новых зависимостей и переменных окружения
нет. Константы contracts объявляются задачей-потребителем, тесты живут внутри
задач — оба правила и их причины в `docs/plan/veille-subscription-lifecycle.md`,
здесь действуют без изменений.

## Фаза 1: Форма подтверждённым адресом создаёт заявку и шлёт письмо (Tracer Bullet)

**Цель:** сквозной путь до письма — повторная форма подтверждённым адресом
больше не отвечает «déjà inscrit·e», а записывает заявку `VeilleChange` и шлёт
французское письмо со ссылкой подтверждения изменения; действующий состав и
рассылка не затронуты, ответ формы неразличим.
**Затрагивает:** contracts / db / api

**Задачи:**

- [ ] Миграция `prisma migrate`: модель `VeilleChange` по схеме research;
      `docs/research/data-model.md` § 6 правится тем же коммитом (отложенный
      состав, каскад). **Проверяется тестами (до кода):** у одной подписки не
      может быть двух заявок (`veilleId @unique` — вторая запись отвергается,
      upsert переписывает единственную); удаление `Veille` каскадом сносит её
      `VeilleChange` — тем же `deleteMany`, что в `unsubscribe`, без нового
      кода.
- [ ] Письмо изменения `veille-change-mail.ts`: ветка `fr.mail.veille.change`
      (параграф-объяснение, блок `list` **нового** состава через общий
      `communeLabel`, блок `link` на `${VEILLE_CHANGE_PATH}?token=…`, параграф о
      сроке из `VEILLE_CHANGE_TTL_DAYS`), `reason` — общий
      `fr.mail.veille.reason`, `unsubscribePath` — общий `unsubscribePathFor`.
      Обе константы объявляются в contracts этим же коммитом. **Проверяется
      тестами (до кода):** письмо несёт ссылку изменения с токеном и ссылку
      отписки в подвале; перечислены коммуны нового состава; срок в тексте равен
      константе contracts; тема и тело — не короче 10 символов (Scaleway TEM);
      в contracts текстов UI нет.
- [ ] Ветка `claim.kind === 'confirmed'` в `upsertSubscription`: upsert заявки
      (состав + `expiresAt`) **вне** гейта лимита; письмо через `sendFormMail`,
      внутри гейта которого перевыпускаются `changeTokenHash` и
      `unsubscribeTokenHash` (`count === 0` любого `updateMany` → `null` —
      гонка, попытка лимита не тратится); `claimUnconfirmed` возвращает
      `veilleId` и для `confirmed`. Файл `veille-already-subscribed-mail.ts` со
      спекой и строками `fr` удаляется; `src/veille/CLAUDE.md` правится тем же
      коммитом. **Проверяется тестами (до кода):** форма подтверждённым адресом
      с другим составом не меняет `VeilleCommune` (критерий «не влияет на
      рассылку» — на данных) и создаёт/переписывает единственную заявку с
      составом последней формы; повторная форма ротирует `changeTokenHash` —
      прежний хеш больше не находится; ответ — тот же `204`, что для нового и
      неподтверждённого адреса; 0 и 21 коммуна — `400`, заявка не создаётся и
      состав не меняется; шестая форма за сутки письма не шлёт, но заявку
      переписывает и хеши не ротирует; email не встречается ни в одном
      аргументе перехваченного `Logger`.

**Когда готова:** форма подтверждённым адресом кладёт в `.mail-outbox`
французское письмо со ссылкой изменения, в базе лежит единственная заявка со
сроком `VEILLE_CHANGE_TTL_DAYS`, действующий состав не изменился, ответ — `204`,
email в логах отсутствует.

## Фаза 2: Подтверждение изменения по ссылке, истечение и чистка

**Цель:** ссылка из письма работает — `GET` показывает новый состав, ничего не
меняя, `POST` применяет его целиком и ровно один раз; просроченные и прежние
ссылки отвечают «lien invalide», просроченные заявки физически исчезают из
базы, а подписка живёт в прежнем составе.
**Затрагивает:** contracts / api

**Задачи:**

- [ ] `GET /veille/changement?token=…` → `200 { status, communes? }`: токен
      голым `@Query('token')`, поиск по `changeTokenHash` с
      `expiresAt: { gte: now }`; для `pending` — коммуны заявки
      (`{ name, departementName }` из справочника). `VEILLE_CHANGE_STATUSES`,
      тип и интерфейсы ответов объявляются в contracts этим же коммитом.
      **Проверяется тестами (до кода):** после `GET` по действующей ссылке
      состав `VeilleCommune` не изменился, ответ несёт коммуны заявки;
      неизвестный токен и просроченная заявка → `invalid`, ответы неотличимы;
      после повторной формы прежний токен → `invalid`, последний → `pending`.
- [ ] `POST /veille/changement` — применение: интерактивная транзакция,
      `deleteMany` заявки по `id` + `expiresAt: { gte: now }` как атомарный
      захват; `count === 1` → `deleteMany` + `createMany` в `VeilleCommune` →
      `applied`; `count === 0` → `invalid`. `@HttpCode(OK)`, `VeilleTokenDto`,
      без `@ThrottleByToken`. **Проверяется тестами (до кода):** после `POST`
      состав применён целиком — коммуны не из нового состава перестали
      отслеживаться, заявки в базе нет; повторный `POST` тем же токеном →
      `invalid` без ошибки; просроченная заявка не применяется, состав не
      меняется; отписка по токену из письма изменения удаляет подписку вместе
      с заявкой (`POST` отписки — существующий эндпоинт), после неё ссылка
      изменения → `invalid`.
- [ ] Чистка просроченных заявок: третья guarded-ветка в
      `VeilleService.cleanupExpired` — `deleteMany({ expiresAt: { lt: now } })`
      по `VeilleChange`, без индекса (осознанно — research);
      `src/veille/CLAUDE.md` дополняется жизненным циклом заявки тем же
      коммитом. **Проверяется тестами (до кода):** после прогона просроченная
      заявка отсутствует в базе — запросом, не ссылкой; подписка и её
      `VeilleCommune` не тронуты — действует прежний состав; живая заявка
      переживает прогон; сбой одной ветки чистки не прерывает остальные.

**Когда готова:** полный цикл проходится по ссылке из письма — `GET` ничего не
меняет, `POST` применяет состав целиком и повторно отвечает `invalid`;
просроченных заявок в базе нет, подписка живёт в прежнем составе; email в логах
отсутствует.

## Фаза 3: Страница подтверждения изменения в web

**Цель:** подписчик по ссылке из письма видит новый состав коммун и применяет
его одной кнопкой; недействительная ссылка отвечает «lien invalide», сетевой
сбой — французским сообщением об ошибке, всё проходимо с клавиатуры.
**Затрагивает:** web

**Задачи:**

- [ ] Страница `/veille/changement` (путь — `VEILLE_CHANGE_PATH`): `page.tsx` +
      клиентский компонент по образцу `veille-confirmation.tsx` —
      `useSearchParams` под `<Suspense>`, `useQuery` статуса (ключ —
      `queryKeys.veilleChange(token)` в `src/lib/api/keys.ts`); `pending` →
      список нового состава (`<ul>`) и кнопка «Confirmer la modification» с
      `useMutation`; `applied` → терминальный результат через `AnnouncedResult`
      с приоритетом над фоновыми рефетчами; `invalid` → «lien invalide»;
      `RequestError` — не «lien invalide». Страница добавляется в
      `tests/pages.ts` с `?token=invalide`; ветки `pending`/`applied` —
      Playwright-тестом со своей подпиской и заявкой. Завершается визуальной
      проверкой в браузере и прогоном скилла **ui-ux-pro-max**
      (`apps/web/CLAUDE.md`). Перед кодом на Query вызвать скилл
      **tanstack-query**. **Проверяется тестами (до кода):** страница с
      действующим токеном показывает новый состав и кнопку, состав в базе не
      меняется до нажатия; нажатие применяет состав и объявляет результат
      скринридером; недействительный токен → «lien invalide»; недоступный API →
      французское сообщение об ошибке, а не «lien invalide»; все строки — из
      `fr.ts` (правило `i18next/no-literal-string`); axe и клавиатура — общими
      сьютами.

**Когда готова:** со страницы по ссылке из письма изменение применяется вживую;
переход без нажатия ничего не меняет; axe без ошибок, страница полностью
проходима с клавиатуры; все критерии готовности PRD закрыты.
