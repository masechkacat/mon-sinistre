# Plan: Монитор Journal Officiel

**PRD**: docs/prd/jorf-monitor.md
**Research**: docs/research/jorf-monitor.md
**Дата**: 2026-08-18

Фича целиком серверная: web не затрагивается ни одной фазой. Новые зависимости
(`tar`, `@rgrove/parse-xml`) — обоснование в research; ставятся в фазе 1.

## Фаза 1: Сквозной прогон DILA → база (Tracer Bullet)

**Цель:** штатный прогон скачивает свежие дельты JORFSIMPLE, находит arrêtés
catastrophe naturelle и наполняет базу — Arrete с обеими annexes, коммуны
сопоставлены со справочником. Без писем и алертов.
**Затрагивает:** api, db, contracts (только докблок `ArreteEntry.motivation` —
research, «Ограничения и риски»)
**Задачи:**

- [ ] Миграция `Arrete`, `ArreteEntry`, `JorfDelta` по data-model § 4 +
      research (частичный unique `ArreteEntry` — SQL руками; `motivation`
      хранится для обеих annexes — правка docs/research/data-model.md § 4 и
      докблока contracts тем же коммитом). **Проверяется тестами (до кода):**
      schema int-spec — вставка arrêté с entries, каскад удаления, отказ
      дубля `(arreteId, codeInsee, risque, eventStart, eventEnd)` при
      сопоставленном codeInsee и допуск двух строк с `codeInsee: null`.
- [ ] Парсер XML JORFSIMPLE (чистые функции, `src/jorf/`): отбор текста по
      `titretxt` оглавления + `NATURE`, метаданные (`NOR`, `DATE_PUBLI`,
      `DATE_TEXTE`, `ORIGINE_PUBLI`), обе annexes по подписям и шапкам колонок,
      даты `DD/MM/YYYY` → `IsoDate`, `contentHash` по распарсенному
      содержимому. **Проверяется тестами (до кода):** фикстуры реальных XML
      (арретé 12.06.2026 с обеими annexes + оглавление номера, ТЗ § 9):
      число строк обеих annexes, поля первой/последней строки, дата публикации
      равна `DATE_PUBLI`, пустая ячейка «Nombre de reconnaissances» не ломает
      строку; текст не-catnat отбором не проходит.
- [ ] Сопоставление коммуны annexe со справочником: `normalizeCommuneName` на
      имя и департамент, приоритет актуальных строк, при нуле или нескольких
      кандидатах — `codeInsee: null`. **Проверяется тестами (до кода):**
      матч с диакритикой/регистром, устаревший код находится, одноимённые
      коммуны двух департаментов не путаются, неизвестная коммуна даёт null.
- [ ] `DilaClient`: листинг каталога (regex по Apache-индексу), скачивание
      дельты, распаковка `tar` потоком в память, выбор только
      `jorf/simple/JORF/CONT/**/*.xml`. **Проверяется тестами (до кода):**
      fetch-функция через конструктор (образец `GeoApiClient`) — листинг
      парсится из сохранённого HTML, тарбол-фикстура распаковывается, лишние
      пути не читаются, сетевая ошибка и не-200 дают исключение.
- [ ] Прогон `JorfMonitorService` + `@Cron('0 6,23 * * *', Europe/Paris)`:
      необработанные дельты по возрастанию имени → парсинг → ingest
      (NOR-дедуп: новый → создать, повторный с тем же `contentHash` → только
      `lastSeenAt`), пометка дельты после полной обработки. **Проверяется
      тестами (до кода):** int-spec — прогон на дельте-фикстуре создаёт Arrete
      с обеими annexes и `publishedAt` из XML (критерий PRD № 1); повторный
      прогон той же дельты и повторная поставка того же NOR не создают ни
      записей (критерий № 2); сбой скачивания не помечает дельту.

**Когда готова:** int-spec «прогон на выгрузке с новым arrêté создаёт Arrete с
обеими annexes, дата публикации равна дате из XML; повторный прогон не создаёт
ничего» зелёный; `npm run lint && npm test && npm run test:int` проходят.

## Фаза 2: Rectificatifs и алерты администратору

**Цель:** ни один сомнительный случай не проходит молча: rectificatif обновляет
существующий arrêté, а нераспознаваемая структура, несопоставленная коммуна и
смена исхода дают алерт в базе и письмо администратору.
**Затрагивает:** api, db
**Задачи:**

- [ ] Миграция `MonitorAlert` (kind: `UNPARSEABLE_ANNEXE` /
      `UNMATCHED_COMMUNE` / `OUTCOME_CHANGED`, detail, arreteId null,
      createdAt) + дополнение docs/research/data-model.md тем же коммитом.
      **Проверяется тестами (до кода):** schema int-spec — вставка всех трёх
      kind, алерт переживает удаление arrêté (FK set null / без каскада).
- [ ] Rectificatif-путь ingest: повторный NOR с изменившимся `contentHash` —
      upsert entries (новые строки добавляются, существующие обновляются);
      смена `outcome` существующей entry — алерт `OUTCOME_CHANGED`, запись
      обновляется. **Проверяется тестами (до кода):** фикстура «rectificatif
      с повторным NOR» (ТЗ § 9) — добавленная коммуна создаёт entry (критерий
      PRD № 3, без писем — их ещё нет), смена исхода даёт алерт (критерий
      № 11); Z-текст (`NOR…Z`, титул с «(rectificatif)») не создаёт Arrete, а
      даёт алерт со ссылкой на исходный NOR.
- [ ] Алерты парсинга и сопоставления: нераспознаваемая структура annexe →
      `UNPARSEABLE_ANNEXE`, прогон продолжает остальные тексты дельты;
      несопоставленная коммуна → `UNMATCHED_COMMUNE`, строка сохранена без
      привязки. **Проверяется тестами (до кода):** фикстура с нераспознаваемой
      структурой (ТЗ § 9) — алерт есть, второй arrêté той же дельты обработан
      (критерий № 9); строка с чужой коммуной сохранена с `codeInsee: null` и
      алертом (критерий № 10). В detail алертов нет email (проверка всех
      аргументов Logger — образец из emails research).
- [ ] Письмо администратору: `ADMIN_EMAIL` в env-схему и `.env.example`,
      отправка через `MailService.send()` при создании алерта; сбой отправки
      логируется и не прерывает прогон. **Проверяется тестами (до кода):**
      алерт при упавшем транспорте остаётся в базе, прогон завершается;
      письмо не содержит email наблюдателей.

**Когда готова:** все три повода дают строку `MonitorAlert` + письмо; прогон с
битым текстом в дельте завершает остальные — критерии PRD № 9–11 зелёные в
int-spec.

## Фаза 3: Рассылка наблюдателям

**Цель:** подтверждённый наблюдатель получает ровно одно письмо в день
обнаружения arrêté по своей коммуне — с исходом, сроком déclaration из
справочника и отпиской в один клик.
**Затрагивает:** api, db
**Задачи:**

- [ ] Миграции: `DeadlineRule` по data-model § 3 (exclusion-ограничение — SQL
      руками) с seed-записью `DECLARATION_ASSUREUR` (30 DAYS,
      `DATE_PUBLICATION_ARRETE`, source L125-2 — значения из research);
      `VeilleNotification.sentAt` → nullable (outbox) + правка
      docs/research/data-model.md §§ 3, 6 тем же коммитом. **Проверяется
      тестами (до кода):** seed идемпотентен, запись несёт `SourceReference`
      (критерий PRD № 8); пересекающиеся интервалы одного code отклоняются.
- [ ] Fan-out получателей: по кодам entries arrêté → `VeilleCommune` +
      итеративный successor-резолв с защитой от цикла, только
      `confirmedAt != null`, группировка «одно письмо на (veille, arrêté)».
      **Проверяется тестами (до кода):** неподтверждённая veille не в выборке
      (критерий № 6); подписчик влившейся коммуны получает arrêté преемника;
      наблюдатель двух коммун одного arrêté — один получатель со списком обеих
      (критерий № 5).
- [ ] Письмо наблюдателя (`fr.mail.jorf…`, блочная модель каркаса): коммуна,
      риск, период, исход, дата публикации, ссылка на Légifrance; для reconnu —
      срок из `DeadlineRule` (резолв по `publishedAt`), для refusé — прямое
      называние отказа без срока; отписка в один клик. **Проверяется тестами
      (до кода):** спека сборки — refusé-письмо называет отказ и не содержит
      срока (критерий № 7), reconnu-письмо несёт дату дедлайна из правила, обе
      версии совпадают по множеству ссылок.
- [ ] Outbox: строки `VeilleNotification(sentAt: null)` создаются в транзакции
      ingest для новых arrêtés и новых entries rectificatif; отправка вторым
      шагом проставляет `sentAt`, каждый прогон сначала досылает pending;
      сбой одного получателя не прерывает остальных. **Проверяется тестами
      (до кода):** int-spec — ровно одно письмо на наблюдателя, повторный
      прогон второго не создаёт (критерий № 4); rectificatif шлёт только
      наблюдателям добавленной коммуны (критерий № 3); смена исхода не
      порождает писем (критерий № 11); упавший транспорт на первом получателе
      не мешает второму (критерий № 12), недоставленное уходит следующим
      прогоном.

**Когда готова:** критерии PRD № 3–8, 12 зелёные в int-spec; письмо глазами
проверено в `.mail-outbox` (текст и HTML).

## Фаза 4: Бэкфилл с 01.01.2026

**Цель:** база наполнена arrêtés 2026 года; ни одно письмо при этом не ушло и
не уйдёт задним числом.
**Затрагивает:** api
**Задачи:**

- [ ] Режим `notify: false` в ingest: строки `VeilleNotification` не создаются
      вовсе; штатный прогон после бэкфилла не рассылает старьё (повтор NOR без
      изменений — только `lastSeenAt`). **Проверяется тестами (до кода):**
      int-spec — бэкфилл-прогон дельты с arrêté и подтверждённым наблюдателем
      не создаёт ни notification, ни письма; следующий штатный прогон той же
      дельты — тоже (критерий PRD № 13).
- [ ] Скрипт `jorf:backfill` (ts-node без Nest-контекста, образец seed):
      дельты `JORFSIMPLE_20260101-000000`…текущая, фильтр
      `DATE_PUBLI >= 2026-01-01`, прогресс в `JorfDelta` — прерванный запуск
      продолжает с недообработанной дельты. **Проверяется тестами (до кода):**
      юнит на отбор имён дельт по границе даты; int-spec на возобновление
      после прерывания (первая дельта помечена — обрабатывается только
      вторая).
- [ ] Живой запуск бэкфилла на реальных выгрузках; итог (число arrêtés,
      entries, несопоставленных строк, алертов) — в сообщение коммита.
      Перед запуском свериться с листингом DILA: дельты всё ещё покрывают
      01.01.2026 (риск регенерации Freemium — research). **Проверяется:** в
      базе arrêtés за 2026 год (19.01, 13.02, 24.02, 03.03, 13.03, 03.04,
      11.05, 12.06 — по research), `VeilleNotification` пуста.

**Когда готова:** критерий PRD № 13 зелёный; живой бэкфилл выполнен, база
содержит arrêtés 2026 года, писем ноль.
