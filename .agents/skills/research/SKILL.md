# Технический ресерч

Прочитай план: $ARGUMENTS (файл в `docs/plan/`). Задача — **один раз на весь
план** принять технические решения (библиотеки, подходы, ограничения), чтобы при
реализации фаз агент не выбирал наугад и не останавливался с вопросами.

## Процесс

1. Изучи план и связанный PRD, затем реальный стек: корневой CLAUDE.md,
   CLAUDE.md затронутых приложений и их `package.json` — точные версии.
2. Сначала проверь существующие отчёты в `docs/research/` —
   уже решённое не переисследуй, сошлись на него.
3. Для каждого технического выбора из плана сравни варианты и прими решение.
   Если выбор зависит от предпочтений, которые нельзя вывести из проекта
   (например, внешний сервис против самописного) — спроси **до** записи отчёта.
4. Сохрани отчёт в `docs/research/<имя-фичи>.md` — то же имя файла, что у PRD
   и плана.
5. Добавь ссылку на отчёт в CLAUDE.md приложения, которого касаются решения, —
   в том же коммите (правило актуализации документации).

## Структура отчёта

```markdown
# Research: {название фичи}

**План**: docs/plan/{имя-фичи}.md
**Дата**: {реальная текущая дата}

## Решения

### {технический вопрос}

**Решение:** берём {X, точная версия}
**Почему:** {аргументы применительно к нашему стеку}
**Отброшено:** {Y} — {причина}
**Как применять:** {минимальные шаги или пример кода под наш стек}

## Ограничения и риски

{что учесть при реализации; TBD, если вопрос остался открытым}
```

## Правила

- Отчёт — это **решения, а не обзор**: каждый раздел заканчивается «берём X,
  потому что…». Перечисление вариантов без выбора — не результат.
- **NestJS работает на Fastify, а не на Express**: рецепты под Express (Multer
  и т.п.) не подходят; совместимость каждой библиотеки с Fastify-адаптером
  проверяй явно.
- Сверяй советы с точными версиями из `package.json` — статьи и примеры в
  интернете часто написаны под старые мажорные версии.
- Предпочитай уже установленные зависимости новым; каждая новая зависимость —
  с обоснованием в отчёте.
- Юридические сроки и справочные данные — только со ссылкой на источник и датой
  сверки (правило SourceReference); при расхождении источников — консервативное
  значение.
- Выбор UI-компонентов и паттернов — с учётом WCAG AA: работа с клавиатуры,
  без ошибок axe.
