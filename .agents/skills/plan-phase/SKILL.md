# Генератор плана фаз

Прочитай PRD: $ARGUMENTS (файл в `docs/prd/`). Перед разбивкой изучи структуру
проекта — корневой CLAUDE.md и CLAUDE.md затрагиваемых приложений, — чтобы фазы
легли на реальную архитектуру монорепозитория, а не на абстрактный «backend/frontend».

План — описание всех фаз; issues заводит скилл `issues <фича> <N>`, и только
на ближайшую фазу.

## Процесс

1. Если статус PRD не `approved` — остановись и скажи об этом: в планирование
   берётся только утверждённый PRD.
2. Если отчёта `docs/research/<имя-фичи>.md` нет — остановись и скажи об
   этом: research идёт до плана, задачи применяют его решения, а не
   перевыбирают их.
3. Если у фазы есть экран, а файла `docs/design/<экран>.html` нет —
   остановись и скажи об этом: UI планируется по принятому макету, не по
   тексту.
4. Если PRD неполный или критерии готовности непроверяемы — задай вопросы по
   правилу «Вопросы человеку» корневого CLAUDE.md **до** создания плана. Не выдумывай задачи, которых нет в PRD.
5. Сохрани план в `docs/plan/<имя-фичи>.md` — то же имя файла, что у PRD.
6. Покажи план и спроси, какие фазы поправить.

## Структура документа

```markdown
# Plan: {название фичи}

**PRD**: docs/prd/{имя-фичи}.md
**Research**: docs/research/{имя-фичи}.md
**Дата**: {реальная текущая дата}

## Фаза 1: {название} (Tracer Bullet)

**Цель:** что даёт эта фаза — работающий результат, не «подготовка»
**Затрагивает:** contracts / api / web / db (любое подмножество)
**Макет:** docs/design/{экран}.html — только у фазы с UI
**Задачи:**

- [ ] Задача 1 — что сделать. **Проверяется:** {команда и что она должна
      показать}

**Когда готова:** автоматическая приёмка `verificationCommands` в
`.claude/ralph.config.json`; {ожидаемый результат и проверки через Playwright}

## Фаза 2: {название}

...
```

## Правила разбивки на фазы

- Каждая фаза завершается **работающим результатом** — можно остановиться после
  любой фазы, ничего не потеряв. Следующая фаза не ломает предыдущую.
- Фаза 1 — всегда **Tracer Bullet**: минимальный сквозной путь через все
  затронутые слои. Последующие фазы его наращивают.
- **Не больше пяти задач** в фазе; больше — дробить дальше.
- **api и web одной фичи — разные фазы**: сначала API, потом UI.
- **Отдельной задачи «Тесты» в фазе не бывает.** Проверки называются внутри той
  задачи, поведение которой они подтверждают. Проект по TDD, тест пишется до
  кода — но в рамках той же задачи и того же коммита: pre-commit прогоняет
  `npm test`, поэтому коммит с одними красными тестами в репозиторий не попадёт,
  а задача «написать тесты» окажется невыполнимой. Сценарии из раздела
  «Тестирование» корневого CLAUDE.md, которых касается фича, обязательны.
- **«Проверяется»** задачи — то, что прогоняется командой: тест, lint, сборка,
  миграция, страница в Playwright. Для задачи с поведением, которое стоит
  теста, список составляется по ZOMBIES: **Z**ero (пусто, не найдено),
  **O**ne (один объект, счастливый путь), **M**any (несколько, порядок,
  повтор), **B**oundaries (пороги из contracts, границы дат, длины полей из
  миграций), **I**nterface (код ответа, форма DTO, редирект), **E**xceptions
  (чужой объект, невалидный ввод, истёкший токен, два запроса одновременно),
  **S**imple (сценарий из PRD, как его пройдёт пользователь). Буквы, которым
  в задаче нечего проверять, пропускаются; каждый пункт называет конкретное
  значение из кода или PRD, а не «проверить границы». Задаче без поведения
  (конфиг, перенос, документ) достаточно одной команды.
- **«Когда готова»** ссылается на `verificationCommands` конфига Ralph,
  не копирует список автоматических проверок. Перед запуском текущей фазы
  этот список согласуют с её критериями: оркестратор выполняет его сам,
  разрешения `allowedTools` ограничивают только агента. Дополнительные
  проверки через Playwright называют экран, состояние и ожидаемый результат,
  а не неопределённое «визуально проверено».
- **Задача не предписывает текст**: ни докблоков, ни комментариев, ни абзацев
  документации. Что и где документировать, решает «Карта документации»
  корневого CLAUDE.md в том же коммите; задача называет только поведение.
- Изменения общих типов и enum'ов — в `packages/contracts`; помни, что contracts
  собирается первым (`npm run build:contracts`).
- Изменение схемы БД — отдельная задача с миграцией `prisma migrate`.
- **Макет — только десктоп.** Мобильная раскладка отдельно не макетируется:
  она выводится из правил `apps/web/CLAUDE.md` и проверяется `/ui-review` на
  320 px. Критерий готовности фазы с UI включает тесты доступности и проход
  экрана с клавиатуры (WCAG AA — жёсткое требование проекта).
- План покрывает **все** критерии готовности из PRD — сверь чек-листом перед
  сохранением.
- План — снимок на момент планирования: после выполнения фаз он не
  актуализируется (в шапке проставляется «Статус: выполнен» с датой).
  Решение по ходу реализации правит задачи текущей фазы скиллом `/decision`.
