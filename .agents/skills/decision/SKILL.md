# Адресат решения

Вход: $ARGUMENTS — источник (раунд на холсте с датой, ревью PR N, разговор) и
решение одной фразой. Если решение не умещается в фразу или зависит от
невыясненного — сначала вопросы по правилу «Вопросы человеку» корневого
`CLAUDE.md`, потом этот скилл.

## Процесс

1. Прочитай ТЗ, `docs/research/<фича>.md` и `docs/plan/<фича>.md` затронутой
   фичи, `gh issue list --state open`, `docs/design/*.html`; модель данных
   (`docs/research/data-model.md`) — если решение про сущности.
2. Найди прежнее состояние везде, где оно записано: grep по словам решения
   и по тому, что оно отменяет (в `docs/`, `CLAUDE.md` всех уровней,
   issues). Перечисли места, включая те, где править нечего.
3. Предложи дифф по всем местам одним сообщением:
   - ТЗ — требование, если решение продуктовое; PRD и план — только у фичи
     в работе: сценарии и критерии, задачи текущей фазы;
   - research — решение в терминах нового состояния;
   - issues — `gh issue edit` тела и `gh issue comment` с источником;
   - макет — правка `docs/design/<экран>.html`, если решение визуальное и
     умещается в правку разметки; иначе строка «макет ждёт экспорта» в
     задаче плана.
4. После подтверждения применяй одним коммитом в `main` (переключись на него,
   если дерево чистое; иначе остановись и скажи):
   `docs(decision): <решение>`, в теле — источник. Issues правятся тем же
   заходом.

## Правила

- Документ описывает текущее состояние, не историю: ни врезок «исправлено»,
  ни «раньше было». Ход решения — в сообщении коммита и в источнике.
- Решение против жёсткого ограничения ТЗ § 7 — остановись и скажи: такие
  правки проходят через ТЗ сознательно, не этим скиллом.
- Решение без источника — не решение; спроси, откуда оно.
